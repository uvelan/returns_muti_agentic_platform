### A6. Generic/unvalidated PATCH — confirmed gap

`patch_domain_config` (releases.py:326-370, delegated to by both routers) validates the **merged result** only when `domain_key` is exactly one of `RETURN_PLATFORM_DOMAIN_KEY`, `AI_GATEWAY_DOMAIN_KEY`, or `DEPENDENCY_SIMULATION_DOMAIN_KEY` (releases.py:343-357, `if/elif/elif` with **no `else`**). The route parameter `domain_key: str` (releases.py:326-329) carries no `Literal`/enum constraint. Consequence: `PATCH /api/config/releases/{id}/domains/{anything-else}` merge-patches and calls `save_draft_domain` with **zero schema validation**, for any `domain_key` string. The value is saved to the graph as a DRAFT domain and:
- `promote_release`'s domain-presence/validation check (release_promotion.py:112-134) only inspects the 3 required domain keys — an unknown domain key is simply not looked at, so it is silently along for the ride into VALIDATED/RELEASED and never validated at any point in the lifecycle.
- No test found exercises this path: `grep` for `domain_key`/`unknown`/`arbitrary`/`invalid`/`custom` across `backend/tests/api/test_canonical_config_domains.py`, `backend/tests/test_configuration_api.py`, `backend/tests/test_graph_configuration.py` found nothing matching an unknown-domain-key PATCH scenario.
- Same absence of validation applies to `create_release`'s domain cloning (releases.py:235-241, loops over whatever `domains_to_copy` contains) and to the full-document `PUT save_domain_config` (CFG-C-017, same if/elif/elif pattern, releases.py:294-309).

This is the exact shape the BRIEF asked to flag. Filed as CFG-C-DEF-001 below.

### A7. Secret masking

- `redact_secret_values` (configuration/api/secrets.py:58-92) runs on every response from `router.py`'s `_ok()` helper (router.py:85-87), which wraps every canonical `/api/config/*` response. Matches key-name fragments (`password`, `secret`, `token`, `credential`, `api_key`, `private_key`, `passphrase`, `connection_string`, `dsn`, case-insensitive substring) and masks the value unless it matches `^vault://` (a reference, not a resolved secret). Tests: `backend/tests/configuration/test_canonical_config_api.py:27-118` cover reference-preserved, resolved-masked, case/convention-insensitive, nested structures, non-string-under-secret-key untouched, lists-of-scalars survive, empty-string-not-masked, and (line 195) "every canonical response goes through the scrub."
- **Console router (`/data-console/v1/configuration/...`) responses are NOT scrubbed** — `releases.py`'s handlers return `APIResponse(data=..., ...)` directly with no `redact_secret_values` call anywhere in that file (confirmed by grep: the only import of `redact_secret_values` in `configuration/api/` is `secrets.py` itself and `router.py`, `agents.py`). Any caller of the console path directly (not through the canonical delegator) gets **unmasked** domain payloads. Since `/api/config` delegates through the same handler functions and re-wraps in `_ok()`, the canonical path is safe; a direct call to `/data-console/v1/configuration/releases/{id}` is not. UNVERIFIED whether anything still calls the console path directly (Part B checks the frontend; nothing in this backend read calls it externally).
- `AIGatewaySettingsView` (operations/models.py:561-566) exposes only `interceptMode`, `providerOrder`, `version`, `updatedAt`, `updatedBy` — no credential fields, so no leak surface there.
- `ConsoleSettingsView` (configuration/api/audit.py:61-70) exposes `aiProviderOrder` (provider names only) and `seedVersion`/`environment` — no secret-shaped fields read from `Settings` directly, so no leak there either. Did not exhaustively check every response model against every `Settings` field within this budget; the systematic defence is the response-side scrub (A7 above), which is present on the canonical surface and absent on the console one.

## D. Duplicate / colliding UI

- **D1 — Three unrelated "sources" concepts share the word "sources" with no cross-linking UI.** (a) `/api/config/sources` — live-probed inventory of 4 fixed infrastructure datastores (MongoDB, SQL Server, Neo4j) (CFG-C-008/009, read-only). (b) `/api/source-bindings` — per-dataset override of where a schema's declared source asset is read from (CFG-C-023, has no UI at all). (c) Graph Schema Analyzer → "Data Sources" screen — the analyzer's own connection-definition store for schema authoring, a wholly separate backend artifact (`POST/PUT /api/graph-analyzer/v1/sources`, PART_C_frontend_ui.md:17). An operator following "Data Sources" in the Analyzer is not looking at (a) or (b), and nothing in the UI says so. Not a true duplicate-control defect (each governs different data) but a naming collision the BRIEF specifically asked to check for.
- **D2 — AI provider configuration is edited in one screen, shown read-only in another.** AI Control Center → Providers & Models writes `RETURN_PLATFORM.runtime_integrations.ai_providers` (real write). Configuration → Integrations tab renders the same released document read-only via `JsonView` (C, "Integrations" row) — so the same underlying field is visible in two places, editable in only one. Low risk (no conflicting writes possible since one side is read-only), but worth flagging as a UX duplication the BRIEF's example called out directly ("/config integrations vs AI Control Center providers").
- **D3 — Two schema-editing screens with an unverified relationship.** Graph Schema Analyzer → Schema (Proposed) edits a draft entity/relationship store (`/api/graph-analyzer/v1/schemas/proposed/...`); Schema (Runtime) edits the *whole active document* directly (`PUT /api/schema-releases/active/document`) via a generic JSON editor. Both screens sit under the same `/graph-schema` page (routeManifest.ts, PART_C_frontend_ui.md:33) but it is **UNVERIFIED from this read** whether "Proposed" changes ever flow into "Runtime" through a promotion step, or whether the two are functionally disconnected paths that could be used inconsistently (edit an entity in Proposed, and separately hand-edit and republish the whole document in Runtime, silently discarding the Proposed edit). Flagged for follow-up with the backend/dynamic-knowledge owner rather than asserted as broken.
- **D4 — Two backend surfaces for the same release-domain write** (not currently duplicated in the UI, but latent). Canonical `PATCH /api/config/releases/{id}/domains/{key}` (merge patch, used by all frontend screens per PART_C_frontend_ui.md) and console `PUT /data-console/v1/configuration/releases/{id}/domains/{key}` (full-document replace, CFG-C-017, A5). No screen currently calls the PUT path, so this is a backend-only duplicate today; flagged because a future screen or script could reintroduce the larger blast radius, and because the console path also returns unscrubbed secrets (A7/CFG-C-DEF-003).

## E. Proposed UI split by business domain

Derived from the actual `ReturnPlatformConfiguration`/`AIGatewayConfiguration`/`DependencySimulationConfiguration` field list (return_configuration.py:1650-1739; ai/routing/tasks.py) rather than invented:

1. **Order Discovery & Identification** — `discovery`, `source_resolution`, `clarification_policy`, `selection_vocabulary`. No UI today.
2. **Return Policy & Eligibility** — `return_policy` (incl. `return_method_requirements`), `policy_evaluation`. No UI today.
3. **Workflow & Case Timing** — `workflow`, `return_case`, `business_calendars`, `housekeeping`. No UI today.
4. **Agents** — `agents` + link into `/approvals` for the proposal it files. Exists today (PARTIAL); the split is mostly about making the proposal step visible in the same screen rather than a separate destination.
5. **Support** — `support`, `support_template` (has a screen today), `support_gate`, `support_ingress`, `support_resolver`, `context_assembly`. Today only 1 of 6 fields has a screen; this should be one page with 6 tabs, not a page for one field.
6. **Shipment Tracking** — `shipment_tracking`. No UI today.
7. **Warehouse & Bay** — `bay`. No UI today (distinct from the transactional bay-assignment screens under Operations, CFG-C-031).
8. **OMC & Business Integrations** — `omc`, `integrations` (currently read-only). No write UI today.
9. **AI Gateway** — `AIGatewayConfiguration.tasks` + `runtime_integrations.ai_providers`/`.data_sources`. Tasks and Providers exist today (as two tabs of AI Control Center, which is already roughly this shape); `data_sources` is missing.
10. **Dependency Simulation** — the `DEPENDENCY_SIMULATION` domain. No UI today, despite being required-valid for every promote (F, CFG-C-DEF-009).
11. **Feature Flags, Extensions, Copilot** — `feature_flags`, `extensions`, `copilot`. No UI today; small enough to combine into one page.
12. **Dynamic-Knowledge Graph Schema** — separate artifact, already has a reasonably-shaped two-stage page (Proposed / Runtime) under Graph Schema Analyzer; recommend clarifying (not rebuilding) the relationship between the two stages (D3).
13. **Source Bindings & Sync** — `/api/source-bindings` (no UI) and `/api/graph-sync` (has a UI, `/sync`). Recommend one "Data Sources & Sync" domain page combining dataset rebinding with sync triggering and run history, distinct from the Analyzer's own connection definitions (D1).
14. **Release Governance** — releases list/detail, promote, runtime snapshot, adoption, audit. Cross-cutting; roughly matches today's Configuration → Overview/Releases/Runtime/Audit tabs already.
