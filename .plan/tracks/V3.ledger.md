## step:01 — placement verdict: the existing responder cannot carry the ladder

Required first step (brief item 1, contracts.md §9: *"inspect and extend
`operations/return_support/auto_responder.py` + `agents/support_response.py`
first; a new graph only on a ledger-recorded verdict"*). Both files read in
full — 281 and 225 lines respectively.

### What they actually are

`SupportResponseAgent` (`agents/support_response.py`) **plays Support**. It is
a deterministic simulator of the Support desk: given a `support-handoff-v1`
payload that *the platform sent outbound to Channel B*, it plans what Support
would issue back — RMA reference, tracking, label, shipping instruction —
derived from the released `return_policy.return_method_requirements` table via
`_reference()`, a pure string derivation over the case id. There is no model
invocation anywhere in the file. `confidenceMillionths` is a hard-coded
`950_000` / `1_000_000` literal on the decision view, not a measured
confidence.

`SupportAutoResponder` (`operations/return_support/auto_responder.py`)
executes that plan **on the Support side of the boundary**: acknowledges the
Support *work item*, posts the agent's message to the Support thread, and
records the outcome through `DurableSupportEventStore.record_support_response`
— the same seam `submit_return_outcome` uses. Its inputs are a
`work_item_id`, a `SupportWorkItemView` and a thread message whose
`businessPayload.schemaVersion == "support-handoff-v1"`.

### Verdict: **they cannot carry the resolution ladder.** Six independent reasons.

1. **Opposite direction across the channel.** These two answer *the
   platform's outbound handoff, as Support*. V3's resolver answers *Support's
   inbound question, on the associate's behalf* — the A-side of the bridge.
   The `SUPPORT_RESPONSE_ACTOR = "support-response-agent"` provenance stamped
   on every outcome and acknowledgement is the Support desk's identity;
   reusing it for an A-side answer would make the platform's own reply
   indistinguishable from Support's, which is exactly the provenance loss RV
   rule 6 names. `agents/support_response.py`'s own module docstring states
   the boundary: *"Plans what Support would issue for a handed-off return."*

2. **Wrong input contract, with no adapter that preserves meaning.**
   `_handoff_request` reads a `support-handoff-v1` business payload keyed to a
   work item and, by its own documented rule, *"reads the structured half of
   the handoff only — never the message text"*. V3's input is V2's
   `NormalizedSupportEvent` keyed `(case_id, support_event_id)`, whose whole
   substance **is** `body_text` plus a classified intent. The one rule that
   file states about its input is the rule V3's input violates.

3. **No reasoning plane at all.** The ladder requires: an LLM invocation
   (`support.question.resolve.v1` via `StructuredOutputInvoker`), measured
   confidence compared against `fact_confidence_millionths` /
   `graph_confidence_millionths`, a graph read with its own on-demand sync, a
   tool step, and a per-case LLM budget. `SupportResponseAgent.assess` is a
   synchronous pure function over a requirement table. Every one of those five
   is a new concern; nothing in either file is reused by adding them.

4. **No checkpointing, and no place to put it.** §9 requires
   `SystemStoreCheckpointSaver` on thread `support-resolver:{case_id}:{support_event_id}`
   with resume-at-last-completed-node (acceptance 23). `assess()` is a single
   synchronous call with no nodes and no interruptible boundary; `respond()`
   is idempotent by *re-reading and recognising its own writes*, which is a
   different and weaker guarantee than checkpoint resume — it re-executes the
   whole body every time. Retro-fitting durable node boundaries into
   `respond()` would rewrite it entirely.

5. **Keyed to the wrong identity, in a way that breaks the checkpoint thread.**
   `support_event_id_for(work_item_id)` mints
   `f"support-response-agent:{work_item_id}"` — the support event id is
   *derived from the work item*. V3's thread id needs V2's
   `support_event_id`, which is derived from
   `(case_id, transport_id, external_message_id)` (`derive_support_event_id`).
   Two different id algebras for the same field name.

6. **Frozen-module adjacency and the status guard.** `_ACTIONABLE` refuses to
   act unless the work item is `NEW | ACKNOWLEDGED | IN_PROGRESS`, on the
   documented reasoning that *"a second answer would talk over it"*. A V3
   resolution of an inbound support question is legitimate on a thread whose
   work item is long past those states — the resolver answers a *message*, not
   a *work item*. Loosening that guard would weaken a shipped safety property
   of the Support-side path for a reason having nothing to do with it.

**Therefore:** a new graph module. Neither file is modified; neither is
imported by V3 except `operations/support_handoff.py`'s `_safe`, which is
composition's neutraliser and is imported rather than re-implemented
(carry-forward condition 7).

**Files touched:** `.plan/tracks/V3.ledger.md` (new).
**Commands:** reads only; config-load check.

### The design decision that carries the tool boundary

§9 says config maps intent → eligible capabilities and that arguments are
validated against `input_schema_ref`. The load-bearing choice is that
`input_schema_ref` **names an entry in a code-side allowlist and cannot define
one** — the same device §8 uses for the formatter allowlist. A release's
strongest possible statement about a tool is "this implementation the build
already has is now reachable for this intent". There is no field on
`ToolBindingConfiguration` that holds a value, an expression or a template;
all seven fields are references, and `extra="forbid"` means a release cannot
add one.

`EntityField.coerced` is a type *check*, not a conversion — a trusted fact of
the wrong shape reads as a missing entity (which the router refuses on) rather
than being coerced into something a tool would accept. `bool` is excluded from
`INTEGER` explicitly, because `isinstance(True, int)` is true in Python and
without that line a boolean fact would reach a tool as the quantity `1`.

Defaults are all closed: thresholds 900,000 millionths, `tool_bindings = ()`
(no tool eligible for any intent), `reply_gate.default = review_required`,
`per_case_llm_budget = 12`.

## step:03 — the tool boundary, made structural rather than disciplinary

**New files.** `platform/capabilities/tool_router.py`,
`tests/platform/test_support_tool_router.py` (22 tests).

### How §9's wording became implementable

§9 separates *selection* from *argument supply*, and both are now structural.

**Selection.** `plan_tool_invocation` takes a `ValidatedIntent` — a frozen
dataclass whose `__post_init__` raises `UnvalidatedIntentError` unless it was
built by `validate_intent`, which checks membership in the released closed
taxonomy. A string of support prose cannot become one. The widest thing any
text can do is land on one of the nine taxonomy members, each of which selects
from a list a release wrote.

**Argument supply.** `plan_tool_invocation(intent, bindings, trusted)` — three
parameters, **none of them text**. It cannot take an argument from a support
message because it has nowhere to receive one. `TrustedEntities` is built only
by `trusted_entities_from(*, case_facts, fact_ids, graph_results)`, which is
keyword-only over exactly the two sources §9 permits. Both signatures are
asserted by `inspect.signature`, so adding a `body_text=` parameter later fails
a test rather than passing quietly.

Additional properties, each with its own test: only fields the schema declares
are filled (an extra trusted fact cannot widen a tool's input); a case fact
beats a graph result of the same name (a disagreement is a *conflict* the
ladder escalates, not a precedence the router settles); the executor
**re-validates the schema** rather than trusting the plan, because a plan
crosses a checkpoint boundary and a stale plan against a moved schema is
exactly what "execution requires schema validation" refuses; authorization runs
before the port is touched; the contract *name* resolves through a code-side
allowlist, so a released string cannot name an arbitrary type; and the port
receives `credential_binding_id`, never a value — there is no field on the plan
or the port through which a secret could travel.

### Why the hostile-input test is not a "does not contain" assertion

`HOSTILE_BODY` names a tool, a capability, a contract, a credential id, two
argument values and a framing-shaped heading. The central assertion pins the
**whole composed plan as one equality** —
`ToolInvocationPlan(tool_id=…, arguments={"caseId": "case-REAL",
"returnReference": "RMA-REAL"}, argument_provenance={…}, …)`. A negative
assertion would still pass if the router grew a *different* way to take an
argument from text; this equality fails the moment any field is not exactly
what the trusted bag and the released binding produced.

## step:04 — carry-forward condition 7, discharged

**New files.** `operations/return_support/outbound_composition.py`,
`tests/operations/test_support_outbound_composition.py` (24 tests).

### How condition 7 is discharged

Three composed messages carry words a person typed: the clarification prompt
shown to the associate (carrying Support's question **verbatim**), the
clarification relay back to Support (carrying the associate's answer), and the
reply draft. These are the two shapes the dispatch called the riskiest in the
design.

**The rule is stronger than four-value parity, deliberately.** Composition
`_safe`s exactly four values on the argument "these are the human-typed ones".
That argument has to be re-derived every time a field is added, and V1's defect
is exactly what happens when it is derived once and not repeated. Here:

- section text is a **code constant** — `_QUESTION_HEADING` and friends are
  `Final` strings in this module, never configuration and never a fact;
- **every interpolated value is neutralised, without exception** —
  `render_section(heading, *values)` is the only way to build a line and it
  neutralises unconditionally. Its signature has no parameter for pre-rendered
  text, so no caller can hand it a string it already formatted;
- model-authored reply text is neutralised too, on the reasoning that a model
  which has just read the untrusted input is the most likely thing in the
  system to reproduce it;
- the released **disclosure line** is neutralised (see the blind test below);
- `render_configured_template` neutralises every value **before** substitution,
  and substitution happens once over the template so a value carrying a brace
  cannot re-enter the grammar.

`_safe` is **imported** from `support_handoff.py`, never re-implemented — V1's
own fix, and what makes a second spelling impossible. A test asserts
`outbound_composition._safe is _safe`, so a local copy fails. Parity is stated
over the **pattern** (`_FRAMING.search(shape)`) rather than over a list of four
field names, so a widened `_FRAMING` is covered without an edit here.

### "Verbatim" and neutralisation are not in conflict

The **fact** stores the question exactly as Support sent it — that is the audit
record and nothing here touches it (pinned by a test asserting the input string
is unmutated). The **rendered message** neutralises, and neutralisation only
rewrites a line that *is itself* a heading or separator. An ordinary support
question passes through **byte for byte**, pinned as a whole-output equality,
not asserted. Nothing a support agent could legitimately write is lost: a
question cannot be asked by a bare `SHIPPING INSTRUCTION:` line. A companion
test pins that neutralisation is narrow — `RMA-4471`, `Bay 7`,
`The label is in the bay: check it` and `1Z999AA1` are untouched.

Every hostile-input assertion pins the **whole composed output as an equality**.
No "does not contain" assertion appears in the file.

### The two design choices that carry the contract

**Assembly and rung one are one node.** The first draft had an
`assemble_context` node handing its payload to `resolve_from_facts` through the
state — which is every fact value the prompt carries, precisely what
`resolution_state.py` refuses to checkpoint. Collapsed into one node, so the
context never outlives the call; only `consumed_fact_ids` and `content_hash`
(references) are written. Nothing is lost on resume: `assemble_case_context` is
pure, so the same log and policy give back the same bytes and the same hash.

**Conflict is checked before the threshold.** A graph answer that is both
confident and contradicts the case's own record is the most dangerous thing this
ladder can produce — it would go to Support, under the platform's name, against
the record. Checking the threshold first sends exactly that. Fault C proves the
order is load-bearing.

`attempt` is in neither the state nor the thread id. `support_resolver_thread_id`
takes two keyword arguments and there is no third to vary, which is the form of
the acceptance-23 guarantee that survives an edit.

## step:06 — one composed message, two destinations; and condition 10

**New files.** `operations/return_support/reply_gating.py`,

### The decision that carries brief item 4

`compose_reply` runs **once**, before the gate is consulted, and the resulting
string is what the `SUPPORT_REPLY` review carries as its draft payload *and*
what an `auto_reply` intent posts directly. Composing per path would give the
reviewed message and the unreviewed message two spellings of the disclosure, the
neutralisation and the framing — and the unreviewed one is the path with nobody
looking at it. `test_both_paths_compose_the_identical_message` asserts each
against a **literal**, not against the other: two values from the same function
are equal by construction, and comparing them would pass with both wrong.

The gate **re-reads** `reply_gate` from the release rather than trusting the
ladder's `resolution["requiresReview"]`; the two are written at different times
and the release is the authority (fault C).

`scope_id` is *not* passed to `create_review` — sect. 6 mints a SUPPORT_REPLY
review's scope id server-side — and the value the gate reports is the one that
came back. Both halves are asserted, because either alone is weak: faults D and
E each break exactly one of them.

### Delivery identity without a store

An auto reply has no approving command, so it has no command-derived
`logical_operation_id`. Derived instead: `support-reply:{case_id}:{support_event_id}`
→ `delivery_id = uuid5(fixed namespace, logical_operation_id)`. The observable
property sect. 7 asks for is "a retry reuses the identity and the receiver
absorbs it", and a pure function of two ids gives that without a row that could
be lost between the generate and the store — a stored id has a window where it
is generated and not yet persisted; a derived one has none. Pinned as a literal
uuid, so changing the derivation is a visible edit rather than a silently
different identity (a test asserting only "two calls agree" would pass for a
derivation that returned a constant for every case).

### Carry-forward condition 10, discharged at the seam

A support-derived value reaching associate-facing text with only `.strip()`
behind it is unbounded. `neutralized` now bounds every interpolated value at
`VALUE_CHARACTER_BOUND` (4,000 characters) with a visible `[truncated]` notice.
Two properties, each fault-injected:

* the bound is applied **after** neutralisation, not before — the other order
  lets a value push a framing-shaped line past the cut and out of the
  neutraliser's reach, a truncation that reopens the hole the neutralisation
  closed (fault M);
* the truncation is **visible**, so a reader can tell a cut from a message that
  merely ended (fault N).

The **fact** still stores the value in full: that is the audit record, and
`verbatim_question` means what it says there. Only the rendering is bounded.
Composition emits plain text with no markup, so "render as data, not markup"
holds by construction on this surface; the panel half of it belongs to item 6.

## step:11 — a rung the deployment cannot serve is absent, not stubbed

**Modified.** `operations/return_support/resolution_ladder.py`,
`tests/operations/test_support_resolution_ladder.py` (+12 tests, 24 → 36).

### The problem this had to solve before a factory could exist

Deliverable 1 is a factory that produces a *working* ladder. Three of the
ladder's ports have no implementation in `src/` and cannot get one without
deciding something this slice does not own (step:13 enumerates each). The
compiled graph, though, entered `sync_graph` and `route_tool` unconditionally.
So a factory had exactly three options:

1. **stub the ports** — forbidden, and rightly: a port whose method raises is
   accepted at construction and swallowed at runtime;
2. **return empty** — *worse than raising*. A `GraphReadPort` returning `{}`
   hands the model an empty context it can still answer confidently from, and
   that answer goes to Support under the platform's name. The one failure this
   slice's config defaults exist to prevent;
3. **not compile the rung in.**

Three is the only honest one, and it generalises the brief's own ruling about
`tool_bindings`: *"leaving the tool rung genuinely unreachable is an acceptable,
honest outcome if you record it as such."* The way to make "genuinely
unreachable" checkable rather than claimed is to make it a **fact about the
compiled topology**.

### What changed

* `CaseFactsPort` is **split in two**. It used to carry `fact_log` (the prompt's
  projection) and `trusted_entities` (the tool router's trust projection), with
  a docstring warning that serving both from one object "would invite a caller
  to pass the prompt's projection to the router". Phase 2's finding: the warning
  was the only thing enforcing it. `TrustedEntityPort` is now a separate type
  behind a separate field, required only by the rung permitted to use it.
* `LadderDependencies` gains `LadderRungUnserviceable` and two availability
  properties. `graph_sync`/`graph_read` are both-or-neither; `trusted_facts`/
  `tools`/`principal_id` are all-or-none. **Half a rung is refused at
  construction**, because both halves fail invisibly: a read with no sync
  answers confidently from a stale graph, and an executor with no trusted-entity
  source refuses every invocation with `MISSING_REQUIRED_ENTITY` — which reads
  exactly like a case that genuinely lacked the entity.

## step:12 — the trigger: which questions reach the ladder, and where

**New.** `operations/return_support/resolution_trigger.py`,
`tests/operations/test_support_resolution_trigger.py` (24 tests).
**Modified.** `configuration/support_resolver_configuration.py`
(`trigger_intents` + one validator).

This is the deliverable. The ladder had no production invocation site; this
decides when it runs, on what, and what becomes of what it decided.

### Where: the existing classify command, not a fifth topic

`ResolvingSupportMessageClassifyDispatcher` **delegates** to V2's
`SupportMessageClassifyDispatcher` and then triggers, on the same
`return-case.support-message.classify` command. Three reasons, in the order they
decided it:

1. **Sect. 7's topic list is an enumeration, and enumerations here are closed.**
   AMENDMENT-1 established that widening one takes an orchestrator amendment and
   not an implementation — §8's binding sources went three to four exactly that
   way. A slice quietly adding a fifth topic would be doing the thing
   AMENDMENT-1 exists to forbid. **No amendment is needed for this design**,
   which is itself part of why it is this design.
2. **The classified intent — the trigger's whole input — exists once, at the end
   of that dispatch.** A separate topic would carry it in a payload (a second
   copy of a committed decision, free to disagree with the record) or re-read
   the record anyway.
3. **The retry envelope is already right.** V2's analysis reuses accepted stage
   results rather than re-invoking, so a redelivered classify command re-runs
   analysis for free; the ladder is checkpointed per `(case_id,
   support_event_id)`, so redelivery *resumes* it.

The cost is stated, not hidden: a resolution failure fails a command whose
analysis half committed. Acceptable because every write on both sides is
idempotent — and made legible by a **distinct `error_code`**
(`SUPPORT_RESOLUTION_FAILED`), because an operator triaging the dead-letter
queue must not be told to look at a stage that succeeded. Fault L injects the
shared code and is caught.

**No V2 file is modified.** Delegation, not modification: V2's dead-letter
classification is the one piece of code that decides whether a support message
ever stops retrying, and re-implementing it here to add four lines would be a
second copy of it. V2 also keeps its own factory for a process that wants
analysis without resolution.

### Which: `info_request`, and why that is a real answer rather than a cautious one

New released `support_resolver.trigger_intents`, default `("info_request",)`.
Of sect. 5's closed taxonomy — `info_request, rma_issued, label_issued,
shipping_instruction, tracking_provided, partial_fulfillment, rejection,
acknowledgement, other` — **`info_request` is the only member in which Support
is asking rather than telling.** The other seven are Support informing the
platform and V2's extraction already commits what they say; running a ladder
over one of them would compose a reply to a statement.

Asserted over the **whole taxonomy** rather than one positive and one negative,
because a predicate that triggered on eight of nine passes a two-case test.

**`other` cannot be configured as a trigger, and that is refused at parse
time.** It is not a classification; it is `coerce_intent`'s sink for everything
the classifier did not recognise, so triggering on it triggers on every
unclassifiable message on every case. A release naming it fails to load with
that sentence, rather than being discovered as a bill.

### The second condition, because intent alone is not enough

**The message must carry prose.** A structured `.../return-outcome` event
normalises with no `body_text`; its intent can still be a trigger intent, and
the ladder would then be handed an empty `question_text` and asked to answer it.
A model given no question still returns *something*, and the gate would carry it
to Support under the platform's name.

Ordered intent-first deliberately: `rma_issued` with no prose is not a question
*whatever* its body, and reporting `no_question_text` for it would invite an
operator to conclude that a body would have made it resolvable. Fault D swaps
the order and is caught.

The intent is read from the **committed** `accepted_classification` on the
analysis record and coerced through `coerce_intent` over the same released list
— not taken from the dispatch's return value. Same discipline
`require_accepted_extraction` enforces on the other stage: a value handed along
in memory is free to disagree with the record after a concurrent worker won the
CAS.

### What the terminal becomes, and a phase-1 function that had no caller

`resolution` → `gate_reply`. `escalation` → `support_clarification_requested`,
composed through **`compose_clarification_prompt`** — which had tests and, until
now, **no production caller anywhere in `src/`**. Written, reviewed, merged,
never executed: the exact shape the frontend phase found ~800 lines of. This is
its call site, and the hostile-question test proves the composer is doing work
(a forged `SUPPORT IS ASKING YOU THIS:` in the question survives as neutralised
text and does not become a second heading).

The associate reads a sentence, not an enum: `SUB_THRESHOLD` on a console tells
a branch associate nothing, and the six reasons call for different actions from
them. Fault J shows the raw value and is caught.

Resolver clarification ids use **their own uuid5 namespace and prefix**, so a
resolver escalation and V2's artifact clarification on the *same support event*
can never mint one id. Fault I collides them and is caught.

### Check-then-act, and why the check is not decoration

`resolve` has three branches: terminal already (land it again — every write is
append-once or keyed on a derived delivery identity), partially complete
(`ainvoke(None)`), fresh (`ainvoke(initial_state)`).

LangGraph applies an input state as an **update** to whatever the thread holds.
Passing the initial state on a retry would reset `llm_invocations_used` to zero
and `graph_synced` to `False` — silently defeating `per_case_llm_budget` and the
sync-once guarantee acceptance 23 is about, **while the run still completed and
still looked right**. So the retry test asserts the invocation count and the
counter, not the completion.

`run_id` is derived rather than generated, for the reason the thread id has no
attempt component: two resumes of one thread must not claim to be two runs.

1. **The two activity bodies had no activities.** `record_clarification_answer`
   and `relay_clarification_to_support` existed in

2. **The endpoint's command payload could not have deserialized into the signal

   unchanged — so the payload *is* `ClarificationAnsweredNotice`. It was

   answered_by}` against a notice requiring `{clarification_id, actor, signal_id,

   passed. Now field-for-field, with two tests pinning it — one that every key is
   a field, and one that **constructs the notice**, because the subset check
   alone passes for a payload missing a required field, which is exactly how the
   old shape failed.
3. **`case_has_return_details` is registered on no worker.** Found by a test
   written for *my* two activities and general enough to see it: the workflow
   calls it, `worker.py` never registers it, and an unregistered activity raises
   nothing and logs nothing — the execution schedules the task and waits. A
   pre-existing stall, reachable whenever `timings.return_details_required` is
   on. Registered, and flagged in the delta report as **not V3's defect**.

### The handler's three decisions

**Async, not record-and-drain.** Every other signal here records into state for
the main loop; that is right for a review notice, which only means anything
while the gate is open. A clarification answer is owed **whether or not any
review is waiting** — a case whose gate had closed would otherwise record an
answer nothing ever drains. `_await_template_reviews` already waits on
`workflow.all_handlers_finished()` before `continue_as_new`, so an in-flight
handler is a shape this workflow was already built for.

**Fact before relay, never the reverse.** The relay is the irreversible half:
it puts the associate's words in front of Support. Relaying first opens a window
in which Support has been told something the case cannot show it ever decided.
Fault A reverses them and five tests fail.

**Both deadlines cross the boundary, or neither.** The released
`clarification_resets_deadline` is implemented once, as the pure
`deadline_after_clarification` in `operations` — which the workflow may not
import (keeping `operations` out of the Temporal sandbox is the rule this file
already follows for `review_aggregate`). Re-spelling its `max(...)`
workflow-side is how one released switch acquires two meanings. So the workflow
resolves both instants through `resolve_business_deadline` and the activity
decides. With the gate closed it sends neither, rather than a stale instant the
activity's guard happens to ignore today.
