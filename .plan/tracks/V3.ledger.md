## step:01 — placement verdict: the existing responder cannot carry the ladder

Required first step (brief item 1, contracts.md §9: *"inspect and extend
`operations/return_support/auto_responder.py` + `agents/support_response.py`
first; a new graph only on a ledger-recorded verdict"*). Both files read in
full — 281 and 225 lines respectively.

### What they actually are

`SupportResponseAgent` (`agents/support_response.py`) **plays Support**. It is
a deterministic simulator of the Support desk: given a `support-handoff-v1`
payload that *the platform sent outbound to Channel B*, it plans what Support
would issue back — RMA reference, tracking, label, shipping instruction —
derived from the released `return_policy.return_method_requirements` table via
`_reference()`, a pure string derivation over the case id. There is no model
invocation anywhere in the file. `confidenceMillionths` is a hard-coded
`950_000` / `1_000_000` literal on the decision view, not a measured
confidence.

`SupportAutoResponder` (`operations/return_support/auto_responder.py`)
executes that plan **on the Support side of the boundary**: acknowledges the
Support *work item*, posts the agent's message to the Support thread, and
records the outcome through `DurableSupportEventStore.record_support_response`
— the same seam `submit_return_outcome` uses. Its inputs are a
`work_item_id`, a `SupportWorkItemView` and a thread message whose
`businessPayload.schemaVersion == "support-handoff-v1"`.

### Verdict: **they cannot carry the resolution ladder.** Six independent reasons.

1. **Opposite direction across the channel.** These two answer *the
   platform's outbound handoff, as Support*. V3's resolver answers *Support's
   inbound question, on the associate's behalf* — the A-side of the bridge.
   The `SUPPORT_RESPONSE_ACTOR = "support-response-agent"` provenance stamped
   on every outcome and acknowledgement is the Support desk's identity;
   reusing it for an A-side answer would make the platform's own reply
   indistinguishable from Support's, which is exactly the provenance loss RV
   rule 6 names. `agents/support_response.py`'s own module docstring states
   the boundary: *"Plans what Support would issue for a handed-off return."*

2. **Wrong input contract, with no adapter that preserves meaning.**
   `_handoff_request` reads a `support-handoff-v1` business payload keyed to a
   work item and, by its own documented rule, *"reads the structured half of
   the handoff only — never the message text"*. V3's input is V2's
   `NormalizedSupportEvent` keyed `(case_id, support_event_id)`, whose whole
   substance **is** `body_text` plus a classified intent. The one rule that
   file states about its input is the rule V3's input violates.

3. **No reasoning plane at all.** The ladder requires: an LLM invocation
   (`support.question.resolve.v1` via `StructuredOutputInvoker`), measured
   confidence compared against `fact_confidence_millionths` /
   `graph_confidence_millionths`, a graph read with its own on-demand sync, a
   tool step, and a per-case LLM budget. `SupportResponseAgent.assess` is a
   synchronous pure function over a requirement table. Every one of those five
   is a new concern; nothing in either file is reused by adding them.

4. **No checkpointing, and no place to put it.** §9 requires
   `SystemStoreCheckpointSaver` on thread `support-resolver:{case_id}:{support_event_id}`
   with resume-at-last-completed-node (acceptance 23). `assess()` is a single
   synchronous call with no nodes and no interruptible boundary; `respond()`
   is idempotent by *re-reading and recognising its own writes*, which is a
   different and weaker guarantee than checkpoint resume — it re-executes the
   whole body every time. Retro-fitting durable node boundaries into
   `respond()` would rewrite it entirely.

5. **Keyed to the wrong identity, in a way that breaks the checkpoint thread.**
   `support_event_id_for(work_item_id)` mints
   `f"support-response-agent:{work_item_id}"` — the support event id is
   *derived from the work item*. V3's thread id needs V2's
   `support_event_id`, which is derived from
   `(case_id, transport_id, external_message_id)` (`derive_support_event_id`).
   Two different id algebras for the same field name.

6. **Frozen-module adjacency and the status guard.** `_ACTIONABLE` refuses to
   act unless the work item is `NEW | ACKNOWLEDGED | IN_PROGRESS`, on the
   documented reasoning that *"a second answer would talk over it"*. A V3
   resolution of an inbound support question is legitimate on a thread whose
   work item is long past those states — the resolver answers a *message*, not
   a *work item*. Loosening that guard would weaken a shipped safety property
   of the Support-side path for a reason having nothing to do with it.

**Therefore:** a new graph module. Neither file is modified; neither is
imported by V3 except `operations/support_handoff.py`'s `_safe`, which is
composition's neutraliser and is imported rather than re-implemented
(carry-forward condition 7).
