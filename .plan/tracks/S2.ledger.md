Both of this step's rules are **refusals**, and both guard the same mistake: treating
a case that is waiting as a case that is broken.

- **Files touched:**

    `AWAITING_SUPPORT`) and `_is_legitimate_wait`, gating the **time-based** sweep
    (`ReturnCaseWorkflowRecovery.recover_once`) only — that sweep reasons from elapsed
    time alone, which is no evidence at all about a case designed to sit until a person
    answers. The probe-based `ReturnCaseRecoveryService` is deliberately untouched: a

# RV round 1 — CHANGES_REQUIRED, three findings addressed

Verdict `.plan/reviews/S2-1.md` (commit `db7bfb9`). All three findings are the same
family: multi-write sequences leaving durable state disagreeing with itself. Each was
reproduced before fixing and re-injected after, per the process rule.

## step:09 — F1 (BLOCKING): the legitimate-wait skip starved the recovery queue

- **The miss, in my own words.** I was right that relaunching a legitimate wait is
  wrong, and wrong that skipping was therefore safe. Relaunching was never the only
  thing that pass did: `ensure_case_workflow` also re-writes `cases.workflowId`, and
  `return_case_launcher.py` docstring names *this sweep* as the designated repair for
  a link write it deliberately swallows — "the recovery sweep re-writes the link on its
  next pass". I falsified that sentence for three statuses without amending it. Worse,
  `list_cases_without_workflow` selects `workflowId: None` oldest-first under a limit,
  so a skipped case never left the queue and, being old, sat at the head of every later
  batch. Monotonic: a matter of time, not chance.
- **Fix:** kept the refusal to relaunch, dropped the refusal to repair.
  `_repair_workflow_link` binds the link and starts nothing. **`bind_case_workflow`
  rather than `ensure_case_workflow`** deliberately: the latter would *start* an
  execution if none existed, which is the relaunch being refused; the former cannot,
  and is idempotent on `workflowId: None`. The id is derived via
  `return_case_workflow_id`, never read back from the link being repaired (advisory A2).
  A failure is logged, not raised — one case's link must not block the sweep from
  reaching the unlaunched cases behind it, and the write is retried every pass instead
  of never.
- `RecoverableCaseRepositoryPort` gains `bind_case_workflow`; `CaseRepository` and the
  other existing double already satisfy it.
- **Evidence.** Two new tests, and the queue double was rebuilt to the shipped query's
  real shape (filters `workflowId: None`, sorts `createdAt` ascending, applies `limit`)
  — an unfiltered double would have let the starvation test pass over a starving sweep.
  `_RecordingLauncher` now writes the link the real launcher writes, so "the launched
  case left the queue" is a real assertion. **Before:** reverting the fix to the bare
  `continue` reproduced RV's probe exactly — `launcher.calls == []`, the one genuinely
  unlaunched case never recovered over five passes, 2 failed / 12 passed. **After:**
  14 passed; `launcher.calls == ["case-never-launched"]` and the queue fully drains.

## step:10 — F2 (BLOCKING): `created` was decided by a pre-read, not by the insert

- **The miss.** The docstring said `created` "can only be known by whoever won the
  insert" and then computed it from a read taken before the insert. Under the branch's
  own race construction the **loser reported `created=True`**, having opened nothing.
  My race test asserted the id, the thread and the document count — everything except
  the one field the race can corrupt.
- **Fix:** `open_case_thread` now delegates to `_open_case_thread`, which returns
  `(item_id, created)`. `created` is `True` on exactly one path — the return after a
  committed transaction; both non-committing paths (the idempotency pre-read and the
  `DuplicateKeyError` loser) return `False`. `open_case_thread`'s public `str`
  signature is unchanged, so no existing caller moves.
- **Interface note (V1/V2-facing):** `CaseSupportThread.created` keeps its name, type
  and meaning; what changed is that it is now *correct* under concurrency. No signature
  change. A consumer that had (reasonably) not trusted it can now rely on exactly one
  caller per case seeing `True`.
- **Evidence. Before:** injecting the pre-read derivation → `assert loser.created is
  False` fails with `created=True`, 1 failed / 9 passed. **After:** 10 passed. The
  race test's blind counter dropped 2→1 because the redundant second pre-read is gone;
  the comment now records that blinding one *more* read would make the code re-raise
  rather than converge, so the count is load-bearing in both directions.

## step:11 — F3: the conflict-marker pair, and the untested approval direction

- **The miss.** Contracts §6 says the marker is "cleared **by** the canonical-edit
  write" — one write. Both `_after_edit_written` and `resolve_canonical_edit` did two
  unsessioned writes. Torn either way the pair is unrecoverable, because
  `conflict_marker()` reads the stored flags rather than recomputing: a phantom
  conflict for ever, or a 409 with nothing visible to resolve.
- **Fix:** both pairs wrapped in `with_transaction` with the session threaded through
  `_bump_conflict_marker`, the shape `approve()` and `retry_delivery()` already used.
  `_CanonicalEditLockLost` raises inside the transaction on a lost version CAS so the
  marker clear cannot commit for a canonical edit that was never written.
- **Scope note:** the *edit rows* stay outside the transaction on purpose.
  `_after_edit_written` recomputes the actor set from those rows, so an aborted pass
  is rediscovered on the next write — the rows self-heal, the flag pair cannot, and
  only the pair that cannot needed wrapping. Pinned by its own test.
- **Advisory A3 also closed:** the approval transaction's command/outbox-leg failure
  direction is now pinned. RV injected the moved-insert shape and my suite stayed green
  38/38; it no longer does.
- **Evidence. Before:** reverting the SET leg to two unsessioned writes → 2 failed;
  reverting the CLEAR leg to a post-transaction write → the torn state caught precisely
  (`canonicalEditVersion == 1` with the marker still set — the phantom-conflict case);
  moving the command/outbox insert outside the approval transaction → 3 failed,
  including the new test. **After:** 42 passed.

## step:12 — N1 (BLOCKING): the race test's blind counter was not load-bearing downward

- **The miss, and it was mine twice over.** I wrote "the counter is load-bearing in both
  directions" into a comment without measuring downward. RV measured it: at `2` the test
  fails (the loser's re-read is blinded and the code re-raises — the direction I *had*
  reasoned about), at `0` it **passes**. With nothing blinded the loser takes the ordinary
  pre-read path, the insert is never attempted, the unique index is never reached, and

- **Why it mattered:** this is the *only* guard on F2, whose failure mode is a duplicate
  opening message to Support. The number is coupled to production read counts and had
  already moved 2 -> 1 this round because a read was removed. The next such edit takes it
  to 0-effective, silently.
- **Fix:** the test now verifies its own injection rather than trusting a magic number.
  Two assertions: the blind fired exactly once, and — the stronger one — the loser's
  insert was actually **rejected by the unique index** (`insert_one` is wrapped to count

  the counter alone can never be: it asserts the `DuplicateKeyError` path this test exists

## step:13 — A1: the `_CanonicalEditLockLost` abort, pinned

- **The gap:** RV deleted the raise and the suite stayed green at 42, while the marker

## step:13 — the `except Exception` caveat: answered by removing the mode, not by arguing

RV's caveat: a port omitting `bind_case_workflow` would be swallowed by
`_repair_workflow_link`'s broad catch and degrade **silently** back to round-1 starvation.

**My answer: the broad catch is right, and the thing it could hide should not be able to
reach it.** The two failures are different in kind and I had been treating them as one.

- An *operational* failure (a transient write error) is per-case and self-correcting: the
  write is retried on every later pass, so swallowing it is correct and is exactly what
  keeps one case's link from blocking the cases behind it. That is what the catch is for
  and it stays broad for it. Pinned by
  `test_an_operational_link_failure_does_not_stop_the_sweep`.
- A *missing method* is neither per-case nor transient: it fails identically for every
  case on every pass, for ever, which is the invisible permanent degradation. So it is now
  refused **at construction** with a `TypeError` naming the consequence — loud at wiring
  time, before a single case is mishandled. `AttributeError` is additionally excluded from
  the runtime catch: reaching it means the construction check was bypassed, and swallowing
  a programming error into a per-case warning is how the invisible mode gets built.
- **Evidence:** removing both the construction check and the `AttributeError` re-raise →
  2 failed. Neither guard is decorative.
