## R2 — OpenAPI document honesty

### step:R2-01 — confirm the mechanism before changing nine fields

Measured on the published document before touching anything:
`CaseFactProjection` had **11 properties, 2 required** (`factId`, `factName`),
gap of nine: `acquisitionMethod`, `actorId`, `agentId`, `channel`, `observedAt`,
`recordedAt`, `sourceSystem`, `supersedesFactId`, `value`.

**Mechanism confirmed** by direct probe rather than assumed:

```
class M(BaseModel):
    a: str | None = None   ->  required: []      {"anyOf":[str,null], "default": null}
    b: str | None          ->  required: ["b"]   {"anyOf":[str,null]}
```

Any default — `= None` included — emits the field non-required. No default gives
required-and-nullable, which is exactly what the writer guarantees:

- `case_repository.append_scoped_case_fact:429-451` builds the document with
  every key present, `actorId` explicitly written with `None` included and an
  in-source comment saying why.
- `case_projection/assembly.py:487-501` (`project_facts`) binds all eleven
  fields explicitly on every construction — no spread, no conditional.

So *absent* and *null actor* stay distinguishable. Mechanism verified.

### step:R2-05 — the data assertion, and the gate that runs it (rule 13)

New `frontend/scripts/check-served-fields.js`. Reads the **generated**
`frontend/openapi/return-platform.openapi.json` as data and asserts
`CaseFactProjection`'s `required` array names all eleven properties.

**Wired into `contracts:check`**, which CI's `contract drift` job
(`.github/workflows/checks.yml`) runs:

```
contracts:served: node scripts/check-served-fields.js
contracts:check : contracts:generate && contracts:served && git diff --exit-code …
```

Ordered *before* the `git diff`, so a regression reports the missing field by
name instead of an opaque diff.

**Why a data assertion and not a type test — both traps confirmed empirically:**

- *The `Served<>` vacuous pass.* The alias is `{[K in keyof T]-?: …}`; it strips
  `?` regardless of the document, so any assertion against it or anything
  derived from it passes for nothing.
- *`tsc` invariance — measured, not argued.* See the injection below: with the
  defect reintroduced, `npx tsc -b` exits **0**. A typecheck injection here
  would be unpassable, so any red would be red for an unrelated reason.

The pin names all eleven fields in full rather than counting them: a count
passes when one field is renamed and another dropped. Three claims are reported
separately (pin still matches the schema / no new undeclared property / nothing
declared-but-not-required) so a rename and a lost `required` entry cannot read
as the same failure. The allowlist is deliberately per-schema, not global —
fourteen schemas legitimately under-declare today and a global rule would fail
on unauthorised work.

## R3 — an empty reply draft must not be approvable

### step:R3-01 — where the rejection belongs, verified against source

The reported symptom was two panes disagreeing about how to describe an empty
reply. The defect is that the draft was **approvable**.

Anchors checked before editing:

- `review_aggregate.approve` (`OPEN -> APPROVING`) already refuses
  `PendingRevisionError` and `ReviewConflictError`. Confirmed.
- The **gap** rejection is *not* in the aggregate. It lives in
  `return_case_activities._auto_send_or_reason` (~line 2001), which reads
  `_gap_field_ids(review)` and returns `TEMPLATE_REVIEW_GUARD_BLOCKED`. So the
  brief's "the aggregate already has the rejection path" is right about the
  *shape* (conflicts and revisions) and the gap check is a workflow-side
  sibling. **Recorded rather than adapted around** — it does not change where
  this condition goes, and the aggregate is the better home precisely because
  it covers both the associate's approve and `auto_send`.
- Reply payload shape from `return_support/reply_gating.py:225` —
  `draft_payload={"messageText": composed.text, ...}`.

### step:R3-02 — the server-side refusal

`operations/review_aggregate.py`:

- `EmptyReplyBodyError`, `EMPTY_REPLY_BODY_GAP_REASON = "SUPPORT_REPLY_BODY_EMPTY"`,
  `REPLY_BODY_FIELD = "messageText"`.
- `_has_reply_body(payload)` — `isinstance(str)` **and** non-empty after
  `.strip()`. Whitespace is not a body: a blank message is delivered and reads
  as an agent with nothing to say. A missing key and a non-string are equally
  empty.
- In `approve`, guarded on `reviewKind == SUPPORT_REPLY`.

Three placement decisions, each with a reason rather than a default:

1. **Against the frozen payload, not the draft.** `canonical_review_payload`
   returns the canonical edit when one exists. The case a draft-only check
   misses is the one an associate can actually cause: composed with text, box
   cleared, canonical edit empty while `draftPayload` still reads fine.
2. **Before the hash check.** A stale client approving an empty body has two
   problems and only one is fixed by reloading; "rebuild the reply" is the
   action either way.
3. **Safe to decide on the read.** Verified in source: `draftPayload` changes
   only with `$inc draftVersion`, `canonicalEdit.canonical_payload` only with
   `$inc canonicalEditVersion`, and the approval transaction CASes on both. The
   payload cannot move between the check and the lock without the lock missing.

`api/case_reviews.py`: added to `_CONFLICTS` (409), and `gap_reason` added to
the detail fields `_conflict` copies, so the 409 carries **why** and not just
"no".

**Deliberately not touched:** `_auto_send_or_reason`'s `except` tuple. Reply
auto-send does not exist — `allow_system=True` has exactly one caller and it is
the template snapshot activity, and un-gated replies bypass the review entirely
(`reply_gating.py`). Adding `EmptyReplyBodyError` there would be unreachable
code today. If reply auto-send is ever built, that path needs its own handling
and a loud failure is better than a guard-block nobody designed.

### step:R3-03 — the client, one constant

`sections/supportReplyDraft.ts` — the module **both** panes already import —
gains `EMPTY_REPLY_NOTICE`, the present-tense actionable sentence.

- `CasePanel.tsx` renders it instead of `"This reply was empty."`, which is
  **deleted**. A live draft is never described as a closed record: `reviews[]`
  carries `OPEN`/`APPROVING`/`DELIVERY_FAILED`/`HELD_FOR_OPERATIONS`, so the
  draft is usually still pending, and the past tense told the associate a
  decision they still have to make was already behind them.
- `SupportReplyBody.tsx` renders the constant instead of its own literal.
- `CasePanel.tsx`'s comment claiming this view is "a record of what was sent"
  is **corrected** — it is false for every review that has not been sent. The
  replacement says what is actually true of the card and points at
  `approved_by` as the only thing on it that asserts anything happened.

**`ReturnCopilotFabrication.test.ts`:** both empty-reply entries removed from
`ABSENCE_VOCABULARY`. The AST walk notes *literals*, not identifiers
(`literalOf` in `fallbackPositions`), so with both surfaces on a shared
constant neither position is a literal any more and the two entries would
match nothing. A stale allowlist line is exactly what that list is written not
to accumulate. Recorded honestly: **this does remove those two positions from
the fabrication walk's view.** What replaces it is stronger — the constant is
pinned by `SupportReplyReview.test.tsx` and the *send* is refused server-side,
so the wording is no longer the defence.

### step:R3-04 — fault injection, three of them, each verified

**A — remove the guard block (4 lines) from `approve`.**
Verified the injection: `grep -c EmptyReplyBodyError` fell 2 → 1 (the class
definition survives, the `raise` is gone).
Result: **8 failed, 106 passed.** Exactly the eight refusal tests.
**The tell:** the failure reason is `Failed: DID NOT RAISE EmptyReplyBodyError`

**B — make the guard refuse *every* reply** (drop the `_has_reply_body` call,

**C — frontend, restore the past-tense literal in `CasePanel.tsx` only.**

read-only operations pane". The review-pane test stayed green, because

surface that diverged and nowhere else, which is what a shared-constant pin

Restored after each; all three suites green again.

### step:R3-05 — test fixture correction, and why it was necessary

`test_a_reply_review_approves_onto_the_reply_command_kind` began failing on the
real fix, correctly: `_open_review(kind=SUPPORT_REPLY)` built the reply from

made `_open_review` default by kind, so a reply fixture is a reply rather than
a template wearing one, with `draft_payload` passed explicitly wherever the
payload is the subject of the test.
