## R1 — the bundle guard

### Step R1:01 — investigate before choosing a number

**The brief's hypothesis was that 79.1/80 kB entry passing while the total sat
18.5 kB over is the signature of a shared dependency bundled into several route
chunks rather than hoisted. Measured, and it is not.**

A `generateBundle` plugin dumped every chunk's `moduleIds` with rendered lengths.

| measure | value |
|---|---|
| chunks | 29 |
| distinct module ids | 386 (116 `src/`, 266 `node_modules`) |
| **module ids appearing in more than one chunk** | **0** |
| **packages resolved at more than one `node_modules` path** | **0** (of 23) |
| raw duplicated bytes | **0** |

**Instrument verified before the answer was trusted**, three ways, because "zero"
is exactly the answer a broken detector gives:

1. *Positive control.* Planting one module id into a second chunk in the
   collected data made the analyzer report exactly 1 duplicate. It detects what
   it is looking for.
2. *The blind spot named.* Same-id-in-two-chunks would miss two **copies of a
   package on disk**, which produce *different* ids. Checked separately by
   grouping ids to package roots: 23 packages, none resolved at two paths.
3. *Coverage.* 116 `src/` ids against 128 non-test `src/` files — the gap is
   type-only modules and re-export barrels erased at build. Probed by name:
   `copilotTokens.ts`, `api/cases.ts`, `DomainShell.tsx`, `registry.ts` each
   appear exactly once, in one chunk.

**Verdict: no duplication. `manualChunks` had nothing to remove, so no
`manualChunks` change was made.** Rolldown already hoists what is shared — the
twelve small chunks in the build output (`chevron-down-*`, `client-*`,
`useMutation-*`, `datetime-*`, `cases-*` …) *are* that hoisting.

What actually explains the split verdict is that **the two lines measure
different things**. The entry is what every visitor pays for before paint; the
total sums every chunk including route chunks most visitors never load. The
largest single chunk is the graph analyzer at 95.3 kB gzip (`@xyflow/react`,
`@xyflow/system`, `@dagrejs/dagre`) — **a third of the whole total, on one lazy
route.** The weight is real feature weight, correctly split.

### Step R1:02 — a second, unasked finding: 79.1 kB was never the gate's number

`check-bundle.js` measures the entry at **78,261 bytes (76.4 kB)**, not 79.1 kB.
The 79.1 figure in `.plan/merge.md` and in the dispatch is from **vite's
build-output column**, a different instrument. No gzip level reproduces it
(levels 1 / 6 / 9 / default give 86.7 / 76.4 / 76.3 / 76.4 kB).

So the premise "entry has 1.1 kB of headroom" was itself measured off the wrong
instrument: against the gate's own 80 kB the margin was **3.6 kB (4.4%)**. The
conclusion the brief drew from it — too tight to keep as a fixed threshold —
survives; the number supporting it did not. Cause of vite's disagreement not
chased, because the gate's measurement is the one that decides the build.

### Step R1:03 — RATCHET, not a raised threshold

**Decision: convert both budgets to a ratchet.** Recorded values in
`frontend/bundle-budget.json`; `check-bundle.js` fails on growth.

Why the ratchet over "raise the total and give the entry headroom":

- **There is nothing to bless and nothing to raise *for*.** Step R1:01 removed
  the duplication story, so raising the total would have been recording feature
  weight against a number picked once in a different world.
- **A picked number answered both questions wrong at the same time.** 260 kB
  called correctly-split lazy weight an emergency; 80 kB called a 4.4% margin
  fine. One constant cannot be right about both lines, because the lines measure
  different things.
- **It removes the judgement from every future change**, which is the brief's own
  stated attraction and the thing that makes the guard maintainable by whoever
  touches it next rather than only by whoever wrote it.
- **The two instruments disagreeing (R1:02) is itself an argument for recording a
  measurement rather than reasoning about a threshold.**

Guarded against the ratchet's known failure mode — drifting up one commit at a
time — by making it **self-pruning, on the repository's own precedent**: a build
that comes in >3% *below* the record also fails, printing the number to write.
That is exactly the reasoning `scripts/ci/known_test_failures.json` already
states about itself ("a known failure that quietly got fixed must not stay on
this list"). A 0.5% growth allowance absorbs zlib drift between Node patch
releases, without which the gate would flake on the toolchain rather than on the
bundle — vindicated in testing, where a chunk-hash change alone moved the entry
by 4 bytes.

The values live in a JSON data file rather than as constants in the script so
that changing them is **a diff a reviewer sees**.

### Step R1:04 — the actual defect: wire it to a gate (rule 13)

`.github/workflows/checks.yml`, `frontend-static` job. `vite build` and
`npm run check:bundle` added as **two separate steps**, not one `npm run build`.

The header comment that said `vite build` and `check:bundle` were "gated by
nothing at all until the budget is settled" is replaced, and the decomposition
now has a *different* reason rather than none: `&&` short-circuits, so under one
`npm run check` a lint error means the bundle is never measured at all; and a
failing step names itself on the GitHub summary line, where "check" could be any
of five things.

Exit codes discriminated per the file's existing convention: `>1` from the check
is node failing to run the script, not a verdict about the bundle.

`FRONTEND_BACKEND_TARGET` is set for the build step — `vite.config.ts` throws
without it by design.

### Step R1:05 — fault injection, both arms, each verified

**A PR that adds weight now fails CI with nobody running a local build.** Proven
twice, and each injection was checked for doing what it claims:

| injection | entry | total | gate |
|---|---|---|---|
| baseline | 78,261 | 285,173 | ✅ green |
| **eager import** of `@dagrejs/dagre` into `main.tsx` | **94,289 (+20.5%)** | 285,492 (+0.11%) | ❌ **entry line only** |
| **82 kB of high-entropy data** imported by `ApprovalsPage` (lazy route) | 78,257 (−0.005%) | **330,221 (+15.8%)** | ❌ **total line only** |
| baseline inflated to 400,000 by hand | — | 285,173 vs record | ❌ **"SMALLER … record it: 285173"** |

**The tells that the injections did what they claim, not merely that something
went red:**

- The eager-import injection moved the total by **+0.11%** while the entry grew
  20.5%, and the analyzer chunk *shrank* 95.30 → 79.45 kB in the build log. That
  is a **move**, which is what importing an already-bundled library eagerly does.
  Had the total jumped 16 kB too, the injection would have been adding a second
  copy — a different fault, and a red for the wrong reason.
- The lazy-route injection moved the entry by **−4 bytes**. If the entry had
  grown, the route would not actually be lazy and the total-line red would have
  proved nothing about lazy weight. `ApprovalsPage` went 4.04 → 49.10 kB gzip:
  the data landed exactly where it was imported.
- **Each injection fired exactly one line and stayed silent on the other** —
  discrimination a single number could not have given.

Both reverted; `git status` clean of them before commit.

## R4 — contrast: fix the rule, not the colours

### Step R4:01 — measured, at the opacity each is actually drawn with

The rule being established: **an opacity modifier is never applied to a
`*-container` background whose foreground is the paired `on-*-container` token.**
The pair is contrast-tested as a pair; tinting one side invalidates the test.

`-container/` grepped across the whole frontend. Every instance of the *paired*
shape, measured against the surface it composites over (worse of
`surface-container-lowest` and `surface`):

| token / call site | tint | measured | full strength | verdict |
|---|---|---|---|---|
| **`review.conflict`** | `/40` | **1.29:1** | 4.54:1 | **FAIL** |
| `review.gap` | `/30` | 8.68:1 | 7.24:1 | pass (AAA) |
| `review.clarification` | `/40` | 5.44:1 | 4.57:1 | pass |
| `support.notice` | `/40` | 5.44:1 | 4.57:1 | pass |
| `support.warning` | `/30` | 8.68:1 | 7.24:1 | pass (AAA) |
| `ConversationPane.tsx:240` | `/40` | 8.45:1 | 7.24:1 | pass (AAA) |
| `AiControlCenterPage.tsx:437, :1572` | `/60` | 7.88:1 | 7.24:1 | pass (AAA) |
| `AiControlCenterPage.tsx:546→551` (ground on parent, fg on child) | `/25` | 8.46:1 | 7.24:1 | pass (AAA) |
| `ShipmentConsolePage.tsx:26` | `/40` | 5.27:1 | 4.57:1 | pass |

**One failure, and the brief's estimate of it was optimistic: 1.29:1, not ~2:1.**

Non-paired `-container/` instances — tinted ground, foreground from a *different*
family (`text-primary`, `text-error`, `text-white`, `text-on-surface`) — are
outside this rule and unchanged: `copilotTokens` `review.field.edited` and
`review.action.danger`; `AuthorizedRmaMode:194`; `CandidateOrderMode:270`;
`ItemSelectionMode:524, :773, :786, :795`; `ReturnEvaluationMode:292, :312`;
`ConversationPane:198, :557`; `ShipmentConsolePage:25, :27, :103, :334, :438`;
and six `analyzer-*-container/` uses, a separate dark palette whose foregrounds
are `emerald-*` and never an `on-*-container`.

**The palette inversion is real, and it is a family of one.** The brief asked
specifically about the `error` pair used by `review.gap` two lines above, on the
grounds that inversions are palette-level. Checked: `error-container` (`#ffdad6`)
and `secondary-container` (`#c5e6e1`) are light grounds with dark `on-` roles, so
a tint moves the ground *away* from the foreground and the pairing **improves** —
`review.gap` at `/30` reads 8.68:1 against 7.24:1 solid. Only
`tertiary-container` (`#8b4b32`, a dark brown under a *light* `#ffc9b7` `on-`
role) moves the ground toward the foreground. So the rule is palette-level and
the answer is: one family fails it, and the reason the other two do not is now
asserted rather than assumed (`reviewContrast.test.ts`, "only tertiary degrades
under tint") — if a palette change flips one, somebody finds out before copying a
token on the strength of it.

### Step R4:02 — a dedicated pair at ≥7:1, not the 4.54:1 line

Dropping the `/40` gives 4.54:1 — passing a 4.5 threshold by 0.04, on the notice
telling an associate *someone else is editing the review they are about to
approve*. Not shipped.

`review.conflict` keeps its `/40` tertiary tint and takes a **tested
foreground**: `text-on-surface`, measuring **9.08:1**.

Not an invention. `support.attentionNotice` two groups down in the same file
already solved the structurally identical problem the same way and documents the
diagnosis at length. Adopting that resolution leaves the file carrying **one
rule** — "the `on-` role is the right foreground for the *solid* container only"
— rather than two ad-hoc fixes, and keeps `review.conflict` in the `tertiary`
family, whose documented meaning ("this is in somebody else's hands") is exactly
what an edit conflict is. All six call sites (`TemplateReviewSection` ×4,
`SupportReplyBody`, `ClarificationsSection`) consume the token wholesale and none
overrides the foreground, so the fix reaches every one.

### Step R4:03 — does the a11y sweep reach these components? NO, three times over

The brief asked to run axe on the affected components and name the second finding
hiding inside. There are three, and they compound:

1. **The only axe in the repository is in Playwright** —
   `frontend/tests/canonical-routes.spec.ts`. **No CI job runs it.**
   `.github/workflows/` holds `checks.yml` and `secret-scan.yml`; neither
   mentions `playwright` or `test:e2e`. `npm test` is `vitest run`, whose
   `include` is `src/**/*.{test,spec}.{ts,tsx}` — which does not match
   `tests/*.spec.ts`. The `*.a11y.test.tsx` files are testing-library, not axe.
   **The contrast check runs nowhere automatically.** Rule 13, verbatim.
2. **Even run by hand it cannot see this.** It sweeps `CANONICAL_ROUTES` — route
   paths in their default loaded state. `review.conflict` renders only when a
   case panel carries `conflict_present: true`. No navigation produces that
   state, so axe never has the element in the page. *A detector must reach as far
   as the thing it protects*; that one reaches a route, and this token lives
   several states inside one.
3. **And wiring axe into the vitest suite would not fix it either — it would go
   green.** Probed rather than assumed: `axe.run` under jsdom against
   `color:#ffffff` on `background-color:#ffffff` — an unmissable 1:1 — returns
   **`violations: 0`, `incomplete: 1`**. jsdom has no layout or canvas, so axe
   cannot resolve computed colours and declines to rule. A suite asserting on
   `violations` would pass. This is the "green because the inputs can't exercise
   the property" shape, and it is why measuring off the token string against the
   real palette is the only mechanism that works here.

**What was actually reaching these tokens** was `supportContrast.test.ts`, which
measures `COPILOT_TOKENS.support` **only**, by an explicit and correct scoping
decision in its own header: *"Widening it to the whole object would make this
V2's test of V1's tokens."* Right for V2, and precisely why `review.*` was never
measured. **That scope boundary between slices is the hole `review.conflict`
walked through.**

Fixed by `frontend/src/domains/returns/reviewContrast.test.ts` — `review`'s own
measurement under `review`'s own ownership, in `src/`, so the **`frontend-tests`
CI job runs it on every PR.** That is the gate rule 13 requires me to name.

### Step R4:04 — the `-container/` grep, and two false positives it took to build

The grep is `containerTintUsages()`: every `bg-<family>-container/<tint>` paired
with `text-on-<family>-container`, across all of `src/`, pinned as a **full
sorted inventory** so a new instance fails the list before it can ship unmeasured
— the mechanism `review.conflict` did not have — and then measured against 4.5:1.

**Both false positives were the instrument reading prose about the bug as the
bug**, and both were caught by injection discipline rather than by review:

1. *Scanning raw lines* reported `copilotTokens.ts:98` failing at **1.29:1**. Line
   98 is a **comment** — the one written in R4:02 explaining the defect, quoting
   the broken pairing verbatim. A red that was real, precise, correctly computed,
   and about documentation.
2. *Scanning quoted strings instead* reported the same line again. JSDoc writes
   code spans in **backticks**, and a backtick span is indistinguishable from a
   template literal to a regex. Two different fixes, one surviving false
   positive, because prose about a bug looks exactly like the bug.

Resolved by stripping comments first (newlines preserved so line numbers stay
true), then scanning literals. Limit stated in the file rather than assumed: it
pairs ground and foreground within **one literal**, so it does not follow a
ground on a parent element to a foreground on a child —
`AiControlCenterPage.tsx:546→551` is that shape and is measured by hand above at
8.46:1.

### Step R4:05 — fault injection, and a first attempt that proved too much

**Attempt 1 was invalid and is recorded as such.** A `sed` on the token's text
matched **two** tokens, not one: `review.conflict` and `support.attentionNotice`
are now byte-identical from `bg-tertiary-container/40` onward — which is itself
confirmation that the two really do share one resolution, but it meant the red
named `copilotTokens.ts:134` *and* `:292`. Five tests failed, and it would have
read as evidence for a claim about one token. **The exact shape merge.md names as
the newest: an injection red for the wrong reason.** The tell was the second line
number in the failure list, which cannot appear if only `review.conflict` was
touched.

**Attempt 2, scoped to line 134 alone** (`sed -i '134s/…/…/'`, verified by
printing both 134 and 292 before running):

| assertion | what it reported |
|---|---|
| `clears 4.5:1 on every one of them` | `conflict: 1.29:1` |
| `holds the conflict notice well clear of the line` | `1.2888… >= 7` failed |
| `finds the tinted-container usages` | one **added** entry, `copilotTokens.ts:134` |
| `clears 4.5:1 at every one of them` (source grep) | `copilotTokens.ts:134: 1.29:1` |
| `never tints tertiary-container under its own on- role` | `review.conflict: …text-on-tertiary-container` |

**Five independent assertions, every one naming line 134 and only line 134.**
`support.attentionNotice` at 292 appears in none of them — the difference from
attempt 1, and the tell that this injection did what it claims. Reverted; the
suite returns to 9/9.

The tests are also proof against passing vacuously: `computes real ratios` pins
two known answers (21:1, 1:1) plus the failing pairing itself, so a `measured()`
returning a constant fails; both inventories are pinned as **lists rather than
counts**; and `measurableTokens()` is **one function** shared by the measurement
and by the guard that proves the measurement is non-empty — the fault
`supportContrast.test.ts` records getting past an earlier version of itself.
