## 2. Findings the orchestrator should see

### 2.1 The resolver had no production invocation site (the reason for phase 2)

`grep` over `src/` for `LadderDependencies|build_resolution_ladder|gate_reply|
SupportResolverState` returned hits only inside V3's own modules. The ladder

### 2.2 The clarification command payload could not have become its signal

`DurableCaseCommandStore` copies the endpoint's payload verbatim into the outbox
row and `CaseCommandSignalDispatcher` hands it to `handle.signal(...)` unchanged
— so the payload **is** `ClarificationAnsweredNotice`. It was
`{clarification_id, case_id, answer_text, resolution_choice, return_record_id,
answered_by}` against a notice requiring `{clarification_id, actor, signal_id,
…}`: **no `signal_id` at all**, plus three keys the notice does not have. The
round-trip would have dead-lettered on the first real answer and every test
passed. Fixed in step:14, with two tests pinning the two shapes together.

### 2.3 `case_has_return_details` is registered on no worker — **not V3's defect**

`workflows/return_case_activities.py:671` defines it,
`workflows/return_case_workflow.py:2214` calls it, and `workflows/worker.py`
never registered it. An unregistered activity raises nothing and logs nothing:
the execution schedules the task and waits, with no symptom but a case that
stopped. Reachable whenever `timings.return_details_required` is on.

Found by `test_every_activity_the_workflow_calls_is_registered_on_the_worker`,
written for V3's two activities and derived from both sources rather than from a
list. **Registered** in the same commit, because the alternative was shipping a
test that documented a live stall. Flagged here because it is pre-existing and
predates this run's slices; someone should confirm no in-flight case is sitting
on it.

## 3. Contract questions (no clause was adapted; nothing was widened)

### 3.1 §7's outbox-topic enumeration — **not widened, and the design avoids it**

The natural home for a resolver trigger is its own topic. §7 enumerates four new
topics, and AMENDMENT-1 established that widening a frozen enumeration takes an
orchestrator amendment, not an implementation. So the trigger runs as a
**continuation of the existing `return-case.support-message.classify`
command**, through a dispatcher that delegates to V2's.

That is not only avoidance: it is where the committed classification exists, and
its at-least-once envelope is the retry this work wants (analysis reuses its
accepted stages; the ladder resumes from its checkpoint). **No amendment is
requested.** If the orchestrator would prefer a dedicated topic, that is an
amendment plus a small change here — the trigger itself is already separate from
the dispatcher.

### 3.2 §10's activity enumeration — honoured as two, not collapsed to one

The deadline reset would have been simpler as one activity. §10 names two, so
there are two, and the reset rides `record_clarification_answer`'s result.

### 3.3 §9's ladder, with rungs the deployment cannot serve

The contract's ladder is *case facts → graph → registered tools → clarification*.
This build compiles **only the fact rung**, because three of the ports have no
implementation that can be written without inventing a trust boundary, a
credential path or a read contract (ledger step:13 has the table). The descent
still descends; it has fewer rungs, `rungs_attempted` says so, and escalation
reports `SUB_THRESHOLD` accurately.

Read as: **§9 is implemented and partly unreachable in this deployment, by
released configuration and absent adapters, both visible.** If the orchestrator
considers a graph rung required for the acceptance gate, the owed work is a
`GraphReadPort` read contract and a `GraphSyncPort` plan — both of which need a
decision this slice is not entitled to make, and neither of which the
`integration-outbox` process currently has a graph stack for.

### 3.4 A new patch marker

`_PATCH_V3_CLARIFICATION_ROUND_TRIP = "v3-clarification-round-trip"`, guarding
the handler's two activity calls. Same instrument and reasoning as
`_PATCH_SUPPORT_TEMPLATE_REVIEW_GATE`. Recorded here because a patch marker is a
permanent history commitment.

## 4. Where the deployment stands after 1a

- An inbound support message classified `info_request` **with prose** reaches the
  ladder. Everything else is analysed exactly as today.
- The ladder tries the fact rung. Cleared → `gate_reply`, which opens a
  `SUPPORT_REPLY` review (released default `review_required`). Not cleared →
  `support_clarification_requested`, on the case and in the panel.
- The graph and tool rungs are absent. `tool_bindings: []` and `compiled_rungs`
  both say so, and `support_resolver_rungs` is logged at construction.
- An associate answering a clarification signals the workflow, which writes the
  fact, relays to Support down the shared receiver-deduped path, and pushes the
  review deadline when the release says to.
