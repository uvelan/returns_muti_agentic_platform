### The fix

- **New `operations/support_template_draft.py`** â€” the seam, and the vocabulary's
  one home. It declares `SNAPSHOT_KEYS` (names the draft derives, no `factId`),
  `FACT_LOG_KEYS` (names an activity already writes), their union, and the
  conditional wording as named constants. `support_template_snapshot(...)` takes
  **`compose_support_handoff`'s own argument list** â€” deliberately, so a caller
  that can compose one can produce the other without deciding anything new, and
  so the equivalence matrix can drive both paths from one set of inputs.
- **The conditionals resolve to presence, not to a fallback.** The Â§8 clause
  grammar describes the shape of a *case*, never the presence of a value, so no
  `visibility_rule` can express "only when the bay was not recommended". Those
  lines are bound with **no `fallback`**: the producer omits the key and the
  renderer omits the line, exactly as the composed path omits it. A fallback
  there is what printed "Not available" where the truth was "no bay could be
  recommended, resolve manually".
- **The contact block is two mutually exclusive arms**, six fields, three ever
  present. Labels stay in configuration (the alternative â€” one pre-rendered
  block â€” would have taken the wording out of the operator's hands); it is the
  *arm* that is chosen in code, because the arm is the conditional.
- **`return_details.additional`** renders through one key holding already-
  labelled lines, because the labels are the release's and no template can know
  them. That preserves `support_handoff.py:157-160`'s property: a release that
  adds a required detail needs neither module edited.
- **`production.yaml`**: the customer, return-details, bay, verification and
  requested-action sections gain their conditional fields; `associate_notes`
  rebinds to `associate_notes_rendered`; the block comment now states what is
  claimed and what is not.
- **F2, the second copy:** `api/template_preview.py` held a hand-written second
  copy of the whole 24-key vocabulary. Deleted. The sample is `SAMPLE_CASE` in
  the seam module, expressed as compose arguments, and its facts come from
  `draft_facts` â€” so the route's "the same text as `compose_support_handoff`"
  claim is now `test_the_preview_is_the_composed_text`, which posts the
  **shipped** default variant and compares.

### The payload, and why the body is recomposed

string would show the reviewer their change on the panel and send Support the
original. `test_an_edited_field_changes_the_body` asserts exactly that gap.

`payload_text` is a second implementation of the renderer's private `_text_of`,

### Where it sits, and what an un-patched history does

Between `draft_support_request` and `open_support_work_item`, under
`workflow.patched("support-template-review-gate")` — the anchor exactly.
`test_a_legacy_history_opens_support_instead_of_wedging` already drove that
method with `patched → False`; it now also asserts **which** markers were
consulted:

```python
assert runtime.patch_ids == [
    _PATCH_STRUCTURED_SUPPORT_DRAFT,
    _PATCH_SUPPORT_TEMPLATE_REVIEW_GATE,
]
```

That pairing is the guarantee. The activity-sequence assertion alone would
pass against a gate that never called `patched` at all — and that gate would
wedge the first replay that *did* record the marker. Its `patched` assertion
was `== _PATCH_STRUCTURED_SUPPORT_DRAFT`, which would have failed on the second
marker for the wrong reason; it is now a membership check plus the ordered
list, so the real property survives and drift is still caught.

`ACTIVITY_RESULT_TYPES` gained the three new calls with the reasoning written
in: the return-details poll next to them rests on `timings` being pinned at
start, and its own comment names the window where that is not enough. The gate
has exactly that window and it is wide (`enabled` defaults to true), so the pin
would not have been safe and the marker is what makes it so.

### One design change I made mid-step, and why

I first had the workflow derive the request ids and loop `record_template_draft`
per request. That put `one_per_case` in the workflow and quietly collapsed the
other two groupings — which would have made "a held record must not block an
approved one" **unfalsifiable**, because the gate could only ever produce one
request. The DoD asks for that test by name, so the design was wrong, not the
test.

`record_template_draft` now resolves the grouping activity-side (it reads
return records, which a workflow may not) and returns a `TemplateReviewDraftSet`
— the whole map in one result. Two consequences worth stating: the ids the wait
is keyed on are **in the history**, not re-derived from a release that may have
moved; and replay safety comes from `create_review`'s documented idempotency on
`(case_id, request_id, kind, scope)` rather than from a replay-stable uuid.

### The wait loop

Cloned from `_await_policy_override` — resumed deadline, `resolve_business_deadline`
legs, reminder cap, `continue_as_new` on the history hint — and a clone by
ruling 12, not by accident; the extraction stays registered.

Two deliberate differences from the source, both recorded:

1. `_await_policy_override` waits for *one* answer and returns on the first
   wake. This drains a notice list and continues, because a case with two
   requests must be able to send the approved one while the other is still
   being read.
2. At the reminder cap the policy loop **returns**; this one keeps waiting to
   the deadline. Stopping at the cap is the reminder count deciding the
   deadline, and a draft is still perfectly answerable after the last reminder.
   The single exit stays in the `remaining <= 0` branch.

**No reminder is sent on Channel B, and that is the gate.** `send_support_reminder`
posts on the case's Support thread and during this wait there is no such thread
— refusing to open one until a person has read the draft is the entire feature,
so nudging Support that our reviewer has not looked yet would be the gate
opening the conversation the gate is holding back. `_await_policy_override`
states the same rule for the same reason. The cadence is durable where it is
actually read: the count rides `continue_as_new` and reaches the panel through
`execution_state`, and the deadline is an absolute instant the browser counts
down from (§9).

### Deadline policy, and the one contract reading I had to make

`hold` and `escalate` park the case and leave every review `OPEN`: a deadline
passing does not make a draft un-reviewable, and a reviewer arriving late can
still answer. `auto_send` approves as `SYSTEM` through the *same* transition
with the same refusals.

**The gap rule is enforced twice**, in the workflow and again in the activity,
and the duplication is deliberate: it is the one rule in the gate whose failure
mode is a message asserting something the case does not know, to a human who
then acts on it. The workflow's copy is a decision; the activity's is a refusal.

*Reading recorded for RV:* `HELD_FOR_OPERATIONS` is reachable only from
`APPROVING` in S2's frozen table, so a guard-blocked review that never left
`OPEN` cannot enter it. The guard block is therefore recorded as the **case**
park reason `TEMPLATE_REVIEW_GUARD_BLOCKED` (a §6 park reason) with the review
left `OPEN` and answerable. The alternative — approving a gapped draft purely
to make the hold transition available — would freeze a payload the case cannot
support in order to satisfy a state diagram.

### Resume

A `continue_as_new` inside the gate happens with `work_item_id is None`, which
the run loop reads as "not assessed yet" and which would have sent the case
back through the customer read, the bay request and the policy evaluator — and
then re-opened a review the associate was already reading.
`_resumed_into_the_review_gate` closes it, and **both** halves are load-bearing:
the status alone is true of a case whose reviews all settled before the reset,
the map alone is true after the gate finished. Tested as a truth table.

**One robustness fix found by a failing test.** `snapshot_sent_template` raised
`ReviewStateError` when the review was not `APPROVING` — a signal for a review
somebody cancelled or redrafted in between would have failed the workflow task
and retried forever against a state that never changes on its own, with the
case sitting in `AWAITING_TEMPLATE_REVIEW` and nothing on the panel to say why.
It now reports the state, which is what lets the wait loop stop waiting.

### Deviations

1. **`return_case_recovery.py`, `api/cases.py`, `workers/integration_outbox.py`,
   `runtime_factory.py` each take one new argument.** A relaunched case
   re-enters the gate, so its input needs the same block a freshly-confirmed one
   gets; without it a deployment that turned the gate off would have it back on
   for exactly the cases already having a bad day. No signature changed
   incompatibly — every addition is defaulted.
2. **`case_timings_from_configuration(..., gate=None)` is not "no gate".** It
   falls back to `SupportGateConfiguration()`, whose defaults are DR-4's, so a
   caller that forgets gets the review rather than silently sending unreviewed
   messages. Pinned by `test_omitting_the_block_gives_the_reviewed_default_not_no_gate`.
3. **`tests/policy/test_case_policy_gate.py` gained a `record_template_draft`
   double** answering `template_available=False`. Truthful rather than
   convenient: those fixtures build a configuration with no `support_template`
   variants, so that *is* the answer for them, and the branch they were all
   written against is unchanged. What it does not cover is covered here.
4. **`ReturnCaseTimings`' gate fields are flat and defaulted**, not a nested
   model — the type is in the workflow history, and a required field or a
   nested type would fail the decode of an input recorded before the gate.
