### The fix

- **New `operations/support_template_draft.py`** â€” the seam, and the vocabulary's
  one home. It declares `SNAPSHOT_KEYS` (names the draft derives, no `factId`),
  `FACT_LOG_KEYS` (names an activity already writes), their union, and the
  conditional wording as named constants. `support_template_snapshot(...)` takes
  **`compose_support_handoff`'s own argument list** â€” deliberately, so a caller
  that can compose one can produce the other without deciding anything new, and
  so the equivalence matrix can drive both paths from one set of inputs.
- **The conditionals resolve to presence, not to a fallback.** The Â§8 clause
  grammar describes the shape of a *case*, never the presence of a value, so no
  `visibility_rule` can express "only when the bay was not recommended". Those
  lines are bound with **no `fallback`**: the producer omits the key and the
  renderer omits the line, exactly as the composed path omits it. A fallback
  there is what printed "Not available" where the truth was "no bay could be
  recommended, resolve manually".
- **The contact block is two mutually exclusive arms**, six fields, three ever
  present. Labels stay in configuration (the alternative â€” one pre-rendered
  block â€” would have taken the wording out of the operator's hands); it is the
  *arm* that is chosen in code, because the arm is the conditional.
- **`return_details.additional`** renders through one key holding already-
  labelled lines, because the labels are the release's and no template can know
  them. That preserves `support_handoff.py:157-160`'s property: a release that
  adds a required detail needs neither module edited.
- **`production.yaml`**: the customer, return-details, bay, verification and
  requested-action sections gain their conditional fields; `associate_notes`
  rebinds to `associate_notes_rendered`; the block comment now states what is
  claimed and what is not.
- **F2, the second copy:** `api/template_preview.py` held a hand-written second
  copy of the whole 24-key vocabulary. Deleted. The sample is `SAMPLE_CASE` in
  the seam module, expressed as compose arguments, and its facts come from
  `draft_facts` â€” so the route's "the same text as `compose_support_handoff`"
  claim is now `test_the_preview_is_the_composed_text`, which posts the
  **shipped** default variant and compares.

### A1 â€” a multi-record subject silently took the last record's value

the state a multi-RMA integrity defect is in right before it is not.

Fixed at both ends, and the two answer different questions:

- **Release validation** now refuses a `subject_template` naming a field that
  lives in a per-record section, with the reason in the message: a request
  covering several records has one subject and would have to pick a record. An
  operator finds out when they publish, not when a customer gets the wrong RMA
  number in a subject line.
- **The renderer** builds the map from case-level sections only. Validation
  already makes this unreachable; it is here so the render cannot resolve one
  arbitrarily if anything ever gets past that gate, and so the question "which
  record does the subject name" has a readable answer in the code: none.

Tested from both sides â€” the release is refused, and a render built past the
refusal states no record's reference rather than the second one's.

### A2 â€” the publish confirmation probably never rendered in production

`key={active.releaseId}` on the editor, and `onSubmit` awaits

operator is not left with nothing â€” but the confirmation, and the "cases already

The confirmation now lives in the **section**, above the editor, where the

## step:11 — carry-forward condition 3: the command horizon is armed

- Files: `workflows/return_case_recovery.py` (the factory only — one port
  argument and the paragraph explaining it),
  `tests/test_case_recovery_command_horizon_is_armed.py` (new, 4).

**What was actually wrong, and it is not what the condition's wording suggests.**
The rule was not half-built; it was complete and untested *at the only place
that matters*. Every one of S2's nine horizon tests constructs
`ReturnCaseRecoveryService(...)` directly and passes `command_horizon=` by
hand. Production has exactly two constructors — `api/cases.py:707` and
`workers/integration_outbox.py:199` — and both go through
`build_case_recovery_service`, which passed `outbox=` and nothing else. So
`_stale_commands` answered `()` for every case in the estate, and a case whose
approval command had committed and never reached the workflow was relaunched
instead of surfaced.

**The fix is one argument, and it is deliberately the *same object*.**
`MongoReconciliationOutbox` already implements both ports over one collection —
`list_commands_requiring_reconciliation` for the dead letters,
`list_unapplied_commands_past_horizon` for the ones still politely retrying —
so the factory now builds one and passes it as both. Two instances would be two
readers of one queue, and a horizon pointed at a different database than the
dead-letter sweep is invisible until an incident.

**Ownership note.** `return_case_recovery.py` is S2's file and I did not touch
its schemas, signatures, transitions or ports. The edit is inside the factory,
which is the one place the ports are *chosen*, and its own docstring forbids
the alternative — "a route that built its own launcher would be a second place
the duplicate-execution rule lives". A `command_horizon=` argument added to
`build_case_recovery_service` and threaded from both call sites would have been
the same change with two more places to get it wrong.

### Fault injection (before/after)

The new tests drive the **shipped factory** with a real
`MongoReconciliationOutbox` over a real `integration_outbox` collection and read
the decision off the outcome — no private-attribute-only assertion, which would
still pass with the port wired to something that never answers.

Deleting `command_horizon=reconciliation` from the factory:

```

E  assert <RecoveryAction.RELAUNCHED> is <RecoveryAction.OPERATIONS_REQUIRED>
FAILED test_the_horizon_reads_the_same_queue_the_outbox_does
E  assert None is <MongoReconciliationOutbox object …>
```

and — **this is the finding, not the fix** — all 16 tests in S2's
`test_case_recovery_review_waits.py` stay green through that injection. The
rule's entire existing test surface is blind to whether production arms it.
Restored: 4 passed, and the S2 file's 16 still pass.

Three tests exist so the first is not vacuous in the other direction:
`…still_relaunches` (empty outbox, same factory → `RELAUNCHED`, the launcher is
reached) proves a horizon that answered "stale" unconditionally would be
caught; `…no_database_still_builds_and_still_degrades` pins that `database=None`
takes both ports to `None` together and produces `RELAUNCHED` rather than a
fabricated `OPERATIONS_REQUIRED` — S2's honest degradation, preserved. The
stale-command fixture is `status: "RETRY"`, not `DEAD_LETTER`, on purpose: that
is the population the horizon exists for and the dead-letter sweep never sees,
so a fixture using `DEAD_LETTER` would pass against a horizon mis-wired to
`list_commands_requiring_reconciliation`.

**Advisory raised, not fixed (S2-owned).** `_stale_commands` asks the port for
`limit=self._batch_size` (100) commands *platform-wide* and then filters to this
case. On an estate with more than 100 unapplied-past-horizon commands, this
case's stale command can fall outside the page and the rule silently answers
"clear". The query has no `case_id` term to narrow it, so closing this needs a
port signature change — S2's, via the orchestrator (contracts §10).
