## Why nothing was built anyway

Every part of item 6 is defined *relative to a contract that does not exist here*:

- a panel section has no registry to register with, and inventing a registration
  shape would create a second one for V1 phase 2 to collide with;
- reply-review entries must render through V1's `review_kind`-aware review
  components — there are none;
- MSW handlers mock endpoints that have no OpenAPI shape yet, so they would be
  mocking a contract I made up.

Contracts.md §9 is explicit about the ownership: *"Section-registry seam: V1
ships the contract + registry and never touches it again; V2/V3 contribute
sections in their own files."* Contributing a section before the registry exists
is not contributing to a seam; it is authoring one.

## What is ready for it

The backend item 6 consumes is complete and tested:

- `support_clarification_requested` (V2) carries `verbatim_question`,
  `why_unresolvable`, `resolution_attempts[]`, `needed_field`, candidates and the
  map-or-reject choice;
- `compose_clarification_prompt` (V3 step:04) renders the associate-facing text —
  neutralised, bounded, plain text with no markup;
- `POST /api/v1/cases/{case_id}/clarifications/{clarification_id}/answer` (V3
  step:07) is the form's target, with `map`/`reject` and the "a `map` must name a
  record" refusal already enforced server-side;
- `SUPPORT_REPLY` reviews are opened on S2's aggregate with a server-minted
  `scope_id` (V3 step:06), so a `review_kind`-aware component has something to
  render.

**Recommendation:** dispatch item 6 as a separate phase once V1 phase 2's panel
contract and registry have merged, as the dispatch itself proposed. The frontend
outcome gates (token reuse, accessibility keyboard path, UX copy including
"support is asking you this", handoff spec, code review) travel with it.

# Delta report addendum — named risk for whoever populates `outbound_templates`

## Advisory A1: `render_configured_template` can assemble a framing line across an interpolation boundary

Recorded at RV's instruction in review V3-2, **not fixed**, because fixing it
naively would break a different frozen guarantee.

**The shape.** `render_configured_template` neutralises every interpolated value
*before* substitution. Each value is checked alone. A template like `"{a}{b}"`
with `a = "SHIPPING INSTRUCTION"` and `b = ":"` interpolates two values, neither
of which is a framing shape by itself, into one line that is. It is the same
class as review V3-1's finding F1 — a framing line built *after* the last
neutralisation of its parts — with the concatenation doing what the truncation
cut did there.

**Why it is not live today.** `support_ingress.outbound_templates` defaults to
`{}` and there is no production caller. Reaching it requires a deployment to
author a template that splits a heading across two adjacent placeholders, and
then an attacker to control both halves.

**Why the one-line fix is wrong.** Neutralising the *rendered* template would eat
AMENDMENT-1's `literal:<text>` source, which exists precisely so a released
template can supply constant section headings — real framing lines that the
default `production.yaml` handoff needs in order to reproduce today's output.
A neutraliser applied after rendering cannot distinguish a heading the template
*is* from a heading an interpolated value *forged*.

**What it actually needs.** A design decision about how a template declares its
own structure separately from its interpolated content — for example,
neutralising each rendered **segment boundary** rather than each value or the
whole line, or forbidding two placeholders from being adjacent without
intervening literal text. That decision belongs to whoever first populates
`outbound_templates`, and it should be made then rather than guessed now.

**Where to look:** `operations/return_support/outbound_composition.py`,
`render_configured_template`. The neighbouring
`TestTruncationCannotManufactureFraming` shows the assertion style this needs —
state the property over the **composed output**, not over the function's inputs.
