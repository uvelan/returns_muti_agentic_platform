# V3 — frontend handoff spec: **not written, blocked at the seam**

The brief asks for a frontend handoff spec here (item 6: the clarifications panel
section, the map-or-reject UI, reply-review entries rendering through V1's
`review_kind`-aware components, MSW handlers).

**It is not written, and that is a halt rather than an omission.**

Item 6 contributes sections through V1 phase 2's panel **section-registry seam**.
The dispatch anticipated this and instructed: *"When you reach item 6, check; if
the seam is absent, stop and report rather than inventing a panel contract."*

## Why nothing was built anyway

Every part of item 6 is defined *relative to a contract that does not exist here*:

- a panel section has no registry to register with, and inventing a registration
  shape would create a second one for V1 phase 2 to collide with;
- reply-review entries must render through V1's `review_kind`-aware review
  components — there are none;
- MSW handlers mock endpoints that have no OpenAPI shape yet, so they would be
  mocking a contract I made up.

Contracts.md §9 is explicit about the ownership: *"Section-registry seam: V1
ships the contract + registry and never touches it again; V2/V3 contribute
sections in their own files."* Contributing a section before the registry exists
is not contributing to a seam; it is authoring one.

## What is ready for it

The backend item 6 consumes is complete and tested:

- `support_clarification_requested` (V2) carries `verbatim_question`,
  `why_unresolvable`, `resolution_attempts[]`, `needed_field`, candidates and the
  map-or-reject choice;
- `compose_clarification_prompt` (V3 step:04) renders the associate-facing text —
  neutralised, bounded, plain text with no markup;
- `POST /api/v1/cases/{case_id}/clarifications/{clarification_id}/answer` (V3
  step:07) is the form's target, with `map`/`reject` and the "a `map` must name a
  record" refusal already enforced server-side;
- `SUPPORT_REPLY` reviews are opened on S2's aggregate with a server-minted
  `scope_id` (V3 step:06), so a `review_kind`-aware component has something to
  render.

**Recommendation:** dispatch item 6 as a separate phase once V1 phase 2's panel
contract and registry have merged, as the dispatch itself proposed. The frontend
outcome gates (token reuse, accessibility keyboard path, UX copy including
"support is asking you this", handoff spec, code review) travel with it.
