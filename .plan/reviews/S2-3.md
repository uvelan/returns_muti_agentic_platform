## The `except Exception` caveat — answered, and the answer is better than the question

I raised one failure mode; the slice split it into two and gave them opposite handling. I
tested the split rather than the wording, and the split is right.

**Each guard is independently load-bearing.** Removing both → **2 failed**, as claimed.
Removing them one at a time → **1 failed each**, and the failing test is the one written
for that guard:

| Removed | Failing test |
| --- | --- |
| Construction check only | `test_a_repository_without_the_link_repair_is_refused_at_construction` (`:282`) |
| `except AttributeError: raise` only | `test_a_programming_error_in_the_link_repair_is_not_swallowed` (`:342`) |
| Both | both of the above |

Neither is decorative, and the operational half is separately pinned by

keeps one case's link from blocking the cases behind it is now a tested property rather
than a comment.

### Does the construction-time refusal close the invisible-degradation path?

**For the mode I raised — a port that omits `bind_case_workflow` — yes, completely.** All
twelve construction sites at `af7052b` go through `__init__`, including the single
production site (`scripts/run_return_workflow_worker.py:218`). I checked specifically for
`__init__` bypass: the repo does have an established `object.__new__` test idiom (17
sites), but **none of them targets `ReturnCaseWorkflowRecovery`**, and production has
exactly one construction site, so the check is effective where it matters. Removing the
mode rather than detecting it is the stronger answer and I withdraw the caveat.

**For a partially-implemented port — no, and you were right to ask.** I built one: a class
whose `bind_case_workflow` exists and is callable but raises `NotImplementedError`.
Measured:

```
construction: ACCEPTED (callable attribute present)
recover_once: returned normally -> swallowed
workflowId after pass: None
=> still in the queue: 1
```

`callable(getattr(...))` verifies presence, not that the method works, so a stub falls
into the broad catch and the sweep degrades to a per-case warning — the same shape as the
mode the check removes. This is **advisory A1 below, not a finding**: the shipped
behaviour is not wrong (nothing is corrupted; the case stays in the queue and a warning is
emitted every pass), the mode actually raised is genuinely closed, and the fix is one
line — the slice's own reasoning for excluding `AttributeError` applies to
`NotImplementedError` verbatim, since it too is neither per-case nor transient.

### Could excluding `AttributeError` turn a legitimate transient into a crash?

**No crash. Verified.** I gave the sweep a repository whose `bind_case_workflow` raises
`AttributeError` from inside its own body (`None.update_one(...)`) — i.e. an
`AttributeError` that is *not* "method missing", which is what the bare `except
AttributeError: raise` will also catch:

```
recover_once: PROPAGATES AttributeError -> 'NoneType' object has no attribute 'update_one'
run_forever still alive after the raise: True
```

`run_forever` catches it, logs `case_workflow_recovery_pass_failed` at **ERROR**, and
continues on the next interval. So the blast radius is bounded at one aborted pass, and
the next pass retries — while the failure is logged at ERROR (visible) rather than WARNING
(the invisible mode). The one honest cost is that cases behind the failing one are skipped
on that pass, which is the very blocking the swallow exists to prevent — but only for an
`AttributeError`, which the constructor guarantees is not "method missing" and is
therefore a bug in an implementation. Aborting loudly on a bug and retrying on the next
pass is the right trade, and it is strictly better than the mode it replaces. Sound as
shipped.

## Advisories

- **A1 — a stubbed port method still degrades silently.** Proven above: a
  `bind_case_workflow` that exists, is callable, and raises `NotImplementedError` passes
  the construction check and is swallowed into a per-case warning. One line closes it —
  add `NotImplementedError` beside `AttributeError` in the not-caught clause
  (`return_case_recovery.py:334`), since the slice's own argument for excluding
  `AttributeError` ("neither per-case nor transient; it fails identically for every case on
  every pass") describes `NotImplementedError` word for word. Relevant because V1/V2 will
  be the first outside implementers of this port, and a stub is a normal intermediate state
  while building one. **Does not block.**
- **A2 — the `AttributeError` exclusion is broader than "method missing".** It catches any
  `AttributeError` from anywhere inside the call, so a bug in a real implementation's
  internals now aborts the pass instead of being retried per case. With the constructor
  guarantee in place this is the correct trade and the blast radius is bounded by
  `run_forever` (measured above), but it is worth knowing that the exclusion is a class of
  exception, not a specific condition.
- Round 1's advisories **A1 (wire `command_horizon=` in V1)**, **A2 (V1 must derive the
  workflow id from the case id, never from `cases.workflowId`)** and **A4 (acceptance 18
  rests on V2 populating `required_predecessor_ids`)** carry forward unchanged.
