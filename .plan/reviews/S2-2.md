### F3 (torn marker pair) — **WITHDRAWN**

Fix: both pairs wrapped in `with_transaction` with the session threaded through
`_bump_conflict_marker`; `_CanonicalEditLockLost` raised inside the transaction on a lost
version CAS.

Three injections at `c884e8e`:

| Injection | Result |
| --- | --- |
| Clear-marker moved back outside the transaction (`resolve_canonical_edit`) | **1 failed** — `test_the_marker_and_the_canonical_edit_are_cleared_as_one` |
| Set-pair unwrapped into two independent writes (`_after_edit_written`) | **2 failed** — `…are_raised_as_one`, `…still_leaves_the_conflict_discoverable` |
| `raise _CanonicalEditLockLost()` deleted (marker would clear for an edit never written) | **42 passed — not caught.** See advisory A1. |

The transaction itself is pinned in both directions. The `_CanonicalEditLockLost` half is
correct but unguarded; that is coverage, not a defect, and is recorded as an advisory
consistent with how round 1 treated the same species (its A3).

**Scope judgement — leaving the edit rows outside the transaction: upheld.** I tested the
reasoning rather than the wording. The slice's claim is that `_after_edit_written`
recomputes the actor set from the rows, so an aborted pass self-heals on the next write.
That is *conditionally* true — it needs a next write — so I went looking for what happens
when there isn't one, and found the exposure is much narrower than the bare argument
suggests:

- `_after_edit_written` is called inline after `insert_one` (`review_aggregate.py:477`),
  and only on the insert path — correct, since the actor set changes only when a new
  actor's first row lands. A *failure* therefore propagates to the caller, who sees an
  error and retries; autosave is by nature repeated, so the heal is not hypothetical.
- `submit_edit` (`review_aggregate.py:548-552`) recomputes the actor set **live** from the
  rows and raises `ReviewConflictError` when it is not `{actor_id}`. The sole-actor
  auto-promote path — the one that would silently discard a second actor's edit — is
  guarded by the rows themselves, not by the stored flag.
- Under concurrency with no crash there is no bad interleaving: whichever pass reads after
  both rows exist sees two actors and flags; a duplicate flag is a `$ne: True` no-op and an
  idempotent `$set`.

What remains is a process **death** between the row insert and the flag transaction, with
no subsequent edit, followed by a direct `approve()` — which reads the stored
`conflictPresent` (`:666`). Narrow, and materially narrower than what F3 fixed, which was
unrecoverable by construction and needed no crash-window at all. Wrapping the row in too
would also change `submit_edit`'s failure semantics (an aborted transaction loses the
actor's row rather than their flag), which is not obviously better. **The distinction the
slice drew — only the half that cannot self-heal needed wrapping — holds.** I am recording
the residual precisely in A2 rather than sustaining it, because V1 is about to build
approval endpoints on this and should know the exact shape of the window.

## New finding

### N1 (rule 10, test integrity) — the race test's blind counter is not load-bearing downward, and the comment says it is

- **File:** `backend/tests/operations/test_case_thread_delivery.py`
- **Lines:** 180 (`if blinded["count"] < 1 and "caseId" in str(query):`), against the claim
  at 171–176 (*"the counter is load-bearing in both directions"*).
- **Rule:** 10 — a guard that can pass while exercising nothing, and a comment asserting a
  property the test does not have.

You asked me to verify the load-bearing claim. **Upward it holds; downward it does not.**
Both measured, at `c884e8e`, by editing only the counter:

| Blind count | Result |
| --- | --- |
| 2 | **1 failed** — `DuplicateKeyError` propagates; the loser's re-read is blinded and the code re-raises rather than converging. Claim confirmed. |
| 1 (shipped) | 1 passed |
| **0** | **1 passed** — *green with no blinding at all.* |

With the counter at 0 nothing is blinded, so `_open_case_thread`'s idempotency pre-read
finds the winner's work item and returns `(id, False)` on the ordinary path. The insert is
never attempted, the unique index is never reached, and the `DuplicateKeyError` loser path
— the entire subject of the test — does not execute. Every assertion still holds, because
they are satisfied by the sequential path just as well: the test degrades into a duplicate
of `test_ensuring_the_thread_twice_yields_one_thread` (`:141-152`), which asserts the same
five things.

**Why this matters rather than being a nit.** This test is the *only* guard on F2, a
blocking finding whose failure mode is a duplicate opening message to Support. The counter
is coupled to the number of `caseId` reads on the production path — and it already
changed, this round, from 2 to 1 because a read was removed. That is the exact edit class
that takes it to 0-effective: any future change that removes or reorders a read before the
insert (or moves the idempotency pre-check) leaves the test green while it stops
constructing the race, and F2 becomes unguarded silently. A magic number tied to
production internals, with nothing asserting that the injection fired, is the
loosening mechanism you named, and the docstring's claim that it cannot happen is what
would stop a future reader from checking.

**Fix (one line):** assert the injection actually fired — `assert blinded["count"] == 1`
after the call — so the number verifies itself and any drift is loud instead of silent.
Better still, assert the loser reached the duplicate path. And correct the comment: the
counter is load-bearing upward only.

## Interface stability — claim verified specifically

You flagged this as expensive to get wrong. I checked the round-2 delta for every changed
`def`/`class` line in `backend/src`, and there are seven: five are `_`-prefixed private
methods or nested `transaction` closures, one is `_bump_conflict_marker` gaining an
optional `session: Any = None` (private, and backward compatible regardless), and one is
the Protocol member below. Concretely:

- **`CaseSupportThread`** — the model declaration is untouched in the round-2 delta. The
  only change under it is the value bound to `created` (`created=already is None` →
  `created=created`). Name, type and documented meaning are identical; it is simply now
  correct under concurrency, which is what F2 asked for. No V1/V2 change required.
- **`open_case_thread`** — its `async def` line does not appear in the delta at all. The
  signature and `-> str` return are unchanged; the body delegates to `_open_case_thread`
  and discards the second element.
- **`RecoverableCaseRepositoryPort.bind_case_workflow`** — the one addition, on an
  internal recovery port. Both existing implementers already satisfy it: the real
  `CaseRepository` (`case_repository.py:253`, pre-existing, not added this round) and the
  test double at `test_confirmation_starts_the_case_workflow.py:210`. The only production
  construction site is `scripts/run_return_workflow_worker.py:218`, which passes the real
  repository. Nothing V1 or V2 supplies today implements this port.

**The claim holds.** One caveat worth stating, since the port is structural: because
`_repair_workflow_link` wraps the call in `except Exception` (correctly — it matches the
launcher's own swallow and keeps one case's link from stopping the sweep), a port that
*omitted* `bind_case_workflow` would degrade silently back to round-1's starvation,
visible only as `case_workflow_link_repair_failed` warnings. Not a defect — mypy covers
the two real call sites — but it is why the port addition should be announced to V1/V2
rather than assumed harmless.

## Advisories

- **A1 — the `_CanonicalEditLockLost` abort is correct but unpinned.** Deleting the raise
  leaves the suite fully green (42 passed) while the marker clears for a canonical edit
  that was never written — half of F3, reintroduced silently. The transaction is pinned;
  this mechanism inside it is not. Same species as round 1's A3, which the slice closed
  this round; worth the same treatment. One test.
- **A2 — the precise residual on the edit rows, for V1's benefit.** Two edit rows with
  `conflictPresent` unset is reachable only by process death between `insert_one` and the
  flag transaction, with no subsequent autosave. `submit_edit` recomputes live and refuses,
  so auto-promote is safe; a direct `approve()` reads the stored flag and would proceed. V1
  should not treat `conflictPresent` as the sole authority when it builds the approval
  endpoint if a cheap recompute is available at that point.
- **A3 — announce the `RecoverableCaseRepositoryPort` addition to V1/V2.** Per the caveat
  above: harmless today, silent if ever unimplemented.
- Round 1's advisories **A1 (wire `command_horizon=` in V1)**, **A2 (V1 must derive the
  workflow id from the case id, never from `cases.workflowId`)** and **A4 (acceptance 18
  rests on V2 populating `required_predecessor_ids`)** carry forward unchanged. A2 is
  softened but not retired by F1's fix: the link is now repaired on the next sweep pass
  rather than never, so `cases.workflowId` is eventually-correct rather than
  sometimes-permanently-null — but it is still not authoritative at any given instant.
