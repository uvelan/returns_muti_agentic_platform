### F2 (BLOCKING) — a retry after the gate has closed strands the review in `APPROVING`, which has no operator-reachable exit

This is my answer to the escalated question, and I am raising it as a finding rather than only a ruling request because the harm does not depend on how the ruling goes.

- **Files:** `backend/src/return_platform/api/case_reviews.py:921-961` (`retry_review_delivery`, no liveness guard); `backend/src/return_platform/workflows/return_case_workflow.py:1479-1516` (the handler discards when the gate has closed).
- **Rule violated:** contract §6's state machine — a review that can enter a state it can never legally leave.
- **The chain, verified in code.**
  1. `retry_review_delivery` calls S2's `retry_delivery` unconditionally. That CASes `DELIVERY_FAILED → APPROVING` and records the command in one transaction. **So the arrow is reachable in practice, not only on paper** — the endpoint always succeeds.
  2. If the gate has already closed, `review_delivery_retry` finds the case no longer holding the review and discards the notice with a log. The redelivery never happens.
  3. The review is now `APPROVING`. `_TRANSITIONS[APPROVING] = {SENT, DELIVERY_FAILED, HELD_FOR_OPERATIONS}` — and I confirmed **all three are workflow-driven only**: `mark_sent` and `mark_delivery_failed` are called solely from `support_template_gate.py:747,758`, `hold_for_operations` from the gate, and `grep` over `src/return_platform/api/` finds no caller of any of them.
  4. `abandon` allows only `(DELIVERY_FAILED, HELD_FOR_OPERATIONS)`. So §6's audited escape is refused.

  The review is permanently stuck, the panel shows `APPROVING` forever, and §6's rule that edit/cancel/redraft 409 from `APPROVING` onward means every other surface refuses it too. The operator's recovery action is the thing that creates the trap.
- **Why this is a finding regardless of the ownership ruling.** Whichever way §6/§7 is read, no reading permits a state with no legal exit. A guard is required either way; only its *shape* depends on the ruling.

**My reading of the ownership question, for your ruling.** Delivery belongs to the **workflow**, and the recovery endpoint's job is to record the command and refuse when it cannot be honoured. Three reasons from the contract text rather than from convenience:

1. §7 puts every send on one receiver-deduped path (`post_support_message`, "one `delivery_id` per approved review"), driven from the gate's activities. The operator endpoint has no send path of its own, and giving it one would make a second sender — precisely what §7's single-path design exists to prevent, and the thing that makes "effectively once" true.
2. §6's own wording — "a retry absorbed by receiver dedupe **still reaches `SENT`**" — presumes the party that observes the outcome is the one that transitions to `SENT`, and `SENT` is workflow-driven.
3. Moving delivery to the endpoint would put a synchronous send behind an HTTP request that must also be idempotent under retry, duplicating the durability the command/outbox chain already provides.

**Minimal fix consistent with that reading**, either of:
- have `retry_review_delivery` refuse (409, carrying the transition as every other refusal on this surface does) when the case's execution is no longer holding the review — the panel already composes `execution`, so the liveness answer is at hand; or
- have the gate, when it closes, move any non-terminal review it was holding to `HELD_FOR_OPERATIONS` — which §6 already defines as the operator-decides state and from which `ABANDONED` is legal. This is the better of the two: it leaves the operator a legal action instead of only a refusal.

A one-line §6 clarification naming the owner of redelivery would settle it permanently.

## Advisories — not findings

- **A1.** `retry_review_delivery` mints `signal_id = str(uuid.uuid4())` while every other decision endpoint uses a deterministic `signal_id` (`f"{kind}:{review_id}"`). A client that retries the recovery POST after losing the response therefore records a *second* command rather than recognising its own. The delivery identity is still reused so no second message can reach B, and the review is already `APPROVING` so the second signal is a no-op — the blast radius is a duplicate command row. Worth aligning with the pattern the rest of the surface uses.
- **A2.** The two `_Facts` doubles should become one. F1 is the concrete cost today; the general point is that a second double in a second file is how the first one's discipline gets lost.
- **A3.** For the phase-2 rendering carry-forward already recorded: `TemplateReviewSection.tsx` is clean today (no `dangerouslySetInnerHTML`, no markdown renderer), and its docstring says so — worth keeping that as a guard test rather than a comment when V2's panel sections land beside it.
