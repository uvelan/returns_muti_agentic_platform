### F2 — WITHDRAWN. AMENDMENT-5 is implemented as written, and the trap is closed.

That is the right shape for a guarantee of the form "no state without a legal exit" — assert the trap is gone, then walk out through each door.

**Rule 1** is asked before the CAS and of the *execution* rather than the aggregate, reusing `execution_state`'s existing `template_reviews` pairs (no new query, no new field). Making the guard always pass turns 2 tests red. The reasoning for placing it before the CAS is right: `retry_delivery` moves the state and records the command in one transaction, so a guard after it would be a refusal reporting a change it had already made.

**Rule 2** parks every non-terminal review, and the derivation is what makes it durable: the skip set is `TERMINAL_REVIEW_STATES | {HELD_FOR_OPERATIONS}` read from the enum, not a written-out list — so a state added to the enum later is parked automatically rather than escaping by omission. Deleting the call turns 5 tests red. Extending it beyond `APPROVING` to `OPEN` is the judgement I most want to endorse: the slice saw that an `OPEN` review left by a closed gate is the *same* trap reached through the **approve** endpoint, and shut the door rather than guarding it. That was not in my finding and it is correct.

**`continue_as_new` is not a close**, and the reasoning is exactly right — parking there would settle the gate against itself, since `HELD_FOR_OPERATIONS` is a resolved state and the resumed run would find every review settled and send nothing for a case nobody had answered. Removing the `continuing` guard turns `test_a_continue_as_new_is_not_a_close` red, so the distinction is pinned and cannot be relaxed silently.

**The `finally` is best-effort by design**, with a stated reason I agree with: a failure there would replace whatever was unwinding — including a cancellation — with an activity error, and the case would lose the reason it was ending. An unparked review is visible on the panel and recoverable by a later close; a swallowed cancellation is not.

## New finding

### F3 (BLOCKING) — the liveness check runs before the review's own state, so a review already parked by rule 2 is told to retry indefinitely

- **File:** `backend/src/return_platform/api/case_reviews.py` — `execution_holds_review` (lines 209-238, the bare `except (TimeoutError, ConnectionError, RPCError)`) and its call site in `retry_review_delivery` (lines 993-1010).
- **Rule violated:** AMENDMENT-5 rule 1's own stated purpose — "refused (409) **naming the legal action**" — is not delivered on the path that will be most common; charter standard dimensions (error classification).
- **Confirmed by RV, two probes.**

  1. **`NOT_FOUND` is reported as unknown.** A workflow that no longer exists is a *definitive* answer that nothing is holding the review, and there is nothing to ask again about. The endpoint answers **503 `EXECUTION_LIVENESS_UNKNOWN`, `retryable: true`**. The branch's own panel route already draws exactly this distinction — `case_panel.py:199-205` classifies `NOT_FOUND` as a normal informative answer with its own reason string, separate from `UNAVAILABLE`/`DEADLINE_EXCEEDED` — so the two surfaces disagree about the same status code.

  2. **The sharper case, and the reason this is blocking.** A review **already parked by rule 2** — sitting in `HELD_FOR_OPERATIONS`, the exact state the amendment created so an operator would have a legal action — retried while the host is unreachable:

     ```
     [NOT_FOUND]   state=HELD_FOR_OPERATIONS -> 503 EXECUTION_LIVENESS_UNKNOWN retryable=True
     [UNAVAILABLE] state=HELD_FOR_OPERATIONS -> 503 EXECUTION_LIVENESS_UNKNOWN retryable=True
     ```

     The aggregate would have refused this cleanly and definitively — `retry_delivery` requires `DELIVERY_FAILED`, and `HELD_FOR_OPERATIONS` is not it — but the liveness check is consulted first and converts a state-based refusal into an indefinite "try again shortly." The operator is told to keep retrying a review that can never be retried, and is never pointed at `resume_from_hold` or `abandon`.

- **Why this matters more than the raw status code.** The normal way a gate closes is: gate closes → rule 2 parks the review → operator arrives at the recovery surface. In that ordinary sequence the review is `HELD_FOR_OPERATIONS`, and any transient host problem now produces a retryable 503 rather than the answer that would send the operator to the exit rule 2 built. Rule 1 exists to replace "succeed into a discard" with "refuse and name the legal action"; on this path it replaces it with "come back later," indefinitely.
- **It does fail closed** — the review stays where it was, nothing is changed, and no trap is rebuilt. This is a wrong-answer defect, not a state-corruption one. That is why it is a finding rather than a halt.
- **Fix, and it does not disturb the amendment's ordering rationale.** The amendment's concern is that a guard must not run *after the CAS*; reading the review's state is not the CAS, and `retry_delivery` performs that read internally anyway. So:
  1. Read the review first and refuse definitively (409, naming the legal action) when its state cannot accept a retry — `HELD_FOR_OPERATIONS`, `SENT`, `CANCELLED`, `ABANDONED`, `OPEN`, `APPROVING`. Ask liveness only when the state would otherwise permit it.
  2. Classify `RPCError` by status the way `case_panel.py` already does: `NOT_FOUND` → not holding (409), `UNAVAILABLE`/`DEADLINE_EXCEEDED`/timeouts → unknown (503).

  I am not asking for the 503 to be removed — the distinction it draws is a good one, and the argument that "final" and "ask again" send an operator to opposite actions is right. The defect is only that it is reached too early and on too broad an exception.

## Adjudications you asked for

**The S2 `_TRANSITIONS` edit — acceptable, and on the merits rather than on the amendment being cited.** §10 gives S2 the state transitions, so this is a cross-slice edit to a merged module and rule 11 is the relevant test. It passes, for four reasons I checked rather than accepted:
1. AMENDMENT-5 rule 2 **names this transition** in the contract text. Implementing a written amendment is not inventing one, and rule 11's concern — "another slice's contract altered to compile" — is the opposite case.
2. Rule 2 is genuinely unbuildable without it: `hold_for_operations` from `OPEN`/`DELIVERY_FAILED` requires those arrows to exist.
3. **The edit is exactly co-extensive with the amendment.** I diffed `review_aggregate.py` in full: two arrows added to the table, `allowed_states` widened on `hold_for_operations`, and nothing else in S2's semantics touched.
4. It is declared loudly at the site, addressed to RV, rather than slipped.

Returning a two-line table widening the orchestrator has already specified in writing would cost a slice round-trip and an S2 re-review for no contract risk. **`HELD → HELD` deliberately omitted** is the right call and the stated reason is the right reason: re-holding would overwrite the first hold reason with a later one, and the caller treats the skip as the no-op it is.

**The `actorId` adoption — all three checks pass, and the trap is closed.** Parameter added (`actor_id=actor_id` at both write sites), value-level `"actorId": actor_id` key **gone**, stopgap instruction **gone** (the only remaining mention is prose recording that the key *was* a stopgap and is now removed), and `stored()` asserts against the **stored key** `actorId` rather than the parameter — which is the distinction that matters, since a parameter assertion would pass against a repository that accepted the argument and dropped it.

The slice's honest report is accurate and narrower than it might sound: removing the double's *explicit `actor_id` parameter* does not fail, because the runtime signature bind already covers it. That is a statement about the double's own declaration being redundant, not about the production write being unpinned. I probed the thing that matters — dropping `actor_id` from a gate fact write — and it turns **10 tests red**. The trap is closed. Keeping the explicit parameter for the port's shape and `stored()`'s default, while declining to claim it as a guard, is the right way to hold both facts at once.

**The `signal_id` asymmetry — the slice is right and my advisory A1 is withdrawn as answered.** I asked for uniformity; the slice found that uniformity would be wrong, and the argument is better than mine. A deterministic approval `signal_id` would collide with the frozen CAS key, so a **second** actor approving the same version would meet `record_command`'s "same signalId, same payload → idempotent no-op" and receive a duplicate receipt reading as success — when in fact the *first* actor's approval is the one that went out. With a random id they meet the frozen CAS instead and get a 409 that correctly says somebody else approved this version. Retry is genuinely the other case: a second operator asking for the same stored delivery identity is asking for the same thing, and the outcome is identical whoever asked — so deterministic is right there, and it is now `f"{REVIEW_DELIVERY_RETRY}:{review_id}"`. The rule — *deterministic where a repeat means "again", random where it means "somebody else"* — is a good one and worth keeping stated. **One small request:** that reasoning currently lives in the ledger, and the `uuid.uuid4()` at `case_reviews.py:776` has no comment beside it. A future tidier will "fix the inconsistency." Worth one sentence at the site.

**The replay-safety claim — probed, and it holds structurally.** `hold_unsettled_reviews` is called from `_await_template_reviews`' `finally`, which is only reached by a history that entered the gate, and the gate is inside the patch marker — so a pre-gate history can never reach the close, and gate and hold ship in one release. I tested the claim rather than reading it: hoisting the close outside the patch marker turns `test_a_legacy_history_opens_support_instead_of_wedging` red. The test asserts the patch-id sequence *and* names the activity explicitly, so a later edit relaxing the sequence list cannot quietly introduce a command a pre-gate history has no record of. That is the right belt-and-braces for a replay claim about in-flight cases, and the second guard genuinely earned its keep.

**Three pre-amendment gate tests updated with in-place notes**, and a deadline docstring that made the same claim in prose corrected — the right way to move an assertion when the contract moves under it, since the note explains why the old expectation no longer holds rather than silently rewriting it.
