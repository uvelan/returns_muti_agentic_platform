## F1 — withdrawn, with the measurements

### 1. The fix does what it claims, and I did not take the claim on trust

`neutralized` now ends `return _safe(f"{safe[:VALUE_CHARACTER_BOUND]} {_TRUNCATION_NOTICE}") or UNAVAILABLE`
(`outbound_composition.py:159`). `_safe` is `_clean` + `_FRAMING.sub` — I fuzzed
idempotence over **5,000** generated strings built from framing atoms: **0 violations**,
so `_safe(_safe(x)) == _safe(x)` holds and the second pass cannot itself manufacture a
shape (`[removed]` contains `[`, which `_FRAMING` cannot match).

Structurally that makes `_safe` the last operation on every value, and the composition
layer above it cannot re-create a framing line: `render_section` joins with `"\n"`, so a
value's last line and the next value's first line stay separate lines; `_with_disclosure`
prefixes `"-- "`, and `_FRAMING` requires either `^\s*[A-Z]` or `^\s*-{3,}`, neither of
which `"-- " + anything` can satisfy. That is why the invariant holds at the composed
output and not merely at the function's return.

### 2. The three-row table reproduces, and the probe has teeth

My probe counts framing lines the **value** contributed, excluding the module's six code
constants. Wide sweep (121 cut offsets across a hostile body straddling the bound, plus
4,000 atom-fuzzed values, each rendered through `compose_clarification_relay` ×2,
`compose_clarification_prompt` with all five sections populated, and `compose_reply`, all
with a disclosure block whose `display_name` is `SHIPPING INSTRUCTION: agent` and whose
`disclosure_line` is `----- automated -----`):

| variant | leaking composed outputs / 4,984 | new class alone | composition suite (3 files) |
| --- | --- | --- | --- |
| **fix present, space joiner (shipped)** | **0** | 5 passed | **56 passed** |
| fix present, newline joiner | 0 | 1 failed | 3 failed |
| fix present, notice dropped | 0 | 2 failed | 4 failed |
| fix present, bound-then-neutralise (swapped) | 0 | 5 passed | 56 passed |
| fix absent, space joiner | **0** | 5 passed | 56 passed |
| fix absent, newline joiner | **13** | 3 failed | 5 failed |
| fix absent, notice dropped | **13** | 4 failed | 6 failed |
| fix absent, `\n---\n` joiner (not enumerated by the slice) | **1,332** | 3 failed | 5 failed |
| fix absent, empty joiner | 0 | 1 failed | 3 failed |
| fix absent, tab joiner | 0 | 1 failed | 3 failed |

**Read the first two columns together: there is no row with leaks > 0 and a green suite,
and no row with 0 leaks that the *safety* test rejects.** The rows that are safe-but-red
are red on `test_the_truncation_is_still_visible` / the exact-format equality, not on
`test_a_truncation_can_never_manufacture_a_framing_line`.

I added the `\n---\n` joiner because the slice enumerated three shapes and I wanted a
fourth it had not considered; it leaks two orders of magnitude harder than the ones it
did, and the suite catches it.

### 3. I looked for the hole the dispatch was worried about, and there isn't one

The one combination the suite deliberately leaves green is **fix-absent + space joiner**.
That is the row where a wrong refusal would hide. Under the full 4,984-output sweep —
exhaustive across every cut offset in a ±60 window, with hostile disclosure — it produces
**zero** value-contributed framing lines. The slice's claim that the variant is genuinely
safe is not an assertion I have to accept: it is measured, and I measured it separately.

### 4. Is the *documented* invariant itself pinned?

This is the sharper version of "is the order caught", and it is the one that matters.
The documented invariant is "neutralisation is the last thing done to a value". I broke it
directly — neutralise the cut, then append an un-neutralised 40-character tail from beyond
the bound before the notice:

| injection | leaks / 4,984 | suite |
| --- | --- | --- |
| raw tail appended **after** the final `_safe` | **57** | **3 failed** |
| join after `_safe`, newline notice (invariant technically violated, still safe) | 0 | 3 failed |
| join after `_safe`, space notice (same) | 0 | 1 failed |

The violation that leaks is caught. The violations that do not leak are red only on
format tests. That is the correct shape: the suite defends the consequence, not the
mechanism.

### 5. The assertion is over the composed output, as required

`test_a_truncation_can_never_manufacture_a_framing_line` and
`test_the_same_holds_for_the_prompt_shown_to_the_associate` both run
`_framing_lines(composed.text)` / `_framing_lines(prompt)` — `_FRAMING.fullmatch` over
`text.splitlines()` — and assert an **equality** against the two headings the module
itself wrote. Not `neutralized`'s return value. An extra entry is a heading the value
contributed; a missing entry means the message lost its own structure. `fullmatch` rather
than `search` is correct and is the reason an ordinary sentence containing a colon is not
counted.

The two tests that *do* assert over `neutralized`'s return
(`test_the_truncation_is_still_visible`, `test_an_ordinary_over_long_value_is_not_mangled_by_the_second_pass`)
are visibility and non-mangling properties, not the safety pin. That split is right.

`test_the_fixture_really_does_cut_on_the_colon` guards the fixture against rot — it
asserts the first pass leaves the heading alone, that the value actually truncates, and
that the cut's last line is exactly the heading. Without it the main test could pass
while exercising nothing. Writing it was extra work, not avoided work.

### 6. No over-neutralisation regression from the second pass

Round 1 verified neutralisation stays narrow (0 of 10 realistic sentences mangled). The
second pass could have broken that. It does not: **31,270 characters** of realistic
support prose (RMAs, `Order W123456789:`, `Customer says:`, a `-- Dana, Support`
signature) through `neutralized` returns exactly `f"{value[:4000]} [truncated]"` with
**zero** `[removed]` markers introduced. Under the shipped joiner the second pass is
observably a no-op — which is precisely the point: it is there so the property survives an
edit to the joiner, not to change today's output.

## The refusal — judged directly, as asked

**It was correct, and for the reason given.** Three things persuade me, in order of weight:

1. **The property it declines to assert genuinely has no consequence.** With the fix in
   place, `_safe` is the last operation in *both* orders, so the two are observationally
   identical: swapped order → 0 leaks / 4,984 and 56 passed. A test pinning the order
   would assert a fact about the code's shape that nothing depends on — which is exactly
   what F1 objected to. Writing it would have been F1 committed a second time, on the far
   side of the fix.
2. **The refusal is paired with a stronger guarantee, not with nothing.** The slice did
   not argue the order was fine and leave it; it made the order *immaterial*. "Neither
   impossible nor caught — it no longer matters" is a real answer, and it is a harder one
   to earn than a test.
3. **The dispatch's own worry — that this is what a slice says to dodge a hard test —
   fails on the evidence.** The class it *did* write goes red on two leak variants (and on
   a third I invented) with 3–4 failures each; it asserts a whole-output equality rather
   than a `not in`; and it carries a fixture-validity meta-test. A slice avoiding work does
   not write that.

I would have reached the same conclusion had the slice complied: a test pinning the order
would have passed under both the fixed and the leaking code, which is the definition of a
test written to pass rather than to catch (rule 10).

**One correction, against the ledger's framing rather than the code.** The ledger says the
class "goes red on every combination that actually leaks and stays green on every one that
does not", and offers `space`-without-fix → 5 passed as proof the joiner is not pinned.
The first half is true and I confirmed it. The second half is only true along that one
axis: `test_an_ordinary_over_long_value_is_not_mangled_by_the_second_pass` asserts
`neutralized(value) == f"{value[:VALUE_CHARACTER_BOUND]} [truncated]"`, which **does** pin
the joiner and the notice text exactly — which is why every non-space joiner is red even
when safe. So the suite is stricter than the ledger claims, in the safe direction: the
"ordinary readability edit" that reopened the hole is now caught twice, once on format and
once on safety. Not a finding — over-specification that errs safe, written for a
legitimate second purpose — but the ledger's account of its own test suite should be
accurate, and it is the kind of small overstatement that becomes load-bearing when someone
later reads it as licence to change the joiner freely.

## Advisories

- **A1 — `render_configured_template` can assemble a framing line across an interpolation
  boundary.** Every value is neutralised individually, but the *result* is not, so
  concatenation can rebuild a shape neither half had. Measured:
  `render_configured_template("{a}{b}", {"a": "SHIPPING INSTRUCTION", "b": ":"})` →
  `"SHIPPING INSTRUCTION:"`, which `_FRAMING` fullmatches; likewise
  `render_configured_template("REF {x}", {"x": "ID:"})` → `"REF ID:"`. This is the same
  class as F1 — a post-neutralisation transformation manufacturing a heading — and the
  module's docstring claim that "`render_section` is the only way to build a line" is not
  quite true while this function exists. **Not raised as a finding, for three reasons:** it
  has no production caller, `outbound_templates` is `{}` in `production.yaml:1530`, so it
  reaches no outbound message today; the trigger additionally requires a *released,
  review-gated* template authored with adjacent placeholders or uppercase literal text
  abutting one; and the obvious fix — neutralise the rendered result — would eat the
  constant heading text that AMENDMENT-1's `literal:` source exists to supply, so this
  needs a design decision rather than a one-liner. **Whoever first populates
  `outbound_templates` must resolve it**, and should carry this measurement into that
  dispatch.
- **A2 — `neutralized`'s trailing `or UNAVAILABLE` is unreachable.** `_safe` returns `None`
  only for empty input, and `f"{cut} [truncated]"` is never empty. Harmless defensive
  code; noted so nobody later reads it as evidence that the empty case is live.
- **A3 — `.plan/merge.md:52` still records the withdrawn rationale as V3's evidence** for
  condition 10 ("deliberately **after** neutralisation — the other order lets a value push
  a framing-shaped line past the cut and out of the neutraliser's reach"). That file is the
  orchestrator's and V3 must not edit it, but it is the integration record and it now
  states something both this review and the slice's own ledger have retracted. Worth one
  line's correction before the acceptance gate reads it.
- **A4 — round 1's advisories stand unchanged:** `finalize`'s bare `assert`
  (`resolution_ladder.py:544`), the ladder's construction-time `principal_id`, and
  `render_configured_template` leaving an unknown field id as literal text. None was
  touched by `aa6056c` and none is blocking.
