## Finding

### F1 (rule 10, and it lands on §9's neutralisation guarantee) — the outbound guarantee depends on the truncation notice's formatting, which is undocumented and unpinned

- **File:** `backend/src/return_platform/operations/return_support/outbound_composition.py`
- **Lines:** 110–128 (`neutralized`), specifically 123 (`safe = _safe(value)`) and 128
  (`return f"{safe[:VALUE_CHARACTER_BOUND]} {_TRUNCATION_NOTICE}"`), against the
  rationale stated at 118–122 and the bound's rationale at 96–105.
- **Rule:** 10 — a documented safety property with no assertion behind it, and prose
  claiming a protection that is not the one actually operating.

**What I verified first, because it is the claim you asked about.** The ordering *is*
neutralise-then-bound, exactly as stated. Confirmed by reading and by probe: a
framing-shaped line placed beyond the 4,000-character cut does not appear in the output.

**But the ordering is not what makes the output safe, and the ordering is not pinned.**
Two measurements:

1. **Swapping the order to bound-then-neutralise leaves the entire composition suite
   green** — 51 passed across `test_support_outbound_composition.py`,
   `test_support_reply_gating.py` and `test_support_clarification_roundtrip.py`. Nothing
   in the slice asserts the order the docstring argues for at length.
2. **I could not construct a value on which the two orders differ.** In the rejected
   order, content past the cut is also absent from the output, so the stated hazard —
   *"a value push[ing] a framing-shaped line past the cut and out of the neutraliser's
   reach"* — does not materialise: what is out of reach is also out of the message. The
   documented reason for the ordering is not the reason the ordering is right.

**What is actually load-bearing is the truncation notice, and it is undocumented.**
Under the shipped order the whole value is neutralised first, so a heading *with trailing
content* — which `_FRAMING` correctly leaves alone — survives; the cut can then land
exactly after its colon, manufacturing a framing-shaped final line that the neutraliser
has already run past. Measured, with the cut landing on the colon by construction:

| Final line built as | Un-neutralised framing line in the composed output |
| --- | --- |
| `f"{safe[:BOUND]} {_TRUNCATION_NOTICE}"` (shipped) | **No** — `SHIPPING INSTRUCTION: [truncated]` does not match `_FRAMING` |
| `f"{safe[:BOUND]}\n{_TRUNCATION_NOTICE}"` (notice on its own line) | **Yes** — `['SHIPPING INSTRUCTION:']` |
| `safe[:BOUND]` (notice dropped) | **Yes** — `['SHIPPING INSTRUCTION:']` |

Moving a truncation marker onto its own line is an ordinary readability edit. Neither
variant is caught by any test.

**The path is live, not theoretical.** `SupportIngressLimits.max_body_characters`
defaults to **16,000** — four times the composition bound — so the truncation branch is
reachable by an ordinary long message and trivially reachable by a hostile one, whose
author controls both the content and the offset. The output is an outbound **Channel B**
message: V3 owns this composition entirely, and a forged heading in it is precisely the
V1 defect this module was built to prevent.

**Fix (one line, and it makes the property independent of formatting):** neutralise again
after truncating — `_safe` is an idempotent regex substitution, so
`return _safe(f"{safe[:VALUE_CHARACTER_BOUND]} {_TRUNCATION_NOTICE}") or UNAVAILABLE`
closes all three rows of the table at once. Then pin it: one test with an over-bound
value whose framing-shaped line lands at the cut, asserting no line of the composed
output matches `_FRAMING`. And correct the docstring — the operative invariant is "no
framing-shaped line survives *into the composed output*, however the value was cut", not
the ordering.

## The three self-found defects — all genuinely fixed, verified by re-injection

### 1. Thread-id collision — fixed, and injective by construction

I did not stop at re-running the refusal test. Four measurements:

- **Removing the separator refusal** (`resolution_state.py:113`) → **3 failed**, the
  parametrised cases including the real `support-response-agent:wi-7` shape.
- **Exhaustive injectivity probe** over an alphabet containing the separator
  (`a`, `b`, `:`, `a:`, `:a`, `ab`, `a:b`, `-`, `1`, both positions): **25 accepted, 56
  refused, 0 collisions**. The pre-fix bare join collides on the same alphabet — e.g.
  `("a", ":a")` and `("a:", "a")` both mint `support-resolver:a::a`.
- **The real producer is compatible.** You flagged this as the thing to probe hard, and
  the sharp version of the question is not "does it refuse colons" but "can the platform
  still build a thread id at all". `derive_support_event_id` — the *inbound* minter, and
  inbound is what the ladder answers — returns a **uuid5** (`73e0e46c-…`), colon-free and
  accepted. The colon-bearing `support_event_id_for` is the *outbound simulator's*
  identity, correctly refused and correctly cited in the docstring as proof that colons
  occur in this codebase's event ids.
- **The codebase already agrees with the fix.** `derive_support_event_id` length-prefixes
  its own parts for exactly this reason (`("a","bc")` vs `("ab","c")`). The refusal is the
  same principle by a stricter route.

Injective by construction, compatible with the real producer, and the failure mode if a
caller ever supplies a colon-bearing id is a loud `ValueError` on the first call — not a
silent shared checkpoint. Withdrawn as a concern.

## For the orchestrator — the `actorId` gap is cross-slice and needs a decision now

**The gap is real.** §4: *"Command-originated facts carry server-stamped `actorId`."*
S1's `append_scoped_case_fact` (`case_repository.py:383-401`) has no `actor_id`
parameter, **and the document it persists has no `actorId` field at all** — so this is not
a signature omission that a caller could work around, it is a schema that cannot hold the
value. V3 carries the actor inside the fact value as `answeredBy`.

**My read: this is not a rule-6 violation by V3.** The fact carries agent, channel,
method and timestamp; the actor is recorded and auditable; and V3 used the only mechanism
available to it. Editing S1's shipped repository contract to make its own code compile is
exactly what rule 11 forbids, and §10's rule for a missing contract — return it to the
owning slice through the orchestrator rather than work around it silently — is what the
slice did.

**But the platform is now in a state where §4's requirement is unimplementable, and three
slices are about to solve it three ways.** A value-level `answeredBy` is caller-supplied
data indistinguishable from any other value field: no uniform query for "facts by actor",
nothing to stop the next writer omitting it, and no reason for V1 phase 2 to choose the
same spelling when it writes revision facts with an actor. That is the drift rules 2 and 6
exist to prevent, arriving through a gap rather than through a decision.

**Recommended action, and the sequencing matters:** reopen S1 to add `actor_id` to
`append_scoped_case_fact`, persisted as a top-level `actorId`, **before V1 phase 2 writes
its first revision fact**. Then V3's `answeredBy` becomes a migration rather than a
precedent. If S1 is not to be reopened, the alternative is a recorded contract amendment
naming the value-level key **once**, binding on every slice — but the schema-level field
is the better answer, and it is cheap while only one slice has written such a fact.

## Verified and not contested

- **The ladder's escalation discipline.** Three distinct reasons (sub-threshold,
  conflicting sources, missing required entity), none of which produces an answer, and
  conflict escalating *immediately* without preferring a source — a ladder that resolved
  disagreement by precedence would be inventing an answer neither source gave.
  `_conflicting` reads the model's own `agreesWithPrior` rather than comparing text, and
  agreement left unstated is correctly not a conflict (pinned).
- **Budget exhaustion is visible work** — one fact
  (`support_resolver_budget_exhausted`, derived id per support event so a retry does not
  double-write), one escalation, no answer; and the negative case is pinned too, so a
  writer that fired on every run would not pass.
- **`_resolve_payload` enumerates the prompt's key set** rather than assembling it from
  state, so a checkpoint field added later cannot silently become a prompt input. That is
  the code-side half of `allowedInputKeys`, and having both halves is right.
- **Resume semantics.** `attempt` is deliberately absent from both the state and the
  thread id, with the reasoning stated: a per-attempt thread would turn "resume" into
  "start again" while still passing any test that only checked a retry completes.
  Acceptance 23's shape is pinned by `test_a_retry_resumes_at_the_last_completed_node`.
- **Standing greps.** The three new fact names
  (`SUPPORT_RESOLVER_BUDGET_EXHAUSTED`, `SUPPORT_REPLY_DRAFT`,
  `SUPPORT_CLARIFICATION_ANSWERED`) are declared in `operations/fact_names.py` and
  referenced by V3 code in the same change; ACC's guard is in the green suite. No new
  imports of frozen modules. No template/section/intent/tool literals in code — the intent
  taxonomy is a released closed set and the schema registry is a code-side allowlist,
  which is the opposite of the hardcoding rule's concern.
- **Rule 3:** no workflow-definition file is touched (which is deviation 1's whole point).
  **Rule 8:** no credential in the diff; the only credential surface is an id.
  **Rule 11:** files are V3's declared set plus the integration-agent shared files
  (`return_configuration.py` append, `production.yaml` block, `ai_gateway.yaml` tasks).
- **Integration honestly reported.** `api/case_clarifications.py` is genuinely unmounted —
  no reference in `main.py` — and the slice says so rather than implying a wired system.

## Advisories

- **A1 — `finalize`'s guard is a bare `assert`** (`resolution_ladder.py:544`), stripped
  under `python -O`. It still fails loudly (a `TypeError` on the next line) rather than

  rather than raising. The reasoning given (a released template naming a missing field
  should reach an operator as visible text, not swallow the whole outbound message) is
  sound, but it means a typo in a released template ships `{field_id}` to Support. Worth a
  release-validation check that every field id a template names is one the message carries
  — the §8 precedent for subject placeholders.
