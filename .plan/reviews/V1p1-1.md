## Blocking findings

### F1 — The default `production.yaml` variant does not reproduce today's handoff, and the recorded caveat covers the wrong half

- **Files:** `backend/config/returns/production.yaml:1835-1990` (the `default` variant);
  `backend/tests/operations/test_support_template_renderer.py:527`;
  `.plan/tracks/V1.ledger.md:46`; `.plan/handoffs/V1-phase1.md` (silent on this).
- **Rules:** 2 (contract drift — contracts.md §8: "Default `production.yaml` block
  reproduces today's `compose_support_handoff` output"), 10 (a test that passes
  rather than catches).

The equivalence test holds *on its own fixture*. I re-ran it: green. But the fixture is
constructed so that every conditional in `compose_support_handoff` takes the branch the
template can express — a branch associate is named, the bay is `RECOMMENDED`,
`outstanding_support_dimensions` is empty, `return_details.additional` is empty. Change
any one of those and the two paths diverge, silently.

Rendered by me against the shipped `production.yaml`, same renderer, a case with no
branch associate and no bay recommendation (`gaps: ()` — the renderer reports **nothing
wrong**):

```
--- compose_support_handoff
+++ default variant
 - Account: ACCT-9
-- Branch Associate: Not recorded -- customer contact below
-- Customer Phone: 555-0199
-- Customer Email: buyer@example.com
+- Branch Associate: Not available
+- Branch Associate Email: Not available
+- Branch Associate Phone: Not available

 - Product Presence: AT_BRANCH
-- Warranty Claim: YES

 - Handling/Staging Instructions: Not available
-- Unresolved Reason: No bay free

 - Required Return Information: Complete
-- Awaiting From Support: RMA, LABEL

 - Review or confirm the bay recommendation.
-- Resolve manual bay assignment: no bay could be recommended.
```

Why it matters, line by line:

1. **The customer's phone and email disappear.** `support_handoff.py:118-127` records
   this exact loss as a defect it fixed: "what Support got in their place was three
   lines of `Not available` on a case whose order carried a phone number and an email
   address all along." The default variant reinstates it.
2. **`Awaiting From Support` disappears** — including its three-state
   `UNKNOWN -- case state could not be read` arm, which `support_handoff.py:405-422`
   argues at length must survive any rewrite because "nothing is outstanding, proceed"
   and "we could not find out" send Support to opposite actions.
3. **`Unresolved Reason` and the `- Resolve manual bay assignment` action line
   disappear** on exactly the cases that need them.
4. **`return_details.additional` disappears** — the property that "a release that adds
   a field does not need this module edited" (`support_handoff.py:157-160`).

None of these produce a `TemplateGap`, because each field carries a `fallback`. Phase 2
swaps the composed path for this one behind `workflow.patched`; on the day that lands,
Support silently starts receiving a shorter message on precisely the cases where the
missing lines are the ones that matter.

The ledger's recorded caveat (`V1.ledger.md:46`) says **"body text compared exactly"**
and qualifies only the *subject*. The subject caveat is correct and honest. The body
sentence is not: the body is compared exactly on one fixture chosen to avoid every
divergence, and the five divergences above are neither named nor tracked anywhere in
the diff. That is the caveat pointing away from the problem.

**Resolution required (either):** (a) express the conditionals — which the §8 clause
grammar cannot do today, so this returns to the orchestrator as an amendment; or
(b) narrow the claim to what actually holds, in all four places it is made (yaml
comment `production.yaml:1824-1829`, test docstring, ledger:46, handoff spec), and
record the five unexpressible divergences as a named contract-level open item that the
phase-2 gate must not cross silently. A `fallback` is not an acceptable stand-in for a
line the composed path emits conditionally — it renders "Not available" where the truth
is "no bay could be recommended, resolve manually".

### F2 — Five `case_fact:` bindings in the shipped default variant name facts that do not exist, and the vocabulary is duplicated in code

- **Files:** `backend/config/returns/production.yaml` (fields `workflow_status`,
  `selected_items`, `order_confirmation`, `required_return_information`,
  `policy_evaluation`); `backend/src/return_platform/api/template_preview.py:60-97`.
- **Rules:** 1 (fact-name literals in code with no single home), 2 (contracts.md §8:
  "`case_fact:<factName>` → scoped facts only").

`workflow_status_at_handoff`, `selected_items`, `order_confirmation`,
`required_return_information` and `policy_evaluation_rendered` appear nowhere in
`backend/src` outside `template_preview.py` and this branch's own additions. No
activity writes them; `operations/fact_names.py` does not carry them. The renderer's
docstring declares the seam — "the assembler wraps snapshot values it derives ... the
same way, with no `factId`" — but the assembler is phase 2 and unwritten, and the seam
exists only as prose.

The consequence is the F1 failure mode again, from a second direction: if phase 2's
assembler spells any of those five keys differently, the field falls to its `fallback`,
no gap is raised, and the handoff quietly loses the line. Nothing in this diff would
fail.

Meanwhile `template_preview.py:60-97` is a second, code-side copy of the whole binding
vocabulary — 24 keys — with nothing keeping it in step with `production.yaml`. Its own
docstring claims "the sample mirrors the representative fixture the equivalence test
pins, so 'preview of the default variant' and 'what `compose_support_handoff` says
today' are the same text". No test asserts that. A rename in the yaml makes the preview
start showing fallbacks for values a real case would fill, which is the one thing the
preview screen exists to be trusted about.

**Resolution required:** give the synthesised (non-fact-log) key vocabulary one code-side
home that phase 2's assembler must import, and derive or assert the preview sample
against it, so a mismatch is an import error or a test failure rather than a blank line
in a support message.

### F4 — `return_record:<attr>` resolves through unconstrained `getattr`

- **File:** `backend/src/return_platform/operations/support_template_renderer.py:245-248`.
- **Rule:** 9 (the grammar must not let released config reach beyond what it declares).

```python
def _record_attribute(record: Any, attribute: str) -> Any:
    if isinstance(record, Mapping):
        return record.get(attribute)
    return getattr(record, attribute, None)
```

`attribute` comes straight from `source_binding` in released configuration, unvalidated
against the projection's declared fields. `return_record:__class__` resolves to a class
object and `_text` will happily render `<class '...'>` into the message a human on the
Support desk reads; other dunders reach further. There is no call and therefore no code
execution — this is not an eval path, and the rest of the grammar is genuinely clean
(see "What is clean" below) — but §8's whole premise is that a template can only reach
what it declares, and this one reads an open namespace. Publishing is capability-gated,
which lowers the severity, not the finding.

**Resolution required:** validate `return_record:` attributes against the projection's
declared field set at release validation (the model already validates formatter ids the
same way), or at minimum refuse names beginning with `_`.

## Non-blocking advisories

Not findings. Listed for the slice's judgement; none gates merge.

- **A1 — a multi-record subject silently takes the last record's value.**
  `support_template_renderer.py:549`: the `values` map for subject interpolation is
  built by flattening every rendered section, so in a per-record group two records'
  copies of the same `field_id` collide and the last one wins. Today's
  `production.yaml` subjects interpolate only case-level fields, so this is latent; a
  variant whose subject names a per-record field would state one RMA's value for a
  request covering several. Worth either scoping the subject map to case-level sections
  or refusing a per-record `field_id` in `subject_template` at validation.

- **A2 — the publish success message probably never renders in production.**
  `SupportTemplateSection.tsx:129` keys `DocumentEditor` on `active.releaseId`, and
  `onSubmit` awaits `invalidateQueries(["config"])` before returning. In production the
  refetch returns the *new* release id, the key changes, the editor remounts, and the
  `role="status"` "Release … is published" at line 162 is destroyed with the old
  instance. The test does not catch this because `mocks.runtime` returns a static
  `rel-1`. The four DONE steps survive (they live in the parent), so the operator is not
  left with nothing — but the announced confirmation, and the "cases already running
  keep the template they started with" reassurance, are the part that gets lost.

- **A3 — the one behaviour delta in the `DocumentEditor` extraction.**
  `AgentsSection.tsx:176`: `invalidateQueries({queryKey:["proposals"]})` moved from the
  mutation's `onSuccess` into `onSubmit`, i.e. before the mutation resolves. A rejected
  invalidation now presents to the operator as a failed proposal submission when the
  proposal in fact succeeded. Rare, and strictly safer than the old unhandled rejection,
  but it is a change and the 32 passing tests do not cover it.

- **A4 — the preview endpoint accepts an unbounded template under a read capability.**
  `template_preview.py`: `variants`, `sections` and `fields` have no length bounds
  (individual strings do). `RETURNS_SESSION_READ` is a wide grant relative to
  `config.release.promote`, and rendering is synchronous. Contract §9 puts size limits on
  config publish; a bound here would be consistent.

- **A5 — the versionless-path guard now carries three exemptions.**
  `frontend/src/api/noVersionedPaths.test.ts:52`: `/api/v1/config/support-template/`
  joins two existing entries. The reasoning given (no `POST` on the versionless
  `/api/config` surface, whose only mutation is promotion) is coherent and the entry is
  narrow and documented. Recording it because widening a guard is how a guard stops
  guarding, and this is the third time.

- **A6 — `item_list` is the residual template-string locus in code.**
  `template_formatters.py:90-97`: six labels and six item keys as literals. Contract §8
  puts formatters code-side, so this is not hardcoding "instead of config" — but it is
  the one place where changing the handoff's wording still means changing Python, and it
  belongs on the `compose_support_handoff` retirement follow-up rather than being
  forgotten because the formatter allowlist made it look settled.

- **A7 — files touched outside the brief's declared set.**
  `domains/ai/AiControlCenterPage.tsx`, `api/releasePublish.ts`,
  `components/PublishProgress.tsx`, `domains/registry.ts`,
  `api/noVersionedPaths.test.ts`, four OpenAPI snapshots. I verified each is either a
  verbatim move, a mechanical registration, or a generated artefact, and none belongs to
  a concurrently-active slice. Not held as a rule-11 breach; recorded so the orchestrator
  sees the actual footprint rather than the declared one.

## What is clean

Selector semantics match §8 exactly, including the two decisions that could easily have
gone the lazy way: a clause-less rule matches *nothing* (the catch-all belongs to
`default_variant_id`, not to whichever variant was listed first), and a mixed
parcel-and-LTL render falls to the default rather than sending one freight class's
instructions about the other's. Graph batching is real and pinned — N missing bindings
across M sources cost exactly M `synchronize` calls, the within-draft cache prevents a
re-render from syncing a source twice, and both are tested. Per-record section groups
are derived structurally from their bindings rather than from a flag that could disagree
with them, and a case-level fact provably cannot leak into a record group. `extra="forbid"`
throughout, so an unknown key is a refused release. The preview accepts no case id at
all, which is a stronger guarantee than checking case access would have been.
