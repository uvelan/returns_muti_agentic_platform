## Round-1 findings — both withdrawn

### F1 — WITHDRAWN. The chain is allocated inside the transaction, the fork is now expressible, and the instrument that proves it is sound.

**The source fix is right, and complete.** The tail read and the sequence allocation moved inside `transaction`, with `session` threaded through `_classify_command` → `_classify_command_fields` → both `_last_enqueued_inbound_event` and `ordered_command_fields`. Making `session` a **required** parameter on all three rather than defaulting it to `None` is the right call and the docstring gives the right reason: a future caller outside a transaction would get a chain that forks *silently*, because the sequence numbers would still be distinct and only the predecessor would be wrong. `drain_parked` got the same treatment, which matters — two drains racing one backlog is the same defect wearing different clothes.

**The sufficiency argument — judged specifically, as asked, and it holds.** The claim is that `allocate_case_stream_sequence`'s `$inc` on the per-`(case, stream)` counter is now inside the transaction, so concurrent enqueues conflict on one document, one aborts, and `with_transaction` re-runs against a tail that includes the winner. That is sound, and the guarantee is structural rather than probabilistic: two transactions writing the same document produce a write conflict in MongoDB, the loser's abort is a `TransientTransactionError`, and `with_transaction` retries by re-running the **whole** callback against a new snapshot — which re-executes the tail read. The ordering inside the callback is what makes it work: the tail is read *before* the counter write in the same transaction, so a conflict on the counter always invalidates the read that preceded it. If the two do not overlap, the second's tail read already sees the first. Both branches give a chain.

**One edge worth recording, not a finding.** `allocate_case_stream_sequence` upserts the counter, so the *first two* messages on a brand-new case may race to insert the same `_id`. Depending on server version that surfaces as a write conflict (retried, correct) or as a duplicate-key error (not a `TransientTransactionError`, so not retried). In the second case the transaction aborts with nothing partial committed and `record_inbound_message`'s `except DuplicateKeyError` re-raises, because this event's own inbound document was never written — the caller gets an error and the transport retries. **It fails closed: an error, never a fork.** The ordering guarantee is unaffected; the cost is a spurious 5xx on one narrow race. Worth knowing when the live-infra acceptance run exercises bursts on fresh cases.

**The instrument, verified independently in all three directions.** This is the load-bearing test for acceptance 18 and it has now been wrong once in each direction, so I did not take any part of it on trust:

| What I injected | Result |
|---|---|
| **Fault K** — tail read + allocation back outside the transaction | **2 failed** — `test_two_messages_arriving_together_still_form_a_chain` and `test_a_chain_built_under_concurrent_arrival_still_drains_in_order` |
| **Fault K′** — fault K, with the `_assert_is_a_chain` precondition suppressed so only the end-to-end delivery assertion is live | **1 failed**, on `dispatcher.dispatched == chain_order`. The headline assertion is genuinely load-bearing, not decorative |
| **The abandoned flattening loop** restored, plus fault K′ | **passed** — the defect reproduced exactly as the slice described it |
| The **sequential** drain test under fault K | **passed** — my round-1 point restated: it proves the dispatcher half only |

So the diagnosis was right and `load_against_the_answer` is what fixes it. Re-staggering on every pass, and clearing `leaseOwner`/`leaseUntil`, is the correct repair: `claim` sorts `(nextAttemptAt, createdAt)`, and flattening every waiting command to one `nextAttemptAt` hands the tie-break to `createdAt`, which is enqueue order, which is the answer. A deferred command returns with `now + 2s`, so a queue staggered once quietly sorts itself right during the drain.

**The two doubles are faithful, and I checked they are not what makes the test pass.** `_TransactionalClient` serialises `with_transaction`, modelling the *end state* of MongoDB's conflict-and-retry rather than the machinery — the second body runs after the first commits. That is exactly the property under test, and it is not load-bearing in the wrong direction: under fault K the tail read happens outside the lock, so the fork is still expressible and both tests still fail. `interleaved_reads` is necessary rather than decorative — an all-in-memory store never context-switches, so without it two `gather`ed calls run to completion one after the other and the double would be proving that concurrency does not happen. Real collection calls yield at every round trip.

`_assert_is_a_chain` asserts two properties rather than an expected list, with the right reasoning stated: a fork is precisely the shape an expected-list assertion written from a sequential run would still accept, because the sequence numbers are correct in both cases and only the predecessors differ.

## Advisory A1 — judged as a design choice

**The asymmetry is right.** An over-long *value* drops the artifact whole; an over-long *binding* nulls the claim and keeps the artifact. That is the correct way round, and for the reason given: the value **is** the payload, and a truncated tracking number is not a shorter tracking number but a different one — binding it would attach the wrong parcel to a real return, which is the same class of harm DR-11's never-guess-a-reference rule exists to prevent. The binding is only *metadata about* the payload, so discarding it degrades gracefully into machinery that already exists for exactly this situation: with no reference the artifact falls into S1's no-reference rules and becomes `BOUND` (one record), `AMBIGUOUS` or `UNMATCHED` — a clarification rather than a guess. Truncating either would have been the wrong choice; dropping the artifact on a bad *binding* would have been over-strict, discarding good data because a claim about it was unusable.

Choosing the ceilings from `ReturnOutcomeRecord`'s columns (256 / 128) rather than inventing them is also right: a value the authoritative store cannot hold is not a value worth carrying, and it makes the bound a fact about the schema rather than a number somebody picked.

**The asymmetry itself is pinned, not incidental.** I re-injected three of the five faults: truncating instead of dropping (**2 failed**), dropping the whole artifact on an over-long binding (**1 failed** — so "null the claim, keep the artifact" is a tested decision), and removing the value bound entirely (**2 failed**). Each caught by the test named for it.

**Can either silently lose an artifact a human sent? Effectively no, and the docstring's claim is accurate.** The message itself always survives: `rawBody` is stored on the inbound document and the full `bodyText` is written as the `support_message_received` case fact, so what Support actually wrote stays readable on the case — which is what the docstring claims, and it claims no more than that. A dropped artifact is ops-visible via `logger.warning` but not case-visible. Given the ceiling is the widest column the platform can store, a legitimate reference can never exceed it, so what is dropped is a malformed extraction rather than a real artifact. **Carried to phase 2, not held here:** when the panel is built, a "this message contained something we could not read" indicator would close the last gap cheaply, and it belongs with the rendering note the orchestrator has already carried forward.
