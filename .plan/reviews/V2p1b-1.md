## 1. The route move and its collision test — verified, including the two properties the dispatch asked me to doubt

**The walker really does cover unmounted routers.** `pkgutil.iter_modules(api_package.__path__)` + `importlib.import_module` + `dir(module)` reaches every module in `return_platform.api` and every `APIRouter` bound at module level in it, with no reference to `main.py` or to any mounted app. I ran it directly: **135 endpoints across 31 modules**, matching the claim exactly, and `support_ingress.router` is among them while being unmounted. De-duplication by `id(candidate)` is correct — several api modules import each other's routers, and without it the test would fail against itself.

**The normalisation matches FastAPI's matching semantics, and errs in the safe direction.** Starlette compiles `{name}` to `[^/]+`, so `/work-items/{work_item_id}/messages` and `/work-items/{id}/messages` are one endpoint; `re.sub(r"\{[^}]*\}", "{}", path)` collapses them to one key. The one place it *over*-normalises is the `:path` converter (`{x}` vs `{x:path}` compile to different regexes but normalise the same), which can only produce a false collision report, never a missed one. There is no under-normalisation. This is the question the dispatch asked and the answer is clean.

**The companion by-name assertion is the right instrument.** `assert claims[("POST", ...)] == ["return_support.router::add_message"]` fails if `return_support` is deleted, renamed, or has its handler replaced; a `not in` assertion would pass on all three. The GET discovery (`list_messages`) is real and material: the frozen path carried **two** live handlers, so T0's freeze would have displaced or shadowed both. **Integration sanity-check the dispatch asked for — done.** The committed `backend/openapi/return-platform.openapi.json` today has `/api/v1/return-support/work-items/{work_item_id}/messages` carrying **both** `list_messages` (GET) and `add_message` (POST), and no `inbound-messages` path (correct: router unmounted). After the integration agent mounts and regenerates, the document must show those two operations unchanged **plus** a new POST on `.../inbound-messages`. ## 2. The omc idempotency key — the three design choices judged, and the collision test verified against the separator

`uuid5(fixed_namespace, "|".join(f"{len(p)}:{p}"))` over `(case_id, support_event_id, return_record_id, artifact_type, value)`, prefixed `omc-return-update:`. The namespace is a fixed literal UUID, not minted at import — correct, and the docstring gives the right reason.

**Event-scoped rather than content-only: correct, and it is the choice §7 requires.** §7 defines a delivery identity as derived from the operation, and assigns collapsing to the receiver everywhere else in this contract. Two support messages naming one tracking number are two operations. Content-only keying would have this module silently implement a receiver-dedupe policy §7 does not give it, and would make "Support said it again" unobservable downstream. I agree with the choice and with the reason given for it.

**Content-keyed rather than position-keyed: correct, and it fixes a real latent defect.** The previously shipped key embedded the artifact's index in `bind_artifacts`' output. That is a hidden dependence on iteration order over the accepted extraction's artifact list: reorder it and every key moves, so a redelivery mirrors the same bindings again under new identities — a duplicate omc write on exactly the path acceptance 17 says must not produce one. Removing the index is not a tidy-up; it closes a rule-4 hole.

**Length-prefixing: verified as effective, and the collision test genuinely exercises the separator.** This is the item the dispatch flagged as having been "believed fixed three times", where adjacency turned out necessary but not sufficient. I injected the fault myself:

| What I injected | Result |
| --- | --- |
| length prefixes removed (`"|".join(parts)`) | **CAUGHT**, 4 failed — and critically, `test_a_value_carrying_the_separator_cannot_forge_a_part_boundary` fails **on its own merit**, not only via the pinned literal |

The test varies two **adjacent** parts (`artifact_type`, `value`) where one contains the separator: `("TRACKING|a", "b")` against `("TRACKING", "a|b")`. Bare-joined both render `…|TRACKING|a|b`; length-prefixed they differ. Both conditions the earlier generations kept missing are present here. That is a real collision test, not an adjacency test wearing one's clothes.

Two supporting properties also verified: the pinned literal `omc-return-update:448695e5-b59e-5f6b-b876-14e202c250ce` is the true uuid5 (I recomputed it), so the test cannot pass by comparing the function with itself; and `test_every_part_of_the_identity_changes_the_key` walks all five components one at a time, so a projection that dropped one could not hide behind the others.

**The digest question, checked and clean.** `record_omc_command` (the session-plane sibling) refuses a same-key row whose `requestDigest` differs; the new upsert does not check the digest. That is safe here and only here, because the payload `{caseId, returnRecordId, artifactType, value, supportEventId}` is a pure function of the five key components — two different payloads cannot reach one key. Worth knowing if the payload ever grows a component the key does not carry.

## 3. The defect the slice found — the fix is right, and the gate is the right shape

The old code read `if wrote: … mirror`. `wrote` is `False` on every redelivery because `_merge_bound_artifact` compares the stored value and returns `False` when it already matches — so on the redelivery meant to close the crash window the mirror was skipped, and skipped **permanently**, since no later attempt would ever merge either. The row was lost for good on the exact retry designed to recover it. This is a genuine defect and finding it required treating a green suite as suspect.

**The fix is correct and, more importantly, correctly *shaped*.** The gate is now `decision.status is BindingStatus.BOUND`, and the two skips inside `_mirror_to_omc` are `ARTIFACT_STORED_FIELDS[type] is None` and a blank value — both pure functions of the accepted extraction, both identical on every attempt. I checked them against `_merge_bound_artifact` line by line: they are exactly the two conditions under which the merge returns `False` for a reason *other* than "already stored". So the mirror now fires on precisely the set of decisions that represent a real change, on every attempt, and never on an attempt-dependent condition. A skip that depended on what this attempt did would be the `wrote` gate under another name, and it is not.

`test_the_mirror_is_written_even_when_the_record_already_holds_the_value` asserts `parts["records"].updates == []` before asserting the mirror happened — that is the assertion that makes the test prove something, and it is present. `test_a_bound_rma_confirms_identity_and_mirrors_nothing` dispatches twice and asserts both are empty, which is what distinguishes a decision-shaped skip from an attempt-shaped one.

## 4. AMENDMENT-4's honesty — verified clause by clause; the amendment does not overstate

The dispatch asked me to find the amendment overstating the code. I looked for that specifically and did not find it. Each clause:

| Amendment clause | Verified against |
| --- | --- |
| "there is no artifact-persistence transaction" | `persist_binding_decision` takes no session; neither `ReturnRecordStorePort` nor `ScopedFactAppendPort` has one; `_merge_bound_artifact` is an `expected_version` CAS with one re-read retry. **True.** |
| order is "merge → mirror row → outbox row" | `_persist_artifacts` calls `persist_binding_decision`, then `_mirror_to_omc`; `enqueue_omc_update` upserts `omc_command_records` and only then calls `enqueue_integration_command`. **True, in that order.** |
| "each a no-op on repeat" | merge: value-equality short-circuit. mirror row: `update_one(..., {"$setOnInsert": doc}, upsert=True)` on the uniquely-indexed `idempotencyKey`. outbox row: `enqueue_integration_command` is itself `$setOnInsert` upsert on `idempotencyKey`. **True for all three.** |
| "driven by at-least-once redelivery" | the classify command is acked only on `DispatchResult`; `ConcurrencyConflictError` is a `RuntimeError`, so the outbox's retry branch marks it retryable rather than dead-lettering; only `CandidateRoutesExhaustedError` and an unknown event dead-letter, both after their durable half is written. **True.** |
| acceptance 17 still holds | one omc row and one outbox row per derived key across three enqueues (`test_the_same_delivery_identity_mirrors_once_however_often_it_is_retried`), and a second distinct artifact still gets its own row — so "written once" is distinguished from "writes at most one row ever". **Holds.** |

Two details worth recording because they are the difference between the amendment being true and being nearly true. First, `$setOnInsert` rather than insert-and-catch means the retry cannot reset an in-flight row's `status`/`attemptCount` back to `PENDING`/`0` under the worker draining it — the slice tests this (B5) and it matters more than it looks. Second, the read-back before enqueue means the outbox payload names the `commandId` actually on file rather than the one this attempt computed. With the shipped derivation (`uuid5(namespace, delivery_id)`) those two coincide, so the read-back is defence rather than repair — but it is the right defence, because it also holds if a different writer put the row there, and the test pre-seeds a foreign id to prove it.

**§6's boundary rule is respected, not evaded.** Manufacturing the transaction §5 named would span `return_records`, `omc_command_records` and `integration_outbox` across two modules — a cross-store transaction §6 explicitly forbids claiming. Declining to claim it and amending the text is the correct resolution; building it and asserting a guarantee that does not exist would have been the contract violation.

**The amendment gives up exactly what it says it gives up.** The merge→mirror window is a recoverable gap bounded by the outbox's redelivery interval. That is stated in the amendment and in `DurableOmcMirror`'s docstring in the same terms. Nothing in the code claims more.

## 5. `routing_policy_version` — the enumeration is right, in both directions

Derived per access as `f"{schemaVersion}:{sha256(canonical projection)}"` from `invoker.dispatcher.configuration` (the document in force now, swapped atomically with routes under `AIRoutePool`'s lock) and `invoker.task`. `StructuredOutputInvoker.dispatcher` already existed — no shared-file edit was needed to reach it.

**Everything that determines routing is in.** I read `AIRoutePool` rather than the docstring: selection filters on `route.tier is task.tier`, `route.provider_name in task.allowedProviders`, and `configuration.context_shortfall(...)` which compares `modelContexts` against `task.maximumInputTokens`; admission consults `configuration.rateLimits` (`lightweight`/`standard` by tier) and `configuration.providerLimits`; the breaker consults `configuration.circuitBreaker`. Every one of those is in the projection. `allowTierEscalation`, `fallbackStrategy` and `fallbackTemplate` widen or terminate the same filter and are in. `retry` is arguably dispatch rather than routing; including it is over-inclusive, which can only cause a spurious bump, never a missed one.

**Only things that do not route are out.** `promptVersion` and `systemPrompt`/`systemPromptSections` are the release, already pinned as `release_id` on the same record — folding them in would make two fields say one thing twice and would report a routing change on a reword. `maximumOutputTokens` is deliberately excluded from `context_shortfall` upstream and so cannot rule a route out. `allowedInputKeys` gates payload admission, not route choice. `pricing` rides the release but does not route. `domain` is a single-valued `Literal` and cannot vary. `tasks` as a whole is out while this task's own fields are in — correct, since another task's reword is not this task's routing change, and the test asserts both halves of that.

**The tests assert the half that is easy to get wrong.** Not only "it moves when routing changes" (parameterised one field at a time, so a dropped field cannot hide behind its neighbours) but "it does **not** move when the prompt changes" and "does not move when another task changes, while that task's own version does". They run against the shipped `config/ai_gateway.yaml`, not a fixture built to agree with the code. `test_nothing_in_src_supplies_a_routing_policy_version_as_a_literal` turns my standing grep into a standing test and matches a string literal on the right-hand side rather than the keyword, so the legitimate pin at the call site is not caught by it.

Choosing a digest over a config key is right for the reason given: a hand-maintained version string fails silently when someone forgets to bump it, and every record then pins a policy version that no longer describes the policy.

**Per-route pinning / `block_exhausted`.** Confirmed still present: `StructuredStageInvoker.invoke` passes `route_id` only as `log_context={"routeCandidate": route_id}`, so `StructuredOutputInvoker` still routes internally and `ordered_candidate_routes` is the released task's `allowedProviders` in declaration order — a declared preference, not a constraint. `block_exhausted` therefore fires after candidate-count attempts rather than genuine provider exhaustion. **Not blocking, for three reasons:** the fix requires a route constraint on `StructuredOutputInvoker`, shared AI-gateway code outside V2's declared set, so fixing it in-slice would itself be a rule-11 breach; the record does capture who actually answered (`result["provider"]`) beside the pinned candidate, so the audit trail is not lying about what happened, only about what was eligible; and phase 1b does not worsen it — what item C changes is the policy version beside the list, which now moves with the release rather than with someone's memory. ## Observations — none is a finding

1. **The walker's scope is `return_platform.api` only.** Five further routers are mounted from outside that package (`bootstrap.api`, `configuration.api.agents`, `configuration.api.router`, `graph_analyzer.api`, `graph_schema_analyzer.api`). The test's docstring scopes itself honestly and does not overclaim, and I checked the wider property myself: **170 endpoints across all mounted routers, zero collisions.** So nothing is hidden today. Widening the walk to those five modules would cost about four lines and would make the property hold over the whole application rather than over one package — worth doing when the router is mounted.
2. **`relay` still defaults to `None` on `SupportMessageAnalyser`.** `_relay_to_channel_a` returns 0 silently when it is absent — the identical failure mode item B was raised to close for `omc`, and DR-3 makes the relay contractual. The live risk is closed: the factory always supplies it and C7 is caught by the composition test. But the argument in this phase's own docstring ("the failure mode of an optional port is that nobody notices it is absent") applies equally here, and a second wiring site would reintroduce it. Suggested for V3, which reuses these seams.
3. **Stale-value re-merge on out-of-order redelivery.** If event A (tracking `1Z-AAA`) is redelivered after event B corrected it to `1Z-BBB`, `_merge_bound_artifact` sees a difference and writes A's stale value back. This is S1's merge semantics, unchanged, pre-existing, and outside V2's ownership — and the mirror change does not amplify it (the redelivery re-derives the same key and enqueues nothing new). Recorded so it is not rediscovered as new.
4. **Concurrent-upsert race on `omc_command_records`.** Two simultaneous attempts on one key can surface a `DuplicateKeyError` from the unique index rather than a clean no-op; it is not caught. It propagates as a retryable failure and the redelivery converges, so the outcome is correct, but the operator surface will show an error where a no-op would be more truthful.
