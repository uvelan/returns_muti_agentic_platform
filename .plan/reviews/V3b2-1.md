## The trigger design, and the constraint it accepted

**Delegation is genuinely composition, not a fork.** Verified three ways:

1. **No V2 file was modified** — `git diff --name-only` matches nothing under `message_classification`, `ingress`, `analysis_wiring`, `relay.py` or `support_ingress`.
2. **The factory delegates**: `build_resolving_classify_dispatcher` calls V2's own `build_support_message_classify_dispatcher` and wraps the object it returns, rather than rebuilding it. It also returns `(topic, dispatcher)` in V2's shape, for V2's stated reason — a table keyed by the wrong constant is a queue nothing drains, and it fails silently.
3. **The dispatcher delegates at run time**: `dispatch()` opens with `result = await self._analysis.dispatch(command)` and finally `return result` — V2's answer is returned verbatim. The delegation is deliberately unguarded so that whatever V2 raises propagates with its own `error_code`, "because a resolver wrapper must not be able to relabel an analysis failure." That is the right call and it is stated as a decision rather than an omission.

**The retry reasoning holds when the ladder fails after classification is accepted**, which was the sharp version of the question. On a post-classification failure the dispatcher raises, and redelivery re-enters V2's dispatcher first — where the accepted stages are **reused, not re-invoked** (the property I verified in V2p1-1: `accept_result` returning `is_new=False` means the model is not called again) — and the ladder then resumes from its checkpoint. So a retry costs neither a second classification nor a restarted ladder.

Two details make that argument sound rather than merely plausible. Failures are **classified**: `ConnectionError`/`TimeoutError` become transient (a retry), and anything else becomes a permanent dead-letter carrying its **own** `RESOLUTION_FAILED` code rather than `SUPPORT_ANALYSIS_BLOCKED` — so a resolver bug does not retry forever pretending to be an outage, and an operator is not sent to inspect a stage that succeeded. And the resume is real rather than nominal because the checkpointer is mandatory; see below.

## Unserviceable rungs — the design decision, assessed

**The three places genuinely agree, and they agree because they read one source.** `deps.graph_rung_available` / `deps.tool_rung_available` drive (a) whether the node is added to the graph, (b) whether it appears in the conditional target map, and (c) what `compiled_rungs` reports; the routers read the same flags through `_next_rung_after_facts` / `_next_rung_after_graph`. That is not three consistent copies — it is one fact consulted three times, which is the difference between agreement and coincidence. The docstring's supporting argument is also correct: a target map naming a node that was never added is a LangGraph compile-time error and a router returning a name absent from the map is a runtime one, so deriving both from one flag is what stops them drifting.

**No path reaches a rung the config excludes.** I injected a router that names `route_tool` unconditionally: **11 failed**, including `test_a_facts_only_ladder_escalates_instead_of_entering_a_rung_it_lacks` and `test_a_graph_but_no_tool_deployment_stops_after_the_graph_rung`. The availability tests are named for the property and they bind.

**I endorse the decision.** The argument — *a `GraphReadPort` returning `{}` is worse than one that raises, because the model still answers confidently under the platform's name* — is exactly right, and it is the same principle §9's tool boundary states for missing entities (refuse, do not guess). A stubbed rung would have satisfied a shape check while producing the one output this ladder must never produce: a confident answer with nothing behind it. Absence is the honest encoding, and `compiled_rungs` is what turns absence into something an operator can *ask about* rather than infer.

The five stopped ports each carry a specific, checkable reason rather than "not implemented": `GraphSyncPort` (the coordinator needs schema/generation/digest/read-plan that `synchronize_for_case` does not supply), `GraphReadPort` (every available read is question-derived, which the port forbids), `TrustedEntityPort` (nothing maps fact names to entity names, and that mapping is what decides what fills a tool argument), `ToolExecutor.contracts` + `AuthorizationPort`, and `principal_id`. Those are descriptions of missing seams, not of missing effort, and the third one in particular is the correct reason to stop rather than improvise — inventing a fact-name-to-entity-name mapping is inventing what a tool argument is allowed to contain.

## The three gaps — all confirmed, all real

**(a) The two clarification activity bodies had no `@activity.defn` and no registration.** Both now carry the decorator and both are registered. More importantly the slice added the *general* guard, `test_every_activity_the_workflow_calls_is_registered_on_the_worker`, which is what found the third gap.

**(b) The command payload could not have deserialized into the signal it becomes.** Confirmed and pinned: removing `"signal_id"` from the payload fails `TestTheSignalBodyIsTheNoticeTheWorkflowDeclares::test_the_stored_payload_constructs_the_notice`. The test constructs the notice from the **stored payload**, which is the right boundary — the same construction V1 phase 2 needed for `TemplateReviewNotice`, and for the same reason: this is the seam where a green endpoint and a green workflow can still fail to meet.

**(c) `case_has_return_details` registered on no worker — pre-existing, and I confirm it.** `_await_return_details` calls it, no worker polled for it, and an unregistered activity in Temporal raises nothing and logs nothing: the execution schedules the task and waits. Reached only when `timings.return_details_required` is on, which is what kept it unnoticed. Un-registering it again fails the general guard, so the fix is pinned.

**On severity and scope, since you asked.** Severity is high for any deployment with that flag on — a silent indefinite stall with no error, no log, and no operator signal, which is the worst shape a defect can take. But it is latent, gated behind a released flag.

**Registering it here was right, and a separate dispatch would have been worse.** The slice built the general guard because it needed to prove its *own* two new activities were registered; the guard then immediately surfaced this one. Deferring the fix would have meant either merging a knowingly-red test or suppressing it — both worse than a one-line addition in a file the slice already had to modify. The change is also inert in the failure direction: registering an activity nobody calls costs nothing, and registering one that *is* called removes a stall. Rule 11 is about editing outside a declared set to make things compile; this is the opposite — a guard the slice built found a defect in a file already in scope, and the fix is the guard's own remedy. Flagging it in the ledger and commenting the reason at the site is the correct handling.

## The two contract questions — my reading

### §7's topic enumeration — respected, not evaded

**Confirmed.** The topic set is unchanged; no fifth topic exists; V2's dispatcher is built by V2's factory and its result returned verbatim; V2's files are untouched. The resolver is a strict continuation *after* V2's dispatch returns, on the command that already exists.

I want to record that this is the right reading of AMENDMENT-1's precedent and not merely a permissible one. AMENDMENT-1 established that a frozen enumeration cannot be widened by an implementation — and the honest consequence of that rule is that a slice which *needs* a new topic must return to the orchestrator, while a slice that can achieve its aim **within** the enumeration should. This one could, and the reason it could is substantive rather than clever: the classify command is the only place the committed classification exists, so the resolver genuinely belongs there rather than at a topic that would have to re-derive it. A fifth topic would have been the easier implementation and the worse contract.

### §9's ladder, and acceptance item 10 — an honest posture, and a T0 gap to record

**My reading: §9 does not require the tool rung to be serviceable, and this slice has not violated it.** §9 specifies the ladder's *shape* ("case facts → graph → registered tools → associate clarification"), the *rules* that apply when a tool is used ("execution requires schema validation + authorization; missing required entities → refuse"), and a **released, config-driven** binding list. An empty `tool_bindings[]` is a legitimate release state — the shipped `production.yaml` says so in as many words — and nothing in §9 obliges every deployment to make every rung reachable. Given that, absence is more faithful to §9 than a stub would be, because §9's own tool boundary is built on refusing rather than guessing.

**But acceptance item 10 is a different artefact from §9, and it is genuinely unreachable as shipped.** "Support asks a question requiring a tool → agent resolves via the registry, credentials never surfaced" cannot be observed with no bindings, no `TrustedEntityPort`, and no tool node in the compiled graph. That is a fact about the acceptance list, not a defect in this branch.

**My recommendation, in three parts:**

1. **Defer item 10, with the reason recorded** — the deployment cannot serve the rung, and the work to make it serviceable (a fact-name-to-entity-name mapping, a question-independent case-scoped graph read, a capability adapter with contracts and authorization) is substantial and was correctly not invented under time pressure. Inventing an entity mapping to make an acceptance item pass would be the worst possible reason to decide what a tool argument may contain.
2. **Make the deferral checkable rather than silent.** ACC should assert the unreachability rather than skip the item: a test that reads `compiled_rungs` for the released configuration and pins that the tool rung is absent, with the released `tool_bindings: []` beside it. That converts a deferred acceptance item into a recorded, verified fact — which is exactly what this slice's three-places-agree design makes possible, and it is the difference between "we didn't test it" and "we tested that it is off."
3. **Record it as a T0 gap.** The acceptance list named an observable that requires adapters the contract never specified anyone would build. That is the same class as AMENDMENT-3 (a frozen path already taken), AMENDMENT-4 (a named transaction that did not exist), and AMENDMENT-6 (a DTO field the seam could not fill) — **the fourth of its kind, and again found by someone trying to use the thing rather than read it.** Whether it warrants an eighth amendment is your call; my view is that the acceptance list, like §9, is a frozen artefact and item 10 cannot be quietly reinterpreted at gate time.

I am deliberately **not** treating this as a finding against the slice. It raised the question without adapting anything, which is what the charter asks for, and it built the mechanism that makes the honest answer observable.
