## Data not markup, without breaking verbatim — the sharpest requirement

**Both directions verified, and I did not rely on the slice's fixtures.**

**Structural.** No `dangerouslySetInnerHTML`, no markdown renderer, no `innerHTML`,
`outerHTML`, `eval` or `new Function` anywhere in V3's surface — the only `innerHTML` in
the diff is a test's `document.body.innerHTML = ""` cleanup. All three attacker-influenced
values (`verbatimQuestion`, `artifactValue`, `evidenceSpan`) reach the DOM as plain React
text children.

**Their injection, reproduced precisely.** A well-meaning "safety" pass in
`clarificationModel.text()` — strip `<>`, rewrite `:` — fails **exactly 2 tests**, and
exactly the two claimed:

```
× renders a script tag, an img onerror and an iframe as text in all three fields
× leaves ten realistic support sentences byte for byte identical
```

I then injected **colon rewriting alone**, leaving markup untouched, to test whether the
equality half is doing independent work. Both tests still fail — because the markup test
is itself written as an equality (`textContent` pinned) *and* an absence
(`querySelector(...)` null) in the same test, with the reasoning stated in place:

> *"Either assertion alone passes for the wrong reason — the absence one passes on a field
> that never rendered, and the presence one passes on a field that rendered and executed."*

That is the correct construction, and it makes the slice's central claim true: **every
negative assertion would have passed a console quietly rewriting a supplier's words.** The
ten-sentence list is the right list — colons, RMAs, bays, bare numbers, mixed quotes — the
same shapes I probed V3's backend neutraliser with in round 2.

**My own independent probe**, with vectors deliberately different from theirs
(`<svg onload>`, `<style>`, `javascript:` href, a quote-breaking `"><script>`,
`<template>`) and my own ordinary sentences: every vector renders as literal text with
**no element created** for any of `svg`, `style`, `a`, `script`, `template`, `b`; every
ordinary sentence survives byte for byte through the model. Both directions hold on
inputs the slice never saw.

**On the one concession** — the question is not `whitespace-pre-wrap`. I accept the
argument: the DOM text is byte-identical either way, so a screen reader is unaffected, and
the only thing lost is a hostile newline's ability to restructure the visual block. That
is a rendering choice that does not touch the text, which is the right side of the line
§9 draws.

## The three cross-slice findings — adjudicated

### 1. `CasePanelView.clarifications[]` undeliverable → **AMENDMENT-6 checks out; retiring is right**

You asked me to check the amendment against the code as I did with AMENDMENT-4. I did,
and it holds on all three grounds:

- **The seam genuinely cannot fill it.** `api/case_panel.py` sets `support_digest=()`,
  `clarifications=()` and `parked_messages=0` as literals, with V1's comment stating the
  intent correctly and describing a connection that does not exist. A registered
  contributor returns `PanelSectionView | None` into the sections list; there is no path
  from a contributor to a top-level DTO field.
- **Retiring breaks nothing.** No backend module outside the DTO and its composer reads
  any of the three. On the console, **nothing reads `support_digest` or
  `parked_messages` at all**, and the only reader of `clarifications` is V3's own bridge.
  V1 phase 2 and V2's in-flight frontend are unaffected — I checked V2's branch directly.
- **Extending the registry would be the duplication this run keeps finding.** Your
  reasoning is right: the registry already works, and both V2's and V3's sections go
  through it.

One consequence worth naming, and it is a *good* one: V3's `readClarifications` spreads
`...panel.clarifications` directly, with no cast and no optional chaining. When the
retirement lands and the generated type loses the field, that line **fails typecheck** —
the bridge self-destructs loudly, at the right place, rather than silently going empty.
Sequence the retirement and V3's one-line simplification together and nothing is ever
red for longer than one commit.

### 2. The fabrication guard only inspects `??` — **upheld, and I reproduced it**

`ReturnCopilotFabrication.test.ts:153-169` is a line regex over `\?\?\s*"…"`. A ternary is
invisible to it. Demonstrated with the same fabricated string in both forms, appended to a
V3 production file:

| Construction | Guard result |
| --- | --- |
| `v ?? "Delivered on time"` | **1 failed** — caught |
| `v === null ? "Delivered on time" : v` | **35 passed** — invisible |

V3's card had four ternaries, so this is not theoretical for this branch. Not V3's to fix
(the file is V1's, rule 11), and V3 correctly reported it. **Orchestrator action:** dispatch
the guard extension to V1, with this injection as the acceptance test. Note the guard is
not broken within its stated reach — it caught this slice twice — the reach is just
narrower than the guard's name implies.

### 3. `/template-review/redraft` offered on reply reviews — **advisory, not blocking**

The backend is kind-agnostic so it works; the cost is a log reader seeing a
template-review URL for a reply. Cosmetic and correctly reported. Worth a rename when

## Merge precondition — the tripwire is now armed by trunk

`caseClarifications.contract.test.ts` fires when the answer route reaches the **committed
OpenAPI document**. I checked both sides precisely:

| | `/api/v1/cases/{case_id}/clarifications/{clarification_id}/answer` in `paths` |
| --- | --- |
| V3f head `a2751a1` | **absent** — tripwire green, which is why the branch is green |
| trunk `HEAD` (after `13d70dd`) | **present** — tripwire fires |

**As a design, it is good, and I want to say so plainly.** It is not a bare
`expect(false)`: it keys on the artifact the frontend actually consumes — so it fires
exactly when the frontend can act, not when the router happens to be mounted — and its
failure message is a three-step runbook ending *"delete this test"*. Nobody who hits it
has to reverse-engineer the intent. The hand-written types it guards are a declared
temporary, and this is what stops them becoming permanent.

**But it is now a guaranteed red at merge, caused by an event outside V3's control, and it
will be misattributed.** Whoever runs CI after the merge sees V3's frontend commit
adjacent to the failure, not `13d70dd`. And the three steps — import the generated types,
fold `caseClarificationHandlers` into `casePanelHandlers`' ROUTES table, regenerate —
include a regeneration that §3 assigns to the integration agent, so the person who hits it
may not be the person who can act.

**Condition on merge (yours, not the slice's):** dispatch the three steps to land in the
same merge window as this branch. Not "soon" — a red suite with no owner is how a real
failure gets normalised. This is not a finding: the slice could not have done it, since
the branch was cut before the mount landed, and it wrote the runbook precisely so the
handover would be cheap.

## V2 / V3 overlap — no section collision, three shared files

- **No section-id or order collision.** V3 registers `clarifications` at `order: 30`;
  V2's frontend branch registers no section yet.
- **No token collision.** V3 adds `review.clarification` inside V1's `review` block; V2
  adds a separate `support:` namespace, with its own comment reasoning that *"two
  registries are two registries."* The two are compatible by construction.
- **One real hazard, and it is worth naming.** Both branches edit
  `mocks/handlers/casePanelHandlers.ts` at the **same line**: V3 replaces `sections: []`
  with its clarifications fixture, V2 replaces it with `sections: [...supportPanelSections()]`.
  Neither composes with the other, so a careless merge resolution silently drops one
  slice's section from `dev:mock` while both suites stay green — the silent-loss shape.
  Dev-only and not production, but it should be an explicit instruction to whoever merges
  second: **compose the two arrays, do not take one side.** `mocks/handlers.ts` and
  `copilotTokens.ts` also overlap, but both are appends and conflict textually at worst.
