### F1a (the sixth divergence, assessed as security per the dispatch) — WITHDRAWN, and the fix fully closes it.

`compose_support_handoff` neutralises person-typed text with `_safe()`, whose `_FRAMING` regex replaces a line matching a section header (`^[A-Z][A-Z /_-]{2,}:`) or a rule (`-{3,}`, `={3,}`) with `[removed]`. Binding the raw `associate_notes` fact dropped that, so a note containing `BAY ASSIGNMENT:` reached Channel B intact and could restructure the message for whoever read it next. That is rule 9 territory — structure injection into an agent-authored outbound message — and I agree with the slice's own classification of it as the most serious thing the matrix found.

**The fix closes it.** The template now binds `case_fact:associate_notes_rendered`, produced by `support_template_snapshot` as `_safe(return_details.associate_notes)` — the composed path's own helper, imported rather than re-implemented, which is what makes a second spelling impossible. It is covered from both ends: `test_associate_notes_are_neutralised_before_they_reach_the_template` asserts `BAY ASSIGNMENT:` is gone and `[removed]` is present, and the matrix carries `associate_notes_impersonating_the_framing` as a full text-equality scenario. My injection above confirms the guard is load-bearing.

**The independent judgement you asked for — does any *other* shipped binding reach raw associate- or support-authored text without neutralisation? No.** I enumerated every binding in the shipped yaml (37 total: 34 `case_fact:`, 3 distinct `literal:` action lines; **no** `return_record:` or `graph:` in the default variant) and cross-checked each against the composed path's treatment. `compose_support_handoff` applies `_safe` to exactly four values — `associate_notes` and the three `contact_*` fields — and `_clean` to everything else. `support_template_snapshot` applies `_safe` to exactly the same four. **Parity is exact**, and it is exact because the snapshot borrows the helpers rather than reproducing them. Nothing the template binds is less neutralised than what composition emits for the same value.

See A-new below for the one residual I want on the retirement follow-up — it is pre-existing in composition, identical in both paths, and therefore not a V1 regression.

### F4 — WITHDRAWN. `return_record:` reaches the projection's declared surface and nothing else, and a bypass degrades to a gap.

The allowlist is derived from `ReturnRecordProjection.model_fields` behind `@lru_cache(maxsize=1)`, never hand-listed — so it cannot drift from the projection it describes. **I verified the deferred import is a genuine cycle, not a style preference**: the projection package pulls the agent registry, which imports `return_configuration`, which imports this module. Deferring is the correct resolution and the docstring says so plainly.

Enforcement is at three depths, and I confirmed the load-bearing one is the release gate:
1. **Release validation** — `TemplateFieldConfiguration.validate_field` calls `binding_source` on *every* field, and `binding_source` refuses an undeclared `return_record:` attribute. This is AMENDMENT-2's actual requirement and it is tested directly (`return_record:__class__`, `return_record:active_shipments`, `return_record:no_such_attribute` all refused; `record_attributes() == frozenset(ReturnRecordProjection.model_fields)` pinned).
2. **Render-time** — `_record_attribute` re-checks and returns `None` for an undeclared name, which the caller turns into an ordinary binding failure.
3. **The formatter** — refuses a non-scalar value.

**Confirmed a bypass degrades rather than rendering a repr.** I built a template past validation via `model_copy` with `return_record:__class__` and rendered it against a record passed as an **object** (the `getattr` branch round 1 quoted, which the branch's own test does not reach — its record is a `dict`, and `dict.get("__class__")` is `None` regardless). Result: `'Record:\n'` — no repr, no exception. I then removed the render-time guard and re-ran: **still** `'Record:\n'`, because the formatter refuses the class object. So the vulnerability is closed at the gate that matters and holds even with the second layer stripped. Recorded as an observation below, not a finding, since no layer that actually stops the leak is unpinned.

## The no-fallback decision — contract-faithful, not an evasion

I judged this from the contract text, not from the slice's argument.

**The premise checks out.** §8's clause grammar is exactly five clauses — `shipping_modes[]`, `return_reason_classes[]`, `order_sources[]`, `min_item_count`, `max_item_count` — and I confirmed the implementation carries these and only these. Every one describes the *shape of a case*. None can express "the bay was not recommended", "the case state could not be read", "this case carries additional required details", or "no associate was named". The four conditionals genuinely are inexpressible; this is not a shortcut around a rule that could have been followed.

**Given that, no-fallback is the only faithful option, and the alternatives are both worse.** Marking the fields `required` would raise a review-blocking gap on every ordinary case — a case with a recommended bay is not a broken case. Giving them a `fallback` prints "Not available" where the truth is "no bay could be recommended, resolve manually", which is F1 itself. Producer-omits-key / renderer-omits-line reproduces exactly what the composed path does, and §8's own construction supports it: `fallback` applies "only after the declared binding fails", gaps come only from *missing required*, and a non-required field with nothing to show simply does not render.

**It does not evade the gap mechanism, and the matrix proves that in both directions.** `test_no_scenario_reports_a_gap_it_should_not` asserts no ordinary case gaps; `test_a_missing_case_id_is_still_a_gap` asserts the one genuinely required field still does. A design that had quietly disabled gapping would fail the second. The gap mechanism is intact and correctly scoped to the one field whose absence really is a broken draft.

The honest cost — that the *absence* of a key is now load-bearing signal — is stated in the module docstring rather than buried ("**the absence is the signal**"), and it is what the drift tests exist to protect.
