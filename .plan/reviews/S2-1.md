## Findings

### F1 (BLOCKING) — the legitimate-wait skip strands the workflow link and starves the recovery queue

- **File:** `backend/src/return_platform/workflows/return_case_recovery.py`
- **Lines:** 231–240 (the `_is_legitimate_wait` skip in `ReturnCaseWorkflowRecovery.recover_once`), with `LEGITIMATE_WAIT_STATUSES` at 152–163.
- **Rules violated:** charter standard dimensions (correctness/edge cases — a queue that no longer drains); rule 4 adjacent (a repair path that is no longer check-then-act complete).
- **The orchestrator's question — was the older sweep load-bearing there?** **Yes**, and the branch's premise for the change is half right. It is right that a relaunch is wrong here. It is wrong that skipping is therefore safe, because relaunching was never the only thing that pass did.
- **What the sweep also did:** `ReturnCaseWorkflowRecovery` calls `ensure_case_workflow`, which on an already-running execution adopts it (`WorkflowAlreadyStartedError`) and then **re-writes `cases.workflowId`**. That link write is deliberately allowed to fail at launch — `return_case_launcher.py:224-232` swallows it with a warning — and the launcher's own module docstring (`return_case_launcher.py:19-25`) names this sweep as the designated repair: *"A failed link therefore leaves a fully reachable case, which is why it is logged rather than raised: the case has its workflow, and the recovery sweep re-writes the link on its next pass."* This branch falsifies that sentence for three statuses without amending it. The branch's own test pins the loss: `test_case_recovery_review_waits.py:170-171` asserts `launcher.calls == []`.
- **The consequence, and it is worse than a stale field.** `CaseRepository.list_cases_without_workflow` (`case_repository.py:284-312`) selects `workflowId: None`, sorts `createdAt` **ascending**, and applies `limit`. A case skipped for a legitimate wait never gets its link written, so it **never leaves that queue** — and being old, it sits at the head of every subsequent batch. Once as many such cases accumulate as `batch_size`, the batch is entirely skipped cases and genuinely unlaunched cases are never reached. The sweep is silently, permanently disabled.
- **Confirmed by RV, fault injection** (probe against the branch's own doubles plus the shipped query's shape — oldest-first, `limit=100`): 100 legitimate-wait cases holding null links, plus one genuinely never-launched case. Over five passes: `launcher.calls == []`, the unlaunched case **never recovered**, queue length unchanged at 101. Not a slow drain — no drain at all, and the launcher is not called even once.
- **Why the accumulation is certain rather than unlucky:** it is monotonic. Nothing removes a skipped case from the queue, so the residue only ever grows over a deployment's life. The threshold is reached as a matter of time, not of chance. And the change extends to `AWAITING_SUPPORT` and `AWAITING_POLICY_REVIEW` — two **pre-existing** statuses that cases reach within minutes of launch, well inside the 120s grace, so an early link failure lands a case in the trap almost immediately.
- **No functional strand, to be precise:** the case itself stays reachable, because nothing derives the workflow id from the stored link (`return_support.py` and the rest compute it from the case id via `return_case_workflow_id`). The damage is the permanently clogged repair queue and the operator surface that never empties — not an unreachable case. V1 must likewise derive the workflow id rather than read `cases.workflowId`, which is now sometimes permanently null.
- **Fix:** keep the refusal to relaunch, drop the refusal to repair. A case in one of these statuses demonstrably has a running execution (only the workflow writes those statuses), so the sweep should write the link — either by calling `ensure_case_workflow` (idempotent; adopts the live execution rather than restarting it) or by a direct `bind_case_workflow`, and skipping only the relaunch. Excluding these statuses inside `list_cases_without_workflow` would also stop the starvation, but leaves the link unrepaired and the launcher docstring still false, so it is the weaker fix.

### F2 (BLOCKING) — `ensure_case_support_thread.created` is decided by a non-atomic pre-read, and its docstring claims the opposite

- **File:** `backend/src/return_platform/operations/return_support/service.py`
- **Lines:** 838 (`already = await self._work_items.find_one({"caseId": case_id})`) and 855 (`created=already is None`), against the docstring claim at 851–854.
- **Rules violated:** rule 4 (broken idempotency — a caller-visible "did I create this?" answer that is not check-then-act); rule 10 (the branch's own race test stops one assertion short of catching it).
- **What the code claims:** *"`created` is not a formality. It is how a caller distinguishes 'I started this conversation' from 'I joined one already in progress', which is the difference between an opening request and a reply, and **it can only be known by whoever won the insert**."*
- **What the code does:** reads the work-item collection *before* delegating to `open_case_thread`, and reports `created` from that read. The read is not the insert. `open_case_thread` genuinely does know who won — its loser re-reads the winner's thread — and that knowledge is discarded rather than returned.
- **Confirmed by RV, fault injection using the branch's own race construction** (blinding the two `caseId` pre-checks exactly as `test_case_thread_delivery.py::test_the_race_between_two_creators_leaves_one_thread` does): winner `created=True`, **loser `created=True`**, one thread, one work item. The loser opened nothing and says it opened the conversation.
- **Why the branch's test does not catch it:** that test asserts `loser.workItemId == winner.workItemId`, `loser.threadId == winner.threadId` and `len(work_items.documents) == 1` — everything except `loser.created is False`. The one field the race can corrupt is the one field left unasserted.
- **Why it matters:** by the docstring's own account, `created` selects between composing an opening request and composing a reply. Two workers replaying the same send — the exact scenario the delivery identity exists for — would both compose an opening request. That is a duplicate opening message to Support, which is the failure class this whole spine exists to prevent, arriving through the one field not covered by the delivery identity. It is also a **frozen S2 interface** (§10): V1 consumes it and may not change it, so a latent trap here is one V1 cannot fix.
- **Fix:** return the creator from `open_case_thread` (it already distinguishes the winner internally) and derive `created` from that, not from the pre-read. Add `assert loser.created is False` to the existing race test.

### F3 — the conflict marker is bumped and cleared outside the transaction the contract puts it in, and a torn pair is unrecoverable

- **File:** `backend/src/return_platform/operations/review_aggregate.py`
- **Lines:** 578 (`await self._bump_conflict_marker(...)` after `resolve_canonical_edit`'s `find_one_and_update`), and 502–508 (the same shape in `_after_edit_written`).
- **Rule violated:** rule 5 (durable state that can disagree with itself) and contracts §6, which specifies the marker is *"bumped on conflict appearance, **cleared by the canonical-edit write**"* — one write, not a write followed by another.
- **What happens:** both are two independent writes with no session. `resolve_canonical_edit` sets `conflictPresent: False` on the review and *then* clears `reviews.{review_id}` on the case-scoped marker; `_after_edit_written` sets `conflictPresent: True` and *then* sets the marker. A failure between the two legs leaves the pair permanently disagreeing, in either direction:
  - **Clear torn:** the review says no conflict, the marker says conflict. `conflict_marker()` reads the stored flags rather than recomputing from the edit rows, so nothing ever repairs it. The panel shows a conflict indefinitely, the associate is told to resolve a conflict that no longer exists, and resolving again is a no-op because the review is already clean.
  - **Set torn:** the marker says no conflict, but `approve()` reads `review["conflictPresent"]` and refuses with `ReviewConflictError`. The panel shows nothing wrong and approval 409s with no visible cause.
- **Why it is a finding and not a nit:** the fields are in the same Mongo database as everything else the file transacts, and this file demonstrably knows how — `approve()` and `retry_delivery()` both wrap their multi-collection writes in `with_transaction`. The marker pair is the one place a multi-collection invariant was left unwrapped, and it is the pair the contract explicitly describes as a single write.
- **Fix:** wrap each pair in `with_transaction` and pass the session through, as `approve()` does. Alternatively derive `present` in `conflict_marker()` from the reviews' own `conflictPresent` flags so the marker is a cache that cannot outlive the truth — but the transaction is the smaller change and matches the contract's wording.

## Verified and not contested

**Item 1 — the atomic `OPEN → APPROVING` transition is genuinely atomic.** `approve()` (`review_aggregate.py:593-745`) runs one `with_transaction` whose body: plans the command (allocating the `review_commands` stream sequence through the same session), CAS-locks the review with the full guard predicate in the filter — `state: OPEN`, `pendingRevision: False`, `conflictPresent: False`, and both expected versions — sets the frozen `approvedPayload`, `canonicalApprovedPayloadHash`, `logicalOperationId`, `deliveryId` and `contentHash`, and only then calls `insert_planned` **inside the same session**. The pre-checks (state, pending revision, conflict, `draft_version`, `canonical_edit_version`, payload hash) are all present and all re-asserted in the lock filter, so a read-to-lock race is caught rather than trusted. The three stores are genuinely co-located: `_reviews`, `_edits`, `_conflicts` and the command store's `_commands`/`_outbox` all resolve from `client[settings.mongo_database]`.
- **Both failure directions verified by RV.** Lock-loses is covered by the branch (`test_a_failed_approval_leaves_neither_command_nor_outbox_row`). The other direction I probed directly: forcing the **outbox insert** to raise mid-approval leaves review state `OPEN`, 0 command records, 0 outbox rows — the transaction aborts as one thing. The approval-race defect the state machine exists to fix is closed.
- **Coverage advisory:** only the lock-loses direction is pinned by a test. A future edit that moved the command/outbox insert back outside the transaction — precisely the bug of item 2 — would leave the review stuck in `APPROVING` with no command ever dispatched, and the suite would stay green. I injected that shape and `test_review_aggregate.py` passed 38/38. Worth one test; not a finding, since the shipped behaviour is correct.

**Item 2 — the resumed-session bug is genuinely fixed, and nothing of its shape survives.** The pair-write now lives in `DurableCaseCommandStore.insert_planned` (`case_commands.py:388-400`), which owns both collection names; the aggregate calls it with the session and never names a collection. RV greps across the whole diff: **no** accidental-truthy subscript (`grep -E '^\+.*\[[^]]* and '` → none), **no** raw collection-name string outside the module constants (`CASE_COMMAND_RECORDS`, `_INTEGRATION_OUTBOX`, `CASE_REVIEWS`, `REVIEW_DRAFT_EDITS`, `CASE_REVIEW_CONFLICTS`, `INTEGRATION_OUTBOX_COLLECTION`, `CASE_STREAM_SEQUENCES_COLLECTION`, the analysis constant). The `_INTEGRATION_OUTBOX` duplication carries the same recorded cycle rationale `support_events.py` already uses.

**Item 3 — the `AWAITING_TEMPLATE_REVIEW` mapping is contract-correct, not drift; the OpenAPI regen is in scope.** Contracts §6 declares the **persisted** status and its recovery semantics, both of which are delivered. It says nothing about `ReturnCaseStatus`, which is the frozen *external* vocabulary; growing that enum would have been the drift. Mapping onto the existing `AWAITING_SUPPORT` is also forced rather than convenient — `read_persisted_status` raises `UnmappedCaseStatusError` by design rather than defaulting, so an unmapped status would make recovery raise on the first case V1's gate parks. The evidence that the mapping does what it claims is in the OpenAPI diff itself: the new status appears **nowhere** in it. The only regen is one additive enum member, `RecoveryAction.OPERATIONS_REQUIRED`, a mechanical consequence of an exported enum growing, mirrored across the repo's four export copies. In scope and minimal.

**Item 5 — the `ContextPolicy` protocol is an honest structural dependency, not an evasion.** `assemble_case_context` is a pure function over facts and a policy; it genuinely does not need to know that policies come from a configuration release, and the protocol names exactly the four attributes it reads. The docstring makes the right argument — the layering rule "is right independently of the test that enforces it". `ContextAssemblyConfiguration` satisfies it structurally and is wired through `return_configuration.py` plus a `production.yaml` block that restates the code defaults. An import would have been the evasion; this is the shape the rule exists to produce.

**Item 6 — purity and determinism hold, and the estimator is honestly scoped.** No time, randomness, IO or mutable module state in `case_context.py`. Canonical order `(recordedAt, factId)` applied twice (input sort and post-projection sort), scoped-latest projection per `(record_scope, factName)`, `json.dumps(sort_keys=True, separators=(",",":"))` for every hashed byte, and `content_hash` taken over the finished payload. Pinned names are reserved before the budget is spent and are never trimmed. The persisted summary is read and never generated — which is what makes the determinism claim true rather than aspirational. `_wordpiece_approx_v1` is named, documented and versioned as an **estimate** (4 chars/token), with `UnknownTokenizerError` refusing an unpinned version rather than falling back — "a pin whose unknown values silently fall back is not a pin". Replacing it with a real tokenizer requires a new version string, so no already-assembled context is silently re-measured. Honestly scoped.

**Item 7 — the command horizon degrades honestly.** With no `command_horizon` port wired, `_stale_commands` is simply not asked and the outcome is `RELAUNCHED` — the truthful description of what happened. It does not report a check it did not perform, and it does not invent a safe-looking outcome. Pinned by `test_without_a_horizon_port_the_question_is_simply_not_asked`. **Advisory:** V1 must pass `command_horizon=` when it wires the review endpoints, or the rule stays unarmed in production; the honest `RELAUNCHED` is correct behaviour but is not the protection §7 describes.

**Item 8 — idempotency surfaces, fault-injected rather than read.**
- **Frozen CAS key** `(case_id, review_id, draft_version, canonical_edit_version)`: the partial unique index is declared correctly (`$type` guards on all three, so pre-existing commands with null review fields do not collide). RV neutered the index's partial filter; `test_a_second_approval_of_the_same_frozen_versions_is_a_409` and `test_a_stale_version_pair_is_a_cas_conflict` both went red. The guard is real and the tests catch its loss. `plan_command` additionally refuses half a key.
- **Signal dedupe** on unique `(caseId, signalId)`, with `classify_duplicate` distinguishing the three cases in the right order — same signal same digest → idempotent receipt; same signal different digest → `CommandIdempotencyConflictError`; different signal occupying the frozen slot → `StaleReviewVersionError` (409); neither → re-raise rather than report success for a write that did not happen.
- **Delivery identity chain**: `logical_operation_id` derived from the approving command id, `delivery_id` minted **once** at approval and stored, `content_hash` audit-only. `retry_delivery` reads all three from the stored review and puts them in the retry payload verbatim — it cannot mint a second identity. The receiver-dedupe index on `businessPayload.deliveryId` is unique and partial on `$type: string` (correctly, or every delivery-id-less message would index as null and collide).
- **`ensure_case_support_thread`** reuses `open_case_thread`'s unique-on-`caseId` loser-re-reads path rather than writing a second opener — correct, and the reason F2 is a reporting defect and not a duplicate-thread defect.
- **Per-stream `(case_id, stream, sequence)`**: allocated by server-side `$inc` on an upserted counter inside the enqueuing session, backed by a second unique index on the outbox. Aborted enqueues leave gaps, never duplicates — and gaps are harmless because ordering is by predecessors, not by sequence. Predecessor validation refuses unknown ids at enqueue (`UnknownPredecessorError`) and self-reference (`PredecessorCycleError`); with existence required and predecessor lists immutable, self-reference is indeed the only expressible cycle, and the reasoning is stated rather than assumed. Parentless commands dispatch immediately. A missing predecessor at dispatch defers rather than guessing.
- **`SupportAnalysisRecordStore`**: one record per `support_event_id` on a unique index with `DuplicateKeyError` → re-read. `pin_routing_decision` is idempotent **by keeping the first pin**, not by overwriting — so a re-pin under a newer policy version cannot retroactively change what the recorded attempts were attempts at, and the caller gets the decision it must route by rather than the one it proposed. `accept_result` CASes on `field: None` and returns `is_new=False` both when a result was already accepted and when a concurrent acceptance won — in both cases returning *the stored result*, so "do not invoke again" is what the caller is actually handed. A provider fallback therefore cannot mint a second classification identity. `require_accepted_extraction` is a function returning the accepted extraction, so a caller cannot take the gate without using its result.

**Item 9 — `absorbed=True` is success.** `post_support_message` returns `SupportMessagePost(absorbed=True)` on both the pre-read hit and the `DuplicateKeyError` loser path, carrying the winner's `messageId`/`sequence`; nothing raises and nothing signals failure. `mark_sent` is a plain `APPROVING → SENT` transition with no absorption condition, so an absorbed retry still reaches `SENT`. The two-check design (read first for the expected retry, index second for the concurrent writer) is correct and both checks are load-bearing. The sequence-gap trade-off is stated explicitly and is the right way round.

New imports of frozen modules (`operations/associate_flow`, `agents/order_discovery`, `api/associate_returns`, `api/return_agents`) — none. Command records server-stamp `actorId` (`case_commands.py:307`, commented as such). `abandon` audits actor, reason and timestamp per §6.
