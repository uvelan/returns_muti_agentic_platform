- **AMENDMENT-3 (2026-08-30, raised by the integration agent while mounting the V2 router).** The NL ingress endpoint moves from `POST /api/v1/return-support/work-items/{work_item_id}/messages` to **`POST /api/v1/return-support/work-items/{work_item_id}/inbound-messages`**. *Why:* the frozen path was **already taken** by `return_support.add_message` — a live associate-facing endpoint (201, `CreateSupportMessageRequest`, `require_return_collaboration_roles`) — which T0 froze without checking whether it was free. - **AMENDMENT-4 (2026-08-31, raised by V2 phase 1b while building the omc adapter).** §5's claim that the omc mirror row is "**enqueued in the artifact-persistence transaction**" is replaced by: *the mirror is convergently idempotent in a crash-safe order — merge → mirror row → outbox row, each a no-op on repeat — and is guaranteed to complete by the classify command's at-least-once redelivery.* **Eventually once, not atomically once.** *Why:* there is no artifact-persistence transaction to enlist in. S1's `persist_binding_decision` takes no session, neither of its ports has one to thread through, and the merge is an optimistic version CAS rather than a transactional write. - **AMENDMENT-5 (2026-08-31, raised by V1 phase 2 and sharpened by RV in review V1p2-1 finding F2 — the orchestrator's ruling on the escalated recovery-ownership question).** §6's review state machine gains **two rules**, because the recovery transition it already declares is unreachable in practice and, worse, builds a trap:
  1. **Delivery belongs to the workflow, never the endpoint.** §7 puts every send on one receiver-deduped path with one `delivery_id` per approved review; giving the recovery endpoint its own send would create the second sender that design exists to prevent, and §6's "a retry absorbed by receiver dedupe still reaches `SENT`" presumes the party observing the outcome is the party transitioning to `SENT`. **`DELIVERY_FAILED → APPROVING` therefore requires the workflow execution to still hold the review**; a retry arriving when it does not is refused (409) naming the legal action, rather than succeeding into an execution that will discard the notice.
  2. **The gate, on closing, moves every non-terminal review to `HELD_FOR_OPERATIONS`.** *Why:* rule 1 alone leaves an operator with only a refusal. This leaves a legal action instead, and — the load-bearing part — guarantees **no review is ever in a state with no legal exit**.
  *The defect being fixed:* `retry_review_delivery` had no liveness guard, so it always succeeded — S2 CASes `DELIVERY_FAILED → APPROVING`, the workflow discards the notice, and `APPROVING`'s only three exits (`SENT`, `DELIVERY_FAILED`, `HELD_FOR_OPERATIONS`) are all workflow-driven with no API caller, while `abandon` is refused from `APPROVING`. The review is permanently stranded, **and the operator's own recovery action is what builds the trap.** RV's judgement stands independent of this ruling: no reading of §6 permits a state with no legal exit. **T0 error** — the state machine I specified declared a transition without checking anything could reach it.

## 6. Review aggregate (S2 substrate, V1/V3 surface)

- **Unit:** support request. `support_gate.request_grouping` declarative rule enum `one_per_case | by_shipping_mode | by_ship_from` (default `one_per_case`). One review + one outbound payload per request; per-record sections retain `return_record_id` + own snapshot mapping. One case-level support thread; artifacts bind to records.
- **`review_id`:** opaque per-attempt id scoped `(case_id, request_id)`; `redraft` mints a new attempt under the same scope. `review_kind = TEMPLATE | SUPPORT_REPLY`, both on the aggregate with full guarantees; gap/variant rules TEMPLATE-only. Reply-review `scope_id` minted server-side by the gating transition.
- **State machine:** `OPEN → APPROVING → SENT`; `APPROVING → DELIVERY_FAILED | HELD_FOR_OPERATIONS`; `OPEN → CANCELLED`; `DELIVERY_FAILED → APPROVING` (authorized retry, same delivery identity) `| ABANDONED`; `HELD_FOR_OPERATIONS → OPEN` (blocking condition cleared) `| ABANDONED`. `ABANDONED` is terminal, audited (actor, reason, timestamp), panel-visible. `actor=SYSTEM` is reserved and non-assignable.
- **Edit model:** `draft_version` / `edit_version` / `base_draft_version` / `client_edit_id`; mutable draft-edit store one row per `(review_id, actor_id)`, coalesced autosaves (not facts); canonical edit `{canonical_edit_version, canonical_payload, resolved_from_actor_edit_ids[], resolved_by, resolved_at}` — sole-actor submits auto-promote; conflicts must be resolved (select/merge/discard) to a canonical edit before approval. Conflict-presence marker (case-scoped, versioned) bumped on conflict appearance, **cleared by the canonical-edit write**; participates in the shared panel hash; private edit contents never do.
- **Approval (`OPEN → APPROVING`, atomic):** locks the review; rejects unresolved conflicts and pending revisions; verifies expected `draft_version` + expected `canonical_edit_version` + canonical approved-payload hash (**that exact field name** in request bodies and command payloads); persists the frozen approved payload; creates command + outbox row. Frozen CAS key: unique `(case_id, review_id, draft_version, canonical_edit_version)` → 409. From `APPROVING` on, edit/cancel/redraft return 409 (UI surfaces the transition, not a bare error). Version authority = fact + edit stores, never a Temporal query. `auto_send` = same transition with `actor=SYSTEM`, refused by the same rejections; **an unresolved required gap forces hold/escalate regardless of `on_timeout: auto_send`**.
- **Guard-blocked at deadline** → `HELD_FOR_OPERATIONS`, reason `TEMPLATE_REVIEW_GUARD_BLOCKED`.
- **Recovery surface:** `POST .../reviews/{review_id}/recovery/{retry|abandon}` → command kinds `review_delivery_retry` / `review_abandon`, capability `RETURNS_REVIEW_RECOVERY` + case access. Retry reuses `logical_operation_id`, `delivery_id`, frozen payload; a retry absorbed by receiver dedupe still reaches `SENT`. **Per AMENDMENT-5:** retry requires the workflow execution to still hold the review (else 409 naming the legal action), and the gate moves every non-terminal review to `HELD_FOR_OPERATIONS` on close, so no review is ever without a legal exit.
- **Transactional boundary:** review aggregate + command/outbox + draft-edit store **co-located in one transactional datastore** (Mongo). If ever split: outbox and edit reads driven from the review aggregate; no cross-store transaction claimed.
- **Statuses & park reasons:** case status `AWAITING_TEMPLATE_REVIEW` (a legitimate wait — recovery never relaunches it); park reasons `TEMPLATE_REVIEW_UNANSWERED`, `TEMPLATE_REVIEW_CANCELLED`, `TEMPLATE_REVIEW_GUARD_BLOCKED`.
- **Workflow gate:** inserted in `_open_support` between `draft_support_request` and the send path, under `workflow.patched("support-template-review-gate")`; all request drafts created first, then **one map-based wait loop** over `{request_id → review state}` cloned from the `_await_policy_override` pattern (registered duplication — see §10); per-case reminder cadence (DR-7), deadline via `resolve_business_deadline`, resume field `resumed_template_review_deadline_iso` in `_continued_input()`. Config `support_gate.template_review{enabled: true, review_wait_seconds, reminder_interval_seconds, max_reminders, on_timeout: auto_send|hold|escalate = hold}`.

## 8. Template config & renderer (V1)

- New defaulted field `support_template: SupportTemplateConfiguration` on `ReturnPlatformConfiguration` (new module `configuration/support_template_configuration.py`); rides the release lifecycle; the case's pinned `configurationReleaseId` is the template version pin. Default `production.yaml` block reproduces today's `compose_support_handoff` output; `operations/support_handoff.py` is the un-patched-history fallback until post-gate retirement.
- Shape: `{template_id, variants[], default_variant_id}` → variant `{variant_id, selector, subject_template, sections[]}` → section `{section_id, title, fields[], visibility_rule}` → field `{field_id, label, source_binding, required, fallback, formatter, visibility_rule}`. Multi-record requests render per-record section groups stamped with `return_record_id`.
- **Constrained grammar — no scripting from config:** `formatter` = fixed code-side allowlist id (`text|date|currency|address|item_list`); `selector`/`visibility_rule` = declarative clause structs (`shipping_modes[]`, `return_reason_classes[]`, `order_sources[]`, `min_item_count`, `max_item_count`; all present clauses must match; first variant wins, else default); `subject_template` = `{field_id}` interpolation only, unknown ids rejected at release validation, literal braces `{{`/`}}`.
- **Binding per-source (four sources — see AMENDMENT-1):** `case_fact:<factName>` → scoped facts only; `return_record:<attr>` → **only attributes declared on the record projection; unconstrained `getattr` reach is forbidden** (AMENDMENT-2); `graph:<path>` → graph read; `literal:<text>` → constant text, no interpolation, no expression grammar, never a gap; `fallback` only after the declared binding fails; missing required → `TemplateGap{field_id, reason}` (review-blocking). **Batched sync:** collect all missing graph bindings per render, one `OnDemandSyncCoordinator.synchronize` per source, retry all together. Rendered fields record `{source, source_path, fact_id?}`. Within-draft resolution cache on re-render. `TemplateGap` comes only from the renderer; panel degradation is never a gap.

## 9. Resolver, clarification, panel (V3 / V1 / shared)

- **Resolver placement:** inspect and extend `operations/return_support/auto_responder.py` + `agents/support_response.py` first; a new graph only on a ledger-recorded verdict. Ladder: case facts → graph (own on-demand sync) → registered tools → associate clarification; thresholds `*_millionths`. Checkpointer `SystemStoreCheckpointSaver`, thread `support-resolver:{case_id}:{support_event_id}` (attempt = metadata).
- **Tool boundary:** raw support text can never directly name a tool or supply an argument; classification produces validated intent + required-entity schema; config maps intent → eligible capabilities (`ToolBindingConfiguration{tool_id, capability, contract, description, input_schema_ref, credential_binding_id}` → `CapabilityRegistry`); arguments only from trusted case facts/graph; execution requires schema validation + authorization; missing required entities → refuse. Credentials platform-side only; checkpoint-redaction allowlist test extended to the resolver state. Config-only tool addition = binding/enabling an existing capability implementation.
- **Reply gating:** `support_resolver.reply_gate{default: review_required, per_intent{}}`; gated replies are `SUPPORT_REPLY` reviews on the S2 aggregate. Sub-threshold / conflicting sources / missing entity → escalate, never answer. `per_case_llm_budget` exhaustion → fact + escalation.
- **Tone & disclosure:** shared tone/disclosure `systemPromptSections` anchors on all `support.*` ai_gateway tasks + config `support_ingress.agent_disclosure{display_name, disclosure_line}` applied to templated sends. Outbound composition default = config-templated (`support_ingress.outbound_templates{}`, §8 interpolation grammar); `support.outbound.compose.v1` only where configured.
- **Clarification:** fact `support_clarification_requested{clarification_id, verbatim_question, why_unresolvable, resolution_attempts[], needed_field}` (record-scoped where applicable) → typed system entry in the Order Discovery transcript (DR-3) + panel section. Answer endpoint → command+outbox → `clarification_answered` → relay to B (delivery identity) + `clarification_resets_deadline` per config. Unmatched-artifact clarifications carry value, evidence span, candidate records, and a map-or-reject choice.
- **Panel (DR-10):** `GET /api/v1/cases/{case_id}/panel` composes Temporal `execution_state` + scoped facts + record/request projection + thread digest + clarifications + `reviews[]` + conflict markers + accepted-command states + parked count; canonical order-stable serialization, **absolute instants only** (countdowns client-side from `deadline_iso`); hash = HTTP `ETag`; 304 saves bandwidth, composition always runs. Headers: `Cache-Control: private, no-cache` + `Vary: Authorization`. Every shared field is case-scoped and principal-independent (`accepted_commands[]` unfiltered); two principals, same case → identical body + ETag. Degradation only for expected timeouts/transient failures (`{status: degraded, reason}`); auth/contract/invariant failures are real errors. Per-actor edit state only at `GET .../reviews/{review_id}/edit-state` (actor-scoped version header; `RETURNS_SESSION_READ` + case access; `Cache-Control: private, no-store`).
- **Panel DTO:** `CasePanelView{case_id, execution, reviews[] keyed (review_kind, scope_id) each {state, review_id, draft, gaps, conflict_present, recovery_status}, return_records[], timers, accepted_commands[], sections[]}` — **per AMENDMENT-6, `support_digest`, `clarifications` and `parked_messages` are retired**; contributed sections arrive through `register_panel_section` only, one mechanism — `reviews[]` carries every non-terminal review (incl. `APPROVING`, `DELIVERY_FAILED`, `HELD_FOR_OPERATIONS`) plus recently-terminal for visibility. Section-registry seam: V1 ships the contract + registry and never touches it again; V2/V3 contribute sections in their own files. Same payload feeds `CaseOperationsPage`. Relay-visibility floor = `copilot.case_poll_interval_ms`.
- **Endpoints (all mutations: capability + case access, server-stamped actor; CSRF/size/rate limits on ingress + config publish):** `GET /api/v1/cases/{id}/panel`; `GET .../reviews/{review_id}/edit-state`; `POST .../reviews/{review_id}/{approve|revise|cancel}`; `POST .../template-review/redraft`; `POST .../reviews/{review_id}/recovery/{retry|abandon}`; `POST .../clarifications/{clarification_id}/answer`; `POST /api/v1/return-support/work-items/{id}/inbound-messages` (AMENDMENT-3).
